# 緯度経度から住所を探す

緯度経度から、最も近い住所（番地・号まで、無ければ町字、市区町村）を返す処理です。座標から住所を引くには、全国の町や番地の点から近いものを選ぶ必要があります。全国の番地・号の点を最初から全部持つと、住居表示で約 480MB、地番で約 10GB と見積もられ（運用手引の推定）、大きすぎます。Sora は、町字の代表点の全国の索引で近い町を絞り、その町がある市区町村の番地・号の点だけを取得して、最も近いものを選びます。結果は、土地の形で判定したものではなく、代表点の近さによる推定です。応答には、必ず `approximate: true` を付けます。

用語です。

- **町字**: 大字・丁目・小字などの町の単位です（[address-normalization.md](address-normalization.md) を参照）。
- **代表点**: 町字や番地の位置を 1 つの点で表したものです。デジタル庁の住所データ（ABR）が持ちます。
- **level**: 返した住所の細かさです。8 は番地・号、3 は町字、2 は市区町村、0 は見つからないことを表します。

## 使うツール

- MCP: `lookup_address` に `address` なしで `lat` と `lon` を指定する（応答の `mode` は `reverse`）
- REST: `POST /geo/reverse`、`GET /geo/reverse`

引数は、`lat`（緯度）、`lon`（経度）、`maxDistanceMeters`（番地・号の点を探す範囲。1 から 2000、既定 300）です。MCP の `lookup_address` では、`lat`・`lon` と `zipcode` を一緒に指定したり、`address` があるのに `maxDistanceMeters` を指定したりすると、正しい使い方を示す入力の誤りです（`address` と `lat`・`lon` は、住所との突き合わせ）。

## 手元のデータと外への問い合わせ

Sora は、次のデータを手元に持ちます（取得元は ABR と国土交通省です。保存と更新の仕組みは [address-normalization.md](address-normalization.md) と [address-data.md](../operations/address-data.md) にあります）。

- 町字の代表点の全国の索引（約 20 万点）。SQLite のファイルで、0.01 度（緯度でおよそ 1.1km）四方の格子に分けてあります。
- 全国マスター（市区町村の名前とコード）。
- 市区町村ごとの町字（段A）と、番地・号の点（段B）。
- 市区町村ごとの国土交通省の街区の点。
- 郵便番号（結果に郵便番号を付けるため）。

利用者の要求に答えている間に外へ問い合わせるのは、データがまだ無いときだけです。データがあれば、外には出ません。外部のジオコーディングのサービスは使いません。最初の 1 回は、索引と市区町村のデータの取得を待つことがあります（待ち時間は既定 20 秒）。

## 決め方

1. 入力を検査します。緯度が -90 から 90、経度が -180 から 180、`maxDistanceMeters` が 1 から 2000 の範囲外なら、入力の誤りです。緯度 20 から 46、経度 122 から 154 の範囲の外は、日本国内でないものとして `found: false` を返します。
2. 町字の索引で、近い町字を探します。座標のある格子から外側の格子へ広げながら、近い順に最大 10 件を取ります。距離は球面の距離（haversine）です。探す範囲は、`maxDistanceMeters` に 1,500m を足した距離です。町字の代表点は、広い町では町の端から遠いので、余裕を持たせています。1 件も無ければ `found: false` です。
3. その 10 件の町字がある市区町村を、近い順に最大 4 つ選び、町字と番地・号のデータを使えるようにします。
4. 町字ごとに、番地・号の点を調べます。住居表示の町は住居表示の点、それ以外の町は地番の点を見ます。町ごとにどちらか一方です。`maxDistanceMeters` 以内の点を集めます。
5. 集めた点のうち、最も近いものを答えにします（level 8）。住居表示なら `numberSource: "rsdt"`、地番なら `"chiban"` です。次に近い住所を、`alternatives` に最大 3 件、重複なしで入れます。
6. ABR の点が範囲内に 1 つも無いときだけ、国土交通省の街区の点を探します。範囲内の街区の点のうち、最も近いものを答えにします（`numberSource: "mlit"`、`point.level` は 7、level は 8）。地番の街区は、近くの複数の番地が 1 つの代表点を共有します。どの番地か決められないので、同じ点を複数の街区が共有しているときは、その点を使いません。
7. それも無ければ、最寄りの町字を答えにします（level 3）。`alternatives` には次に近い町字が入ります。
8. 町字の一覧を使えなかったとき（取得中か、取得の失敗）は、最も近い町字がある市区町村の代表点で答えます（level 2）。
9. 答えの住所に当たる郵便番号を付けます（[postal-code.md](postal-code.md)）。`distanceMeters` は、入力の座標から、見つけた点までの距離です。

## 決められないとき

この処理は、聞き返しません。見つからないときは、エラーにせず `found: false` を返し、理由を `reason` に入れます。

- `日本国内の座標ではありません`
- `付近に町字がありません`
- `付近の市区町村を特定できません`

```json
{ "lat": 35, "lon": -120 }
```

```json
{ "found": false, "reason": "日本国内の座標ではありません", "level": 0, "approximate": true, "postalCodes": [], "alternatives": [] }
```

ABR の番地・号の点も、国土交通省の街区の点も範囲内に無いときは、町字の答え（level 3）になります。`maxDistanceMeters` を大きくすると、どちらかの点に届くことがあります（上限 2000）。

データが待ち時間に間に合わなかったときは、取れている範囲の答えに `incomplete: true` と、足りないデータの ID（`pending`、例: `num:131016`）を付けます。番地・号のデータが無ければ、答えは町字止まりです。しばらくして同じ要求を送ると、番地・号まで届きます。

エラーは、住所の正規化と同じです（400 `INVALID_INPUT`、404 `ADDRESS_DISABLED`、502 `ADDRESS_DATA_PENDING`、502 `ADDRESS_DATA_UNAVAILABLE`）。

例です（テストの見本データでの結果の一部です）。

```json
{ "lat": 35.675915, "lon": 139.745515 }
```

```json
{
  "found": true,
  "level": 8,
  "numberSource": "rsdt",
  "approximate": true,
  "normalized": "東京都千代田区永田町一丁目7-1",
  "point": { "lat": 35.675912, "lon": 139.745512, "level": 8 },
  "postalCodes": [ { "zipcode": "1000014", "exact": true, "fallback": false } ]
}
```

## 限界

- 代表点による最寄り判定です。土地の形（ポリゴン）に座標が含まれるかは見ていません。境界の近くでは、座標が実際にある土地の隣の番地を返すことがあります。
- 町字止まり（level 3）の答えは、代表点が最も近い町字です。座標がその町字の範囲の中にあるとは限りません。
- ABR の番地・号の点は、地番では一部にしか位置参照が付いていません。国土交通省の街区の点は、近くの番地が 1 つの点を共有するときは使わないので、街区の点があっても町字止まりになることがあります。
- 国土交通省の街区の点は、街区の近似です。番地の特定ではありません。
- 近い町字 10 件がある市区町村のうち、近い順に 4 つまでしか調べません。
- 日本国内かどうかは、緯度経度の矩形で見ます。近隣の外国の座標が通ることがありますが、その場合は町字が見つからず `found: false` になります。
- 海上や山中など、範囲内に町字の代表点が無い場所は見つかりません。
- データは、取得元が更新して、Sora が再確認するまで古いままです。古さは `dataset.updatedAt` と `stale` で分かります。
- 地番を使った結果には、法務省の登記所備付地図データの出典が付きます。地番から所有者などの個人を特定する用途には使えません。
