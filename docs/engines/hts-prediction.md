# 商品名から HTS コードを推測する

米国へ輸出する商品には、10 桁の HTS コード（Harmonized Tariff Schedule。米国の関税率表の番号）が要ります。先頭の 6 桁は国際共通の HS コードで、残りは米国の細分です。商品名で関税率表を検索するだけでは、"wallet" や "wristwatch" のような普段の言葉と、表の用語が離れているので外します。

Sora の `lookup_hts` は、`htsCode` を省くと、英語の商品名・説明から、10 桁のコード・一般関税率・関連する規制の候補を決めます。公式の関税率表の全文検索と、米国税関（CBP）の分類判例（CROSS。手元の判例の索引から引きます）の二つを、6 桁の単位で合わせます。決めきれないときは、公式の階層の分かれ目を選択肢にした質問を返します。

同じ関税率表を使う照合（`lookup_hts` に `htsCode` を渡したとき。渡されたコードが表に実在するかの確認）も、このページで説明します。

## 使うツール

- MCP: `lookup_hts`（モジュール `trade` の遅延ツールです。`search_tools` で有効化します）。`htsCode` を省くと推測、渡すと照合で、応答の `mode` が `predict`・`verify` です。照合の `description` は、REST の `productDescription` に当たります。推測だけの引数（`productName`・`material` など）を `htsCode` と一緒に渡すと、入力の誤りです。
- REST: `POST /trade/hts-predict`、`POST /trade/hts-verify`。
- `check_product_compliance`（`POST /trade/compliance`）も、内部でこの二つを使います（[product-compliance.md](product-compliance.md)）。

## 手元のデータと外への問い合わせ

手元のデータは、USITC（米国国際貿易委員会）が公開する HTS の全件です。

- Sora には同梱していません。この機能が初めて使われたときに、USITC の公開エクスポートをダウンロードし、SQLite のファイルに保存します（保存先は `SORA_HTS_DIR`、既定は `SORA_DB_PATH` のあるディレクトリの下の `hts`）。ダウンロードは約 12MB、保存したファイルは約 21MB です。取得の時間切れは 90 秒です。
- 説明だけの中間行（"Other:" など）も含む完全な木として持ちます。各行に、祖先の説明（`path`）と、継承した関税率（`rateFrom`）を付けます。10 桁の行の多くは自分の行に率を持たず、いちばん近い祖先の率が適用されるためです。
- 全文検索の対象は、申告に使う行（これより細かい行を持たず、コードが 8 桁以上で、第 98・99 類でない行）で、約 2 万行です。SQLite の全文検索機能（FTS5）で引きます。語の語幹をそろえ、BM25（語の出現数と行の長さから点を付ける、検索で広く使う式）で並べます。
- 更新は 7 日ごとです。7 日を過ぎたあとの最初の利用では、古い表で答えながら、裏で取り直しを始めます。取り直しに失敗したら、1 時間は再試行しません。起動時の取得や定期の処理はありません。初回の取得に失敗したときは、その呼び出しがエラーになり、次の呼び出しで取り直します。
- 推測が使う表は最新の 1 版だけで、取り直すと前の版は残りません。版ごとの全件を残したいときは、`hts-archive` モジュールを有効にします（README の「Module 15: HTS Release Archive」）。1 日 1 回、全件の中身を比べ、変わっていたら `SORA_HTS_DIR` の `releases/` に版ごとに保存します。推測はこの保存を使いません。

CBP の分類判例は、手元の判例の索引から引きます（既定。`SORA_HTS_CROSS_SOURCE=local`）。

- CBP の判例検索（rulings.cbp.gov の API）は、2026 年 11 月の時点でボット対策の後ろにあり、プログラムからの要求は 403 になります（本文は `Security parameters are missing from this request context.`）。Sora はこれを避けません。そこで、公開されている判例のデータから作った索引を、Sora の GitHub のリリースに置いて使います。
- 索引は、推測が初めて呼ばれたときに取得します（gzip で約 8MB）。SHA-256 を確かめてから、SQLite の全文検索（FTS5）の表にして、HTS と同じ場所（`SORA_HTS_DIR`）に `cross.sqlite` として保存します。起動時の取得や常駐の処理はありません。用意ができるまでの呼び出しは、HTS の全文検索だけで答え、`evidence.crossNote` に「判例の索引を準備中」と残します。取得に失敗したら、1 時間は取り直しません。
- 照会は CBP の検索と同じく AND 条件です（照会語の全ての語を、判例の品名か説明に含む判例）。品名を説明の 2 倍の重みにした BM25 で並べ、上位 10 件を見ます。
- 判例を使ったときは、`evidence.attribution` に出典を表示します。判例番号のある判例は `evidence.rulings` に rulings.cbp.gov への URL つきで出します。判例番号の無い判例（下の ATLAS の分）は票だけに使い、`evidence.rulings` には出しません。
- `SORA_HTS_CROSS_SOURCE=api` にすると、これまでどおり CBP の API に問い合わせます（1 回 5 秒で時間切れ、24 時間キャッシュ、失敗したら 60 秒は問い合わせない、分類の判例だけで取り消された判例は除く）。今は 403 で `unavailable` になります。
- 自分で作った索引を使うときは、`SORA_HTS_CROSS_INDEX_URL`（`file://` も可）と `SORA_HTS_CROSS_INDEX_SHA256` を両方指定します。

### 判例の索引の作り方

索引は `scripts/cross-index/build_index.py` で組み立てます。いまの索引（cross-index-2）は、前の索引（cross-index-1）と、判例を品ごとに分けた公開データ（下の 3）から作ります。

前の索引（cross-index-1）の入力は、次の 2 つです。

1. **CBP の判例の原文**（Hugging Face の `orlandowhite/hts-cross-rulings`、版 `050ee2144e`、2000〜2025 年の 54,558 件）。使うのは、判例の原文（米国政府の著作物）と判例番号・日付だけです。データセットの要約の欄は使いません（ライセンスの記載が無いため）。
   - 原文を Claude Haiku 5.5 で、品名（通販の題名の形）と 1〜2 文の説明に書き直しました（Message Batches、構造化出力、考える過程なし）。8,000 字を超える原文は、前の 5,500 字と後ろの 2,500 字だけを渡しました。人・会社・ブランドの名前、住所、型番、判例番号、HTS のコードは書かないよう指示し、正規表現でも消しています。ブランドの名前は正規表現では消し切れないので、指示に頼っています。
   - 分類のコードは、原文の結論の決まり文句（"The applicable subheading for ... will be ..."）と、HQ の判例の HOLDING の節（"is classified in subheading ..."）から抜き出しました。無ければ Haiku が原文から抜き出したコードを使います。どちらも、データセットのコードと 6 桁まで合うものだけを残しました。
   - 残ったのは 45,552 件です（書き直せなかった 103 件と、コードが合わない・分類の判例でない 8,903 件を除く）。
2. **ATLAS のデータの写し**（Hugging Face の `Dayanand314Krishna/cross_rulings_hts_dataset_for_tariffs`、版 `0a66ad34`、Apache-2.0。元は “CROSS Rulings HTS Dataset for Tariff Classification” by Flexify.AI Inc.、https://huggingface.co/datasets/flexifyai/cross_rulings_hts_dataset_for_tariffs）。問い文（判例を要約した品物の説明）と、答えの 1 行目のコードだけを使い、説明からは名前・番号・コードを消しました。判例番号が無いので、票だけに使います。18,652 件で、重複を除くと 17,022 件です。

合わせて 62,574 件です。

**cross-index-2 での作り直し（2026 年 11 月）。** 上の 1 のデータは、2012〜2021 年の判例について、判例番号と中身（原文・コード）の対応が確かめられませんでした。下の 3 のデータと判例番号が重なる 11,030 件のうち、6 桁のコードが合ったのは 28.3% です（2022〜2025 年の 6,066 件では 96.4%）。日付は、重なる全部の件で一致しました。別の公開の写しで確かめられた 2 件は、どちらも 3 のデータのとおりでした。原文とコードの組は合っているので、票への影響は小さいですが、`evidence.rulings` の判例番号が別の判例を指します。そこで、2012 年からの判例は 3 のデータにしました。

3. **判例を品ごとに分けた公開データ**（Hugging Face の `fklc/cbp-rulings-past-2012`、MIT、Copyright (c) 2026 Fatih Kilic）。2012 年から 2026 年 7 月までの判例 36,276 件を、品ごとの 73,843 行にしたものです。品名・説明・コードは、データの作者が AI で判例から抜き出したものです。使うのは、判例番号・日付・品名・説明・コードです。品名と説明には、1 と同じ正規表現をかけました。第 98・99 類のコードの行と、8 桁・10 桁でないコードの行は入れません。58,894 行で、重複を除くと 58,685 行です。

組み立ては次のとおりです（`build_index.py` の `--base` と `--items`）。

- 前の索引の行のうち、日付が 2011 年までの行（28,172 行）と、判例番号の無い行（ATLAS の 17,022 行）は、そのまま残します。
- 前の索引の 2012〜2021 年の行（11,179 行）は入れません。
- 前の索引の 2022 年からの行は、同じ判例番号が 3 に無いものだけ残します（354 行）。
- 3 の行を、1 品 1 行で入れます。

合わせて 104,233 行です（判例番号のある行は 87,211 行で、判例にして 64,796 件）。2011 年までの行は、番号と中身の対応を照らす相手が無く、確かめられたのは 1 件だけです。出典の表示は、索引のファイルの見出しの行、`evidence.attribution`、リポジトリの `NOTICE` にあります。CBP の約 22 万件に比べると約 3 割で、2026 年 8 月からの判例は入っていません。

## 決め方

推測（`htsCode` を省いたとき）の手順です。

1. 入力を確かめます。`productName` と、`description`・`productCategory`・`material` をつないだ文に、英語の語が 1 つも無ければ、REST では 400（`INVALID_INPUT`）、MCP では `isError` の応答です。HTS も判例も英語だからです。
2. 否定された語（"not ceramic"、"without battery"、"non-..."）は検索語から外します。`hasBattery` が `true` のときだけ、検索語に `battery` を足します。
3. 次の二つを並行して行います。
   - HTS の全文検索（上位 60 行）。説明の語を、祖先の説明の語の 3 倍の重みで数えます。
   - 判例の照会。照会語は、具体的なものから順に、品名の全ての語、前置詞（for・with など）より前の名詞句、その後ろ 4・3・2・1 語です。`material` があれば、素材つき（"plastic coaster"）を先頭に置きます。10 件集まるまで続けます。照会は AND 条件で、語が多いと 0 件になるためです。ヒットが多すぎる語は上位が無関係になるので、そこで打ち切ります（手元の索引では 250 件、CBP の API では 2,000 件。250 は dev だけで決めました）。
4. 判例が挙げたコードを、現行の表にある 6 桁に直します。改訂で番号が変わったコードは、上位 5 桁が同じ 6 桁へ、なければ見出し（4 桁）の下の 6 桁へ振り分けます。振り分け先が 6 個を超えるときは使いません。
5. 判例に票を付けます。判例の重みは 1/(順位+1) で、1 件の判例が複数の 6 桁を挙げたら等分します。
6. 候補の 6 桁を作ります。判例の票の多い順に 6 個、全文検索の上位から 6 個を合わせます。どちらも空なら 400 です。
7. 6 桁ごとに点数を付けます。`0.7 × 判例の票の割合 + 0.3 × 全文検索の点数` です。全文検索の点数は、候補の 6 桁の中だけで測り直した値を、最大値で割ります。商品の語が表に無いと、全体の検索は無関係な行に引かれるためです。この重み 0.7 は、評価セットの dev で決めました。
8. 部品・付属品を減点します。見出しが "Parts" で始まる 6 桁は、商品の語に部品・付属品を示す語（part・accessory・case・cover・strap・charger など）が無いとき、点数を 0.5 倍にします。
9. 点数が最も高い 6 桁を採り、その中の 10 桁の行を選びます。入力から読める年齢・性別（"men's"、"aged 3+"、"toddler" など。`targetAge: child` も使います）と、公式の行の説明文（"Men's"、"Under 3 years of age" など。10 本の正規表現で読みます）を突き合わせ、合わない行を除きます。そのうえで、次の順に最初に見つかった行を採ります。
   - 判例が挙げた行（票の多い順）。
   - 判例が挙げた 8 桁の下の、全文検索の上位の行。
   - 最有力の 6 桁の中の、全文検索の上位の行。
   - 年齢・性別に合う行。
   - 最後の行（多くは "Other"）。
10. 確度（`confidence`）を決めます。しきい値は、dev と test の 103 件で適合率を測って決めました。
    - 判例の票が 1 つも無い（照会できない・該当なし）ときは `low` です。全文検索だけの推測は、旧い規則で `medium` になった 25 件でも的中が 16 件（dev では 12 件中 6 件）でした。
    - `high`: 全文検索の 1 位、判例の 1 位、最終の 6 桁が同じで、判例の票の割合が 0.4 以上。
    - `low`: 1 位と 2 位の点数（0〜1 の値）の差が 0.1 未満、または全文検索の 1 位も判例の 1 位も最終の 6 桁でない。ただし、年齢・性別で 10 桁を決められ、どちらかの 1 位が最終の 6 桁なら `medium`。
    - `medium`: それ以外。
11. 候補（6 桁ごとの代表の行、最大 5 件）を作ります。確度が `high` でなければ、分岐点の質問も作ります。候補の行が公式の階層で最初に分かれる位置を探し、その位置の公式の説明文を選択肢（最大 6 個、各 160 字まで）にします。6 桁が競っている（2 位が 1 位の 0.6 倍以上）ときは 6 桁の代表どうしを、そうでなければ最有力の 6 桁の下の全ての行を比べます。商品の語を含まない行も選択肢になります（自転車用ヘルメットは "Athletic, recreational and sporting headgear" で、"helmet" の語を含みません）。
12. 最有力のコードで、CPSC と FDA の判定を呼び、足りない情報を質問にまとめます（[cpsc-certificate.md](cpsc-certificate.md)、[fda-regulated.md](fda-regulated.md)）。

照合（`htsCode` を渡したとき）の手順です。

1. コードから点を除きます。8 桁以上で、表に行があれば `matchLevel: exact` です。公式の説明・階層での位置・率（継承した率を含む）を返します。8 桁の行にこれより細かい 10 桁の行があるときは、細かい行（30 件まで）を `nearbyCandidates` に入れ、10 桁を確かめる質問を返します。
2. 行がなくても、先頭 6 桁の下に行があれば `6-digit-category`（`verified: false`）です。近い行を返し、10 桁を確かめる質問を返します。
3. どちらもなければ `unmatched` です。商品の説明（MCP の `description`、REST の `productDescription`）は必須ですが、判定には使わず、根拠の記録として応答に返します。

## 決められないとき

- 英語の語が無い入力、日本語の字が英字より多い入力（日本語の商品ページの英字はブランド名や mAh・USB などの単位の断片で、無関係な品目に引かれます）、該当する品目が見つからない入力は、REST では 400 `INVALID_INPUT`、MCP では `isError` の応答です。`/trade/compliance` は、`htsCode` を省いたときに限り、エラーにせず `needs_more_info` で英訳を促します。
- 確度が `high` でないときは、`decisionPoints`（選択肢つきの質問）と `clarifyingQuestions` を返し、`missingInputs` に `classificationDetail` を入れます。利用者の答えとなる区分の語を `description` に足して、再実行します。

  ```json
  { "productName": "Bicycle Helmet", "description": "Protective helmet for road cycling" }
  ```

  この入力では、確度 `medium`、最有力は `6506.10.60.45` で、次の質問が付きます（README の実行例から抜粋。選択肢は 6 個のうち、(1) と (3) だけ）。

  ```
  分類の確認: 公式の区分「Safety headgear」のうち、商品が当たるのはどれですか？
  (1) Other › Other › Athletic, recreational and sporting headgear [6506.10.60.45, Free]
  (3) Other › Motorcycle helmets [6506.10.60.30, Free]
  ```

- 確度が `high` でなく `material` が無いときは、素材の指定を促す質問を足します。同じ品名でも、素材で章が分かれるためです（plastic coaster は 3924.10、textile coaster は 6304.93、ceramic coaster は 6912）。

## 限界

評価は、日本からの輸出が多い品目を中心にした 150 件（dev 52・test 51・保留 47、英語）で行いました。正解の 6 桁は作者が 1 人で付けたので、誤りが残っているかもしれません。10 桁の選択は測っていません。

| | 1 位の 6 桁が正解 |
|---|---|
| 全体（150 件。調整に使った dev を含む） | 72.0%（手元の判例の索引。前の索引 cross-index-1 でも、CBP の API でも 72.0%） |
| 調整に使っていない保留（47 件） | 66.0%（信頼区間は約 ±13 ポイント。前の索引でも、CBP の API でも 68.1%。1 件の差） |
| 判例なし（HTS の全文検索だけ） | 37.3%（確度はいつも `low`） |

- 上の表の数は、いまの索引（cross-index-2）で 2026-11-14 に測ったものです。前の索引（cross-index-1）と比べて、1 位の 6 桁の正解は、dev 39 → 41 件、test 37 → 36 件、保留 32 → 31 件で、全体は 108 件のままでした。索引を替えたねらいは、根拠に出す判例番号を正すことで、精度は変わっていません。
- 候補（上位 5 つの 6 桁）に正解が入る割合は 86.7% です（保留では 83.0%。CBP の API では 89.3%）。
- 確度ごとの的中率（手元の判例の索引）は、`high` 100%（31/31）、`medium` 83%（59/71）、`low` 38%（18/48）です。しきい値の決定に使った件を含みます。
- 商品の語が HTS にも判例にも乏しい品目（laptop・toothpaste・webcam など）や、同じ見出しの兄弟（磁器と陶器、靴の底の材質）は外れやすいです。調整を重ねても、1 位の一致率は上がりませんでした。評価の詳細は [docs/evaluations/hts-predict/results.md](../evaluations/hts-predict/results.md) にあります。
- 入力は英語だけです。長い出品タイトルは判例に当たらないことがあり、そのときは全文検索だけで答えます。
- HTS は最大 7 日古いことがあります。判例の索引は 2026 年 7 月までの判例で、リリースで入れ替えるまで更新されません。索引の準備中（初回の取得の間）と取得に失敗している間は、判例なしで答えるので、精度が下がります。
- 一般関税率だけを返します。Chapter 99 の追加関税（通商法 301 条など）は計算せず、通関士への確認を案内するだけです。
- このツールは分類の確定ではありません。自動で採用してよいのは `high` のときだけにしてください（`check_product_compliance` は `medium` も先へ進めます）。通関に使う前に、`evidence.rulings` の判例と CROSS で確かめてください。
