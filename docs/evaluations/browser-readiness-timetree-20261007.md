# ブラウザ待機とTimeTree公開カレンダーの修正（2026-10-07）

## 修正内容

モデルを変更せず、追加のLLM呼び出しも使わずに取得処理を改善した。

- Web検索完了後、独立したX検索の完了を待たずにWeb本文の取得を開始する。X検索結果は最終応答で従来どおり統合する。
- 描画後に本文が空の場合、新しいブラウザコンテキストで再アクセスせず、同じページで追加待機する。追加待機は最大2秒で、ナビゲーションからの残り期限を超えない。
- `Loading…`など、CSSクラスを持たない読み込み表示もDOM待機で認識する。
- 待機中の判定には、実際のcomputed styleに基づいて非表示要素を除いたHTMLのコピーを使う。描画途中の生DOMは削除しない。
- Shadow DOMのコピーを再取得時に更新し、本文の重複を防ぐ。
- Readabilityが日付gridだけを残し、予定ボタンを削除する場合、本文を保持する意味的コンテナで救済する。通常の表ページでは既存のReadabilityによるノイズ除去を維持する。
- TimeTree公開カレンダーでは、ページ自身が取得した`public_events`レスポンスを期限内で回収し、予定名・日付・説明・会場・リンク・画像を本文とEvent構造化データへ反映する。別途APIを呼び出したり、独立した認証を追加したりしない。終日予定の日付を出演時刻と混同せず、出演時刻は原文の説明として保持する。
- scrapeと統合検索のキャッシュ名前空間をv2に変更し、修正前の取得失敗結果を再利用しない。その他のキャッシュは維持する。

`responseMode`の既定値は`full`のまま。明示的な`evidence`は従来どおり、highlightsがあればmarkdownを省略する。全文と同じ情報量になるという保証は追加していない。

## 原因の実測

対象は`https://timetreeapp.com/public_calendars/kimisora?locale=en`。
公開予定APIと描画は成功していた。描画後のDOMには17件の予定がある一方、Readability後の本文は日付gridのみとなり、最終結果は`metadata_only`、28文字、予定0件だった。この空判定により、同じURLへの再ナビゲーションも発生していた。

修正後は`contentStatus: body`、予定17件となった。10月7日の「超 明星現象 2026」、ライブ15:00〜15:20、特典会15:35〜16:35、会場Spotify O-Crestを原文どおり確認した。取得範囲は公開ページ自身が読み込んだ予定であり、全月の巡回取得は行わない。

## 取得時間

旧イメージと候補を、このホストの別コンテナ・別インメモリDB・別ポートで実行した。Bun 1.4.2、Chromium、依存パッケージは同一。検索は旧→新、新→旧、旧→新の順で3回ずつ実行した。

| 対象 | 旧版 | 修正版 |
| --- | ---: | ---: |
| TimeTree単体、キャッシュ不使用、1回 | 7.733秒、metadata_only | 3.611秒、予定17件 |
| deep検索、1回目 | 16.197秒 | 13.685秒 |
| deep検索、2回目 | 41.368秒 | 13.728秒 |
| deep検索、3回目 | 20.031秒 | 13.397秒 |
| deep検索、中央値 | 20.031秒 | 13.685秒 |

deep検索の中央値は約32%短縮した。終わらない描画の再アクセスと、失敗後の追加候補取得による長い待ちも減った。

検索引数は`query: "君と見るそら　ライブ"`、`responseMode: "evidence"`、`noCache: true`。limit=5、includeRealtime=true、adaptiveScrape=falseなどは既定値を使った。既存のdeep検索は`noCache`を子scrapeへ渡さないため、各回の`maxChars`を29960、29959、29958に変えて未使用の子キャッシュキーを使った。対象本文はこの文字数以下で、切り詰めは発生していない。各回のWeb取得結果で子キャッシュ再利用がないことも確認した。

旧版は失敗補充によりWeb結果6〜7件、修正版は指定limitどおり5件となった。修正版は3回ともTimeTreeの17予定とXの24結果を保持した。外部サイトの応答・検索順位・失敗補充が変動するため、URL集合を固定した純粋な処理時間比較ではない。ユーザー申告の34秒と同一の計測にはならないが、旧版で41秒の待ちを再現した。

先行調査でのTavily advanced約13.5秒、Firecrawl本文付き検索約17.4秒は、別条件の単発計測だった。今回の結果だけで、競合より常に速いとは判定しない。Tavily basicの約2.5秒はraw contentなしのため、本文取得を含む今回の検索とは比較できない。

## 検証

ブラウザを含む関連37テストとTypeScript型チェックが成功した。既存のCookie・localStorage・言語設定・lazy load・Shadow DOM・遅延描画・本文抽出の対象テストも確認した。予定ボタン消失、表へのnav/footer混入、Shadow DOM重複、非表示本文の早期完了、独立したX検索によるWeb取得開始の遅延、待機中に追加された予定レスポンスの取りこぼしは、修正前の失敗と修正後の成功を確認した。

キャッシュを使わない実TimeTree取得、実deep検索3回、公開MCPと本番の結果は運用記録とローカル検証成果物に記録する。
