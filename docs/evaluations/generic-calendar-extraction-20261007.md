# 汎用スクレイピングへの修正（2026-10-07）

ユーザーが求めていたのは、サイト専用実装による取得ではなく、汎用スクレイピングの強化によるTimeTreeの取得だった。前回追加したTimeTree専用処理は、この意図と一致していなかった。

## 変更内容

- `src/timetree.ts`と専用テストを削除した。
- ブラウザのホスト名・公開カレンダーパス判定、予定APIレスポンスの回収、APIデータからのMarkdown・Event JSON-LD生成を削除した。
- Web検索とX検索の重複実行、同じページでの追加描画待機、テキストローダー判定、非表示要素のコピー上での剪定、Shadow DOMの更新、Readabilityが落とした表・grid本文の救済は維持した。
- scrapeとdeep検索のキャッシュ名前空間をv3へ変更し、専用処理が生成した古い結果を再利用しないようにした。
- カレンダー予定ボタンの本文保存テストは`example.com/calendar`で検証し、TimeTreeのURLに依存しないことを確認した。

本体コードにTimeTreeのホスト名・APIパス・独自レスポンス項目を使う分岐はない。追加依存パッケージ・LLM呼び出しもない。`responseMode`の既定値は`full`のまま。

## 実ページの観測

対象は`https://timetreeapp.com/public_calendars/kimisora?locale=en`。ブラウザの描画済みDOMから予定名17件を取得できた。通常表示にはライブ出演時刻・会場・予定説明がなく、予定ボタンを手動で開いたときに詳細がDOMへ表示された。

通常表示の汎用scrapeは`contentStatus: body`、Markdown 478文字、取得時間4.906秒だった。予定名「超 明星現象 2026」を含み、詳細表示だけに存在する「15:35」は含まない。`events`は生成しない。前版のAPI補完による予定17件の構造化データ・説明全文と同じ情報量ではない。

手動で詳細を開いた観測では、会場Spotify O-Crest、ライブ15:00〜15:20、特典会15:35〜16:35がDOMとMarkdownに現れた。今回の通常scrapeに、予定ボタンを自動操作する処理は追加していない。

deep検索は`query: "君と見るそら　ライブ"`、`responseMode: "evidence"`、`noCache: true`、`maxChars: 29945`で実行し、11.357秒だった。独立したインメモリDBを使用し、子scrapeキャッシュの再利用を避けた。TimeTree、イープラス、LivePocket、公式サイトが`body`となった。Xの検索結果も返った。別条件・別取得範囲の単発計測であり、前回のAPI補完版や競合との厳密な速度比較ではない。

最初の観測では一度`Loading...`のまま取得が終わったため、TimeTreeの外部応答・描画の変動も残る。取得成功を常時保証するものではない。

## 検証

- `SORA_DB_PATH=:memory: NODE_ENV=test bun --no-env-file test`: 1,297成功、22スキップ、失敗0件。スキップにはChrome未導入のホストでのブラウザ試験や、ライブ認証・配送番号などを必要とする試験を含む。
- 本番と同じBun 1.4.2・Chromium・依存パッケージを使う隔離コンテナの関連ブラウザ・本文抽出試験: 26成功、失敗0件。
- 本番サービス・永続DBから分離したソース検証で実scrape・deep検索を実行した。取得結果は`/tmp/sora-generic-observation/out/`、試験ログは`/tmp/sora-generic-*-tests.log`へ保存した。

以前の記録で「予定17件」は専用API補完によるEvent構造化データを指す。この版で取得する「予定名17件」と区別する。
