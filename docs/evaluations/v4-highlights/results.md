# ハイライトの評価（全文から選ぶ・リンクだけの段落を外す）

2026-11-04。ハイライト（検索語に合う節の選び方、`extractQueryHighlightDetails`）に入れた、次の 2 つの直しを測りました。設計は `docs/superpowers/specs/2026-11-04-v4-extraction-and-params-design.md` の 4 です。

1. **全文から選ぶ**: `maxChars`（既定 30,000 字）で切る前の本文から選びます。元にする本文の上限は 200,000 字です（`HIGHLIGHT_SOURCE_MAX_CHARS`）。それまでは、切った後の 30,000 字から選んでいたので、それより後ろにある答えを選べませんでした。
2. **リンクだけの段落を外す**: 節の中の、短いラベルのリンクだけでできた段落（2 行以上。Wikipedia の言語の一覧など）を、ハイライトの候補にも書き出しにもしません（`parseMarkdownSections` の `dropNavParagraphs`）。

比べたのは、基準（base）が main の 294f1e0、直したブランチ（branch）が `fix/v4-extraction-and-params` の 23822f5 です（そのあとに足した直しは、「評価の方法」の「共通」に書きました）。実行は、どちらも CI と同じ Bun 1.4.2 です（Bun の版で `Intl.Segmenter` の語の切り方が違います）。

## 結果のまとめ

- **JQaRA（ふつうの本文で段落の選び方が変わらないか）**: dev 1,737 問・test 1,667 問のすべてで、選ぶハイライトも点数も base と branch で同じでした（違う問いは 0 問）。選んだ段落の正解の割合は変わりません。ただし、JQaRA の候補はリンクの記法をほとんど含まず（`](` を含む候補は dev 86,850 件中 16、test 166,700 件中 30）、リンクだけの段落を外す処理はほぼ働きません。同じになるのはデータの作りからほぼ決まっていて、リンクの多い本文の段落を誤って外す危険は、このテストでは測れません。
- **200,000 字の時間**: 日本語の 72 ページをつないだ 200,000 字で、ハイライトを選ぶ時間は中央値 13.0〜29.5 ms（3 回。基準は 200 ms 以下）でした。長い Wikipedia の記事 10 件の先頭 200,000 字では、中央値 12.6〜79.6 ms です。リンク行の判定を狙って作った入力（`](` を何万回も含む 1 行。この 1 つの形だけの測定です）は、直す前は 200,000 字で 6.9 秒かかりましたが、同じ判定になる形に直したあとは 70 ms です（base は 65 ms）。中央値の基準を下回り、この入力も 70 ms に収まったので、上限は 200,000 字のままです。ただし、`>` だけの行を 10 万本並べた 200,000 字の文書では、ハイライトの抽出が約 3.4 秒かかります（25,000 字で約 0.5 秒。字数に比例して増える後段の費用で、上限を 30,000 字から 200,000 字に上げた分です）。節の分け方のほかの形（パンくずの行の並びなど）は、時間の節に続けて書きました。
- **長いページ 10 件**: Wikipedia の長い記事で、先頭の 30,000 字より後ろにある事実を問うと、答えがハイライトに入ったのは base が 0 件、branch が 10 件でした（本文の URL で日本語などの字をパーセントエンコードして書いていた直す前は 9 件で、富士山だけ入りませんでした）。ハイライトに言語の一覧が入ったページは、base が 4 件、branch が 0 件です（rs-trafilatura の無い経路の数字。本番の経路（rs-trafilatura あり）を保存した HTML で調べると、答えの有無は同じで、言語の一覧が入るのは base が 1 件、branch が 0 件です）。branch の数字は、直したあとに取得をやり直さず、保存した HTML を手元のサーバーから返して測り直したものです。
- **実際の search_deep（40 問）**（「実際の search_deep（40 問）」の節）: `response-compression` の 4 回目と同じ 40 問を、直したブランチの `integratedSearch` で 1 問 1 回、実際に検索しました。`full` に答えがあった問い・ページのうち `evidence` にも残る割合は、問いが 28 問中 25 問（89.3%。4 回目は 29 問中 25 問・86.2%）、ページが 90 ページ中 80 ページ（88.9%。4 回目は 92 ページ中 79 ページ・85.9%）で、下がりませんでした。4 回目にも今回にも出た同じページ 141 件では、4 回目に残って今回落ちたページは 0 です。今回落ちた 3 問・10 ページは、どれも 4 回目にも落ちていたものです（同じ問い・同じ URL で照らしました）。検索結果は取るたびに入れ替わり、4 回目と同じページは 7 割弱です。そのため、数の差（+3 ポイント）は変更の効果とは言えません。
- **気づいたこと**（「気づいたこと」の節）:
  - Wikipedia の長い記事でも、branch の Markdown が 200,000 字を超えるのは 10 件中 2 件（第二次世界大戦 600,916 字・新幹線 208,075 字）です。上限より後ろの答えは選べません（新幹線は、上限の外が脚注類だけで、本文は全部入ります）。
  - 本文の URL で日本語などの字をパーセントエンコードしないので、branch の Markdown は base の 84〜96% の長さで、同じ 30,000 字に入る本文の字は、10 ページとも base 以上（base の 1.04〜2.16 倍）です。直す前（パーセントエンコードして書いていたとき）は、branch の Markdown が base の 1.17〜1.37 倍長く、30,000 字に入る本文の字は base の 52〜100% でした（大阪府 9,408 → 4,885）。
  - 節の分け方（`src/extractor/markdown_sections.ts`）の 3 か所が、作った入力で長く止まりました。リンクだけの段落の判定は、`](` を何万回も含む 1 行で二乗の時間がかかり、200,000 字で 6.9 秒でした（30,000 字では 0.2 秒）。前置き（最初の見出しの前）のパンくずの判定は、`[a](b)` を 20 回並べて `x` を付けた 121 字で、組み合わせが指数で増え、正規表現だけで 2.6 秒かかりました（base にもあります）。パンくずの行（`> 📍 **階層**: A > B > C`）から最後の節を取る正規表現は、区切り（`>`）を 27 個以上並べた行が文書の終わりにあると約 1 秒、失敗する行を 5,000 本並べた文書で 3.0 秒止まります（base にもあり、ページの HTML から作れます）。最初の 2 つは、同じ判定になる正規表現に置き換えました。直したあとは、リンク行の判定が 200,000 字で 70 ms（30,000 字で 33 ms）、前置きの判定が 0.06 ms です。3 つ目は、置き換えた正規表現（途中で試した形）が、失敗する行の並び（5,000 本で 21 秒）と空白の長い行（10 万字で 12 秒）でかえって遅かったので、正規表現をやめ、行ごとに読んで最後の区切りの後ろを取る形にしました。直したあとは、失敗する行 5,000 本が 7.8 ms、空白 10 万字の行が 1.6 ms、`>` が 20 万個並ぶ 1 行が 20 ms です。この形では、前の正規表現が、行が区切りで終わるときに改行をまたいで次の行の字を取っていた（本文の 1 行目を見出しにしていた）ことが、なくなりました。
  - 直す前は 1 件（富士山）が、答えの節は選んだものの、書き出す窓が答えの 1 文手前で終わっていました。直したあとは URL が短くなった分だけ窓に入る本文が増え、答えまで届きます。窓の長さは URL の字も数えて決まるので、答えが窓の端にあるページでは、URL の長さで当たり外れが変わりえます。

## 評価の方法

### 共通

- **版**: base は main の 294f1e0（v3.0.0 のあと）、branch は `fix/v4-extraction-and-params` の 23822f5（base から 24 コミット先）です。
- **本文の URL の直し**: 23822f5 のあとに、本文のリンクと画像の URL で日本語などの字をパーセントエンコードしない直し（`absolutizeContentUrls`）を足しました。「3. 長いページ」の結果と「気づいたこと」の本文の字の表は、この直しを足した branch（節の分け方の 3 つの直しも入っています）で測り直した数字です。時間も、200,000 字の文書・実際の長い記事・`scrapeUrl` 全体は、この直しを足した branch で測り直しました（時間の値は、直す前と大きく変わりませんでした）。作った最悪の入力と JQaRA は、本文の URL を通らないので、23822f5 などでの値のままです。
- **直す前・直したあと**（作った最悪の入力の測定だけ）: 「直す前」は branch の 23822f5 です。「直したあと」は、23822f5 に、節の分け方（`src/extractor/markdown_sections.ts`）の 3 つの直し（リンク行の判定と前置きのパンくずの判定の正規表現の置き換え、パンくずの行から最後の節を取る処理を行ごとに読む形に書き換えること）だけを足した branch です。最初の 2 つは、前の形と同じ判定になることを確かめてあります。3 つ目は、前の正規表現が改行をまたいで次の行の字を取った場合だけが変わります（「気づいたこと」）。
- **実行**: `HTTPS_PROXY` と `HTTP_PROXY` を外して、それぞれの作業ツリーの直下で走らせました。計算機は AMD EPYC-Milan（6 コア）、Linux 6.12 です。
- **文字数**: 文字数と位置は、JavaScript の `String.length`（UTF-16 の単位）で数えています。

### 1. JQaRA

- **評価集**: JQaRA（https://huggingface.co/datasets/hotchpotch/JQaRA、CC BY-SA 4.0）。質問は JAQKET、文章は Wikipedia です。dev は 1,737 問 × 候補 50 件、test は 1,667 問 × 候補 100 件です。parquet から JSONL への変換の手順は `scripts/eval-jqara.ts` の先頭にあります。評価集の説明は `docs/evaluations/term-matching/results.md` にあります。
- **実行**: `bun scripts/eval-jqara.ts --data <JSONL の場所> --split <dev か test> --select`。`--select` は、問いごとの候補を 1 つのページの段落（`## 見出し` と本文）とみなして `extractQueryHighlightDetails` を呼び、選んだ段落のうち正解の割合（precision）と、1 つでも正解を選べた問いの割合（hit）を出します。
- **同じかどうかの確かめ**: 出力の文字列を `cmp` で比べたほか、1 つのプロセスに base と branch の両方のモジュールを読み込み、全問で `highlights` と点数が文字まで同じかを数えました。さらに、問いごとの文書を `parseMarkdownSections` に通し、base と branch で節の本文が違う問いを数えました（リンクだけの段落を外す処理が働いたかを見るためです）。
- **何を確かめるか**: 「リンクだけの段落を外す処理が、ふつうの本文のハイライトを変えない」ことです。ただし、このテストの検出力は低いです。
  - JQaRA の候補は Wikipedia の本文の段落で、1 件ずつは短く（最大 403 字）、リンクの記法を含むものがほとんどありません（`](` を含む候補は dev 86,850 件中 16、test 166,700 件中 30）。リンクだけの段落を外す処理が節を変えた問いは、dev・test とも 0 問でした。同じ出力になるのは、データの作りからほぼ決まっています。
  - そのため、リンクの多い本文の段落を誤って外す危険は、このテストでは測れません。
  - 候補 1 件ずつは、30,000 字を超えません。問いごとにつないだ文書（`eval-jqara.ts` が `extractQueryHighlightDetails` に渡すもの）では、test の 64 / 1,667 件が 30,000 字を超えます（最大 35,545 字。dev は最大 17,630 字）。ただし、`eval-jqara.ts` は `extractQueryHighlightDetails` を直接呼び、全文の上限（`finalizeScrapeResult` の側）を通らないので、結果に影響しません。全文を渡す側の変更は、このテストでは通りません。
- **判断と回数**: dev で確かめ、test は、精度の指標を base と branch で 1 回ずつ測りました（出力は `cmp` で比べました）。ほかに、同じ出力かの確かめを 2 つ（1 つのプロセスで `highlights` と点数を比べるものと、`parseMarkdownSections` の節の本文を比べるもの。どちらも精度の指標は出しません）、それぞれ dev・test の全問で 1 回ずつ走らせました。

### 2. 全文の上限（200,000 字）の時間

- **200,000 字の文書**: 日本語の 72 ページ（`docs/evaluations/main-content/results.md` の日本語のページ。HTML のある 38 + 34 ページ）を `convertHtmlToMarkdown(html, url, 10_000_000, false, true)` で Markdown にしてつなぎ、先頭の 200,000 字を取りました。
- **測り方**: 3 つの検索語（`開場時間 チケット`・`収容人数 球場`・`release date version`）で、同じ文書に `extractQueryHighlightDetails` を 10 回かけ、中央値（小さい順の 6 番目）と最大を出しました。プロセスを替えて 3 回測りました。
- **基準**: 中央値 200 ms 以下。超えたら `HIGHLIGHT_SOURCE_MAX_CHARS` を 100,000 にして測り直します。
- **あわせて測ったもの**:
  - 同じ文書を 30,000 字で切った場合（今の動き）と、base のコードに 200,000 字を渡した場合（リンクだけの段落を外す処理の費用を分けるため）。
  - 実際の長い記事: 下の 3 で取得した 10 件の Markdown の先頭 200,000 字に、それぞれの検索語をかけた時間。
  - 作った最悪の入力: `[` で始まり、`](` を `n` 回並べ、`x)y)` で終わる 1 行（`[` + `](` × n + `x)y)`）を、`[a](b)` の行のすぐ後ろに置いた文書（空行を挟まないので、2 行の 1 つの塊になる）。リンクだけの段落の判定（`isNavBlock` の `BRACKET_LINK_LINE`）が、この形で二乗の時間がかかる、と先に指摘されていたので、その大きさを測りました（直す前）。実際のページでは見つかっていません。この判定を同じ判定になる別の形に直したので、直したあとの branch でも、同じ入力・同じ測り方で測り直しました。
  - 前置きのパンくずの判定: 最初の見出しの前の、`[リンク](URL)` の並びだけの節を外す正規表現が、`[a](b)` を `k` 回並べて `x` を付けた文字列（`x` があるので当たらない）で、組み合わせが指数で増えることが分かりました。base にもあります。これも同じ判定になる別の形に直したので、前の形と新しい形の正規表現だけを、同じ文字列で測りました。あわせて、その文字列に `\n\n# 見出し\n\n本文です。` を足した文書を `parseMarkdownSections` に通した時間も測りました。
  - パンくずの行から最後の節を取る処理（`breadcrumbMatch`）: `> 📍 **階層**: A > B > C` の行から最後の C を取る正規表現が、区切り（`>`・`›`・`\`）の多い行が文書の終わりにあると、組み合わせが指数で増えることが分かりました。base にもあります（入ったのは 2026-09-11）。最初は同じ判定になる別の正規表現に置き換えましたが（途中で試した形）、失敗する行の並びと空白の長い行で長く止まったので、正規表現をやめ、行ごとに読む形にしました。直す前・途中で試した形・この形を、`# 見出し` と本文の後ろに `> 📍 **階層**: ` + `>` を `n` 個並べた行を置いた文書、失敗する行（`> 📍 **階層**: >`）を 5,000 本並べた文書、空白の長い行で測りました。この行がページの HTML から作れるかは、記事ふうの HTML を `convertHtmlToMarkdown` に通して確かめました。あわせて、ほかの形（200,000 字前後の 28 通り）も測りました。

### 3. 長いページで、後ろのほうの答えが選ばれるか

- **ページ**: 日本語版 Wikipedia の長い記事 10 件（日本の歴史・東京都・第二次世界大戦・江戸時代・新幹線・宝塚歌劇団・富士山・日本の鉄道・大阪府・明治維新）。
- **取得**: base と branch のそれぞれの `src/scraper.ts` から `scrapeUrl` を import し、`{ url, query, noCache: true, mode: 'fast' }` だけを渡して 1 ページ 1 回ずつ呼びました。ほかの引数は既定のままです。応答の `highlights` を判定に使います。
  - 取得は 1 ページあたり 4 回です（問いを作るために全文を読む 1 回・base・branch・補助実験用の HTML の保存）。ページの間は 2.5 秒以上あけました。
  - この環境では `RS_TRAFILATURA_PATH` を設定していないので、本文は全ページ Readability の経路で作られました（補助実験は下の「rs-trafilatura を使う経路」）。
  - 本文の URL の直しのあとの branch は、取得をやり直さず、保存した HTML を手元のサーバーから返して、同じ呼び方（`RS_TRAFILATURA_PATH` なし）で測り直しました（ネットワークを使いません。下の「rs-trafilatura を使う経路」と同じ方法です）。base の列は、取得したときの数字のままです。
- **事実と問いの選び方**（取得の前に決めて、結果を見て変えていません）:
  1. 記事の本文（`脚注`・`注釈`・`出典`・`参考文献`・`関連項目`・`外部リンク`の見出しより前）の、後ろ 3 分の 1 を使います。ただし、branch が見える先頭 200,000 字の内だけです。
  2. その範囲の真ん中に近い、文章の段落（箇条書き・表ではない）から、固有名や数を含む文を 1 つ選びます。
  3. 文の中の語句を、決め手の語にします。決め手の語は、記事の中に 1 か所しか無く（リンクの記法・空白・`\`・`*` を除いた文字で数えて 1 回）、検索語に含まれません。
  4. 検索語は、決め手の語を含まない、3〜7 語の語の並びです。
  - 事実と問いは、本文の URL で日本語などの字をパーセントエンコードして書いていた形の Markdown（直す前の branch）で選びました。次の字数と位置は、そのときの Markdown の数字です。結果の表の位置と「気づいたこと」の表は、直したあとの Markdown で測り直しています。
  - 事実は、記事を読んで人手で選びました（盲検ではありません）。10 件のうち 8 件は、全文の 2/3 より後ろにあります。残り 2 件は、全文の 2/3 より後ろに使える範囲が無かったので、範囲を替えました。
    - 第二次世界大戦（全文 833,902 字）は、2/3（555,935 字）より後ろが全部 200,000 字の外なので、先頭 200,000 字の後ろ 3 分の 1（133,333〜200,000 字）にしました。
    - 富士山（全文 162,575 字）は、2/3（108,383 字）より後ろが、画像のギャラリー（107,512〜112,843 字）と、脚注・出典・参考文献・関連項目・外部リンクだけで、本文の文章が無いので、本文（112,843 字で終わる）の後ろ 3 分の 1 にしました。
- **判定**（base と branch に同じものを使います）:
  - **答えの節を選んだ**: ハイライトのどれかに、決め手の語が入っている。リンクの記法（`[文字](URL "title")` を文字だけに、画像は除く）・空白・`\`・`*` を除いた文字で照合します。決め手の語は記事の中に 1 か所しか無いので、入っていれば答えの場所から選ばれたことになります。
  - **参考（節の見出し）**: ハイライトの見出し（`## a > b > c` の c）が、答えのある節の見出しと同じか。見出しの無い記事（日本の歴史）は数えません。
  - **言語の一覧が入った**: ハイライトに、日本語以外の Wikipedia（`https://xx.wikipedia.org/`）へのリンクが 3 つ以上ある。
  - **リンクだけの段落が入った**: ハイライトの中に、2 行以上で `isNavBlock` が真の段落がある（branch の `isNavBlock` を両方に使いました）。
  - **決めた時期**: 主な指標（決め手の語が入っているか）と、事実・検索語は、走らせる前に `facts.json` に固定しました。判定の関数と、副指標（見出しの一致・言語の一覧・`isNavBlock` の数）は、走らせたあとに書きました（走らせた結果の字数を見たあとです）。

パンくずの行から最後の節を取る処理（`breadcrumbMatch`。`> 📍 **階層**: A > B > C` の行から C を取ります。base の 294f1e0 にもあり、入ったのは 2026-09-11 です）は、もとは正規表現で、区切り（`>`・`›`・`\`）の多い行が文書の終わりにあると、組み合わせが指数で増えました。次の 3 つの形を測りました。

```ts
// 本文の字: 画像の記法 ![alt](URL "title") は alt ごと全部外し、リンク [文字](URL "title") は文字だけにする
// （入れ子の括弧・\ のエスケープ・title の中の括弧を読む。見出しの #、箇条書きの -、強調の * などの記号は残る）
function stripTargets(s: string): string {
  const n = s.length;
  const matchBracket = (start: number): number => { // '[' に対応する ']' の位置（無ければ -1）
    let depth = 0;
    for (let j = start; j < n; j++) {
      const c = s[j];
      if (c === '\\') { j++; continue; }
      if (c === '[') depth++;
      else if (c === ']' && --depth === 0) return j;
    }
    return -1;
  };
  const matchParen = (start: number): number => { // '(' に対応する ')' の次の位置（無ければ -1）
    let depth = 0, inTitle = false;
    for (let j = start; j < n; j++) {
      const c = s[j];
      if (c === '\\') { j++; continue; }
      if (inTitle) { if (c === '"') inTitle = false; continue; }
      if (c === '"' && s[j - 1] === ' ') { inTitle = true; continue; }
      if (c === '(') depth++;
      else if (c === ')' && --depth === 0) return j + 1;
    }
    return -1;
  };
  let out = '';
  for (let i = 0; i < n;) {
    const img = s[i] === '!' && s[i + 1] === '[';
    if (img || s[i] === '[') {
      const open = img ? i + 1 : i;
      const close = matchBracket(open);
      if (close >= 0 && s[close + 1] === '(') {
        const end = matchParen(close + 1);
        if (end >= 0) {
          if (!img) out += stripTargets(s.slice(open + 1, close));
          i = end;
          continue;
        }
      }
    }
    out += s[i++];
  }
  return out;
}
```

### 限界

- **取るたびに結果が変わります。** 4 回目と同じ問い・検索語でも、返るページは同じではありません（両方にあるページは 7 割弱）。1 回だけの測定なので、ページ数の差（+1 ページ）や率の差（+3 ポイント）の向きは、結論に使えません。
- **4 回目の値は、取得をやり直したものではありません。** 4 回目は、保存した検索結果に、そのときの版のハイライトの規則を当てた値です。今回は、検索・取得・本文の取り出し・ハイライトの作成まで、ブランチのコードを通した値です。取れた本文が違うページもあります（上の質問サイトのページ）。
- **rs-trafilatura を使う経路は測っていません。** 本番の経路では、本文の取り出しが変わります。4 回目に使ったかどうかは、記録が残っていません。
- **答えの有無は、文字列の一致です。** 題名・スニペットなどの本文以外の欄にだけ答えがあるページも数えます（今回は 90 ページのうち 7 ページ。4 回目は 92 ページのうち 7 ページ）。参考に、本文に答えのあるページだけで数えた値も上の表に載せました。本文に答えがあるのに、`evidence` の本文にもハイライトにも無く、題名などの欄で残ったと数えたページが 3 ページあります（QA20CAPR-1445 の 5 番目、QA20QBIK-1197 の 1 番目と 5 番目）。QA20QBIK-1197 の 5 番目は、答えが本文の無い見出しの行にしかなく、節にならないので、どのハイライトにも入りません（base も同じです）。

- **リンクだけの段落を外す処理が答えの段落を外す危険**（上の「限界」の JQaRA の項で、測れないとしたもの）は、今回の 40 問の本文では次のとおりです。
  - 本文に答えのある 83 ページのうち 6 ページで、答えが「リンクだけの段落」と判定される段落にあります（2 行以上の塊を空行で分けて `isNavBlock` をかけた概算）。6 ページとも、答えは外されない段落にも出てくるので、外した後の節に答えが残ります。

### 再実行

Bun は 1.4.2 を使います。`HTTPS_PROXY` と `HTTP_PROXY` を外し、`SORA_DB_PATH` に使い捨ての DB、`CHROME_PATH` に Chromium を渡して、`<branch>` の直下で走らせます。`test.jsonl` は `scripts/eval-jqara.ts` の先頭の手順で作ります。`test-answers.json` は、JQaRA test の `answers` 列を、q_id ごとに `[{ "q_id": …, "answers": […] }]` にしたものです。

```ts
// live40.ts: JQaRA test の 40 問を、実際の integratedSearch に 1 回ずつ渡し、full に答えがあった問い・ページのうち evidence にも残る数を数える。
// 使い方: bun live40.ts <test.jsonl と test-answers.json のある場所> <出力先>（<branch> の直下で）
import { mkdirSync, readFileSync, writeFileSync } from 'node:fs';
const root = '<branch>'; // 作業ツリーの絶対パス
const { integratedSearch } = await import(`${root}/src/scraper.ts`);
const { serializeIntegratedSearchMcpResponse } = await import(`${root}/src/integrated_search_host_response.ts`);
const { getSecurityMetrics } = await import(`${root}/src/security/metrics.ts`);
const { STOPWORDS_LIST } = await import(`${root}/src/retrieval/lexicons/stopwords.ts`);
const [dataDir, outDir] = process.argv.slice(2);
mkdirSync(outDir, { recursive: true });

// 問い: q_id の順に 41 問おき、2 回目から 10 問ずらした先頭 40 問。答えは test-answers.json から q_id で引く
const answerOf = new Map<string, string[]>(JSON.parse(readFileSync(`${dataDir}/test-answers.json`, 'utf8')).map((a: any) => [a.q_id, a.answers]));
const byQ = new Map<string, any>();
for (const l of readFileSync(`${dataDir}/test.jsonl`, 'utf8').split('\n')) if (l) { const r = JSON.parse(l); if (!byQ.has(r.q_id)) byQ.set(r.q_id, r); }
const qs = [...byQ.values()].sort((a, b) => a.q_id.localeCompare(b.q_id)).filter((_, i) => i % 41 === 10).slice(0, 40);

// 検索語: 問い文の語のうち、漢字・カタカナ・英数字を含み、不要語でも数字だけでもないものを、出た順に最大 5 つ
const STOP = new Set((STOPWORDS_LIST as string[]).map((w) => w.toLowerCase()));
const seg = new Intl.Segmenter('ja', { granularity: 'word' });
const queryOf = (q: string) => [...new Set([...seg.segment(q.normalize('NFKC').toLowerCase())].filter((x) => x.isWordLike).map((x) => x.segment.trim())
  .filter((w) => w && !STOP.has(w) && /[一-鿿々ァ-ヺa-z0-9]/.test(w) && !/^[0-9.,]+$/.test(w)))].slice(0, 5).join(' ');

// 数え方: 値の中の文字列を NFKC で正規化して空白を除き、欄の間を U+0000 でつないだ中に、答え（同じ正規化）が入っているか
const norm = (s: string) => s.normalize('NFKC').replace(/\s+/g, '');
const strs = (v: unknown, out: string[] = []): string[] => {
  if (typeof v === 'string') out.push(v);
  else if (Array.isArray(v)) for (const x of v) strs(x, out);
  else if (v && typeof v === 'object') for (const x of Object.values(v)) strs(x, out);
  return out;
};
const has = (v: unknown, ans: string[]) => { const t = strs(v).map(norm).join('\u0000'); return ans.some((a) => a && t.includes(norm(a))); };

// Yahoo の 429 が 1 回でも数えられたら、その場で止める（取り直さない）
setInterval(() => { if ((getSecurityMetrics().yahoo_429_total ?? 0) > 0) { console.error('429: 止めます'); process.exit(3); } }, 100);

let pw = 0, pk = 0, qw = 0, qk = 0, tokenFull = 0, tokenEvidence = 0;
const tok = (s: string) => { const c = (s.match(/[　-鿿＀-￯]/g) || []).length; return Math.ceil(c * 0.77 + (s.length - c) * 0.25); };
for (const q of qs) {
  const answers = answerOf.get(q.q_id) ?? [];
  const res = await integratedSearch({ query: queryOf(q.question), includeRealtime: false, noCache: true });
  writeFileSync(`${outDir}/${q.q_id}.result.json`, JSON.stringify(res));
  const fullText = serializeIntegratedSearchMcpResponse(res, { responseMode: 'full' });
  const evidenceText = serializeIntegratedSearchMcpResponse(res, { responseMode: 'evidence' });
  const F = JSON.parse(fullText), E = JSON.parse(evidenceText);
  const byUrl = new Map<string, any>(E.results.map((e: any) => [e.url || e.link || '', e]));
  F.results.forEach((it: any, i: number) => {
    const e = E.results[i];
    const ref = typeof e.highlightsSameAs === 'string' ? byUrl.get(e.highlightsSameAs) : undefined; // 同じハイライトの結果は、指す先で見る
    if (has(it, answers)) { pw++; if (has(ref ? { ...e, highlights: ref.highlights } : e, answers)) pk++; }
  });
  if (has(F, answers)) { qw++; if (has(E, answers)) qk++; }
  tokenFull += tok(fullText); tokenEvidence += tok(evidenceText);
  console.error(q.q_id, JSON.stringify({ pages: `${pk}/${pw}`, questions: `${qk}/${qw}` }));
  await new Promise((r) => setTimeout(r, 15_000));
}
console.log(JSON.stringify({ pages: `${pk}/${pw}`, questions: `${qk}/${qw}`, tokenFull, tokenEvidence }));
process.exit(0);
```
