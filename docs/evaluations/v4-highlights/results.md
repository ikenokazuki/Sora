# ハイライトの評価（全文から選ぶ・リンクだけの段落を外す）

2026-11-04。ハイライト（検索語に合う節の選び方、`extractQueryHighlightDetails`）に入れた、次の 2 つの直しを測りました。設計は `docs/superpowers/specs/2026-11-04-v4-extraction-and-params-design.md` の 4 です。

1. **全文から選ぶ**: `maxChars`（既定 30,000 字）で切る前の本文から選びます。元にする本文の上限は 200,000 字です（`HIGHLIGHT_SOURCE_MAX_CHARS`）。それまでは、切った後の 30,000 字から選んでいたので、それより後ろにある答えを選べませんでした。
2. **リンクだけの段落を外す**: 節の中の、短いラベルのリンクだけでできた段落（2 行以上。Wikipedia の言語の一覧など）を、ハイライトの候補にも書き出しにもしません（`parseMarkdownSections` の `dropNavParagraphs`）。

比べたのは、基準（base）が main の 294f1e0、直したブランチ（branch）が `fix/v4-extraction-and-params` の 23822f5 です。実行は、どちらも CI と同じ Bun 1.4.2 です（Bun の版で `Intl.Segmenter` の語の切り方が違います）。

## 結果のまとめ

- **JQaRA（ふつうの本文で段落の選び方が変わらないか）**: dev 1,737 問・test 1,667 問のすべてで、選ぶハイライトも点数も base と branch で同じでした（違う問いは 0 問）。選んだ段落の正解の割合は変わりません。ただし、JQaRA の候補はリンクの記法をほとんど含まず（`](` を含む候補は dev 86,850 件中 16、test 166,700 件中 30）、リンクだけの段落を外す処理はほぼ働きません。同じになるのはデータの作りからほぼ決まっていて、リンクの多い本文の段落を誤って外す危険は、このテストでは測れません。
- **200,000 字の時間**: 日本語の 72 ページをつないだ 200,000 字で、ハイライトを選ぶ時間は中央値 13.0〜29.5 ms（3 回。基準は 200 ms 以下）でした。長い Wikipedia の記事 10 件の先頭 200,000 字では、中央値 15.9〜77.7 ms です。基準を下回ったので、上限は 200,000 字のままです。
- **長いページ 10 件**: Wikipedia の長い記事で、先頭の 30,000 字より後ろにある事実を問うと、答えがハイライトに入ったのは base が 0 件、branch が 9 件でした。ハイライトに言語の一覧が入ったページは、base が 4 件、branch が 0 件です（rs-trafilatura の無い経路の数字。本番の経路（rs-trafilatura あり）を保存した HTML で調べると、答えの有無は同じで、言語の一覧が入るのは base が 1 件、branch が 0 件です）。
- **気づいたこと**（「気づいたこと」の節）:
  - Wikipedia の長い記事は、branch の Markdown が 200,000 字を超えます（10 件中 7 件。第二次世界大戦は 833,902 字）。上限より後ろの答えは選べません。
  - branch の Markdown は base より 1.17〜1.37 倍長く（日本語の URL をパーセントエンコードするため）、同じ 30,000 字に入る本文の字は、base の 52〜100% になります。
  - 作った入力（`](` を何万回も含む 1 行）では、リンクだけの段落の判定が二乗の時間がかかり、200,000 字で 6.9 秒でした（30,000 字では 0.2 秒）。
  - 1 件（富士山）は、答えの節は選んだものの、書き出す窓が答えの 1 文手前で終わりました。

## 評価の方法

### 共通

- **版**: base は main の 294f1e0（v3.0.0 のあと）、branch は `fix/v4-extraction-and-params` の 23822f5（base から 24 コミット先）です。
- **実行**: `HTTPS_PROXY` と `HTTP_PROXY` を外して、それぞれの作業ツリーの直下で走らせました。計算機は AMD EPYC-Milan（6 コア）、Linux 6.12 です。
- **文字数**: 文字数と位置は、JavaScript の `String.length`（UTF-16 の単位）で数えています。

### 1. JQaRA

- **評価集**: JQaRA（https://huggingface.co/datasets/hotchpotch/JQaRA、CC BY-SA 4.0）。質問は JAQKET、文章は Wikipedia です。dev は 1,737 問 × 候補 50 件、test は 1,667 問 × 候補 100 件です。parquet から JSONL への変換の手順は `scripts/eval-jqara.ts` の先頭にあります。評価集の説明は `docs/evaluations/term-matching/results.md` にあります。
- **実行**: `bun scripts/eval-jqara.ts --data <JSONL の場所> --split <dev か test> --select`。`--select` は、問いごとの候補を 1 つのページの段落（`## 見出し` と本文）とみなして `extractQueryHighlightDetails` を呼び、選んだ段落のうち正解の割合（precision）と、1 つでも正解を選べた問いの割合（hit）を出します。
- **同じかどうかの確かめ**: 出力の文字列を `cmp` で比べたほか、1 つのプロセスに base と branch の両方のモジュールを読み込み、全問で `highlights` と点数が文字まで同じかを数えました。さらに、問いごとの文書を `parseMarkdownSections` に通し、base と branch で節の本文が違う問いを数えました（リンクだけの段落を外す処理が働いたかを見るためです）。
- **何を確かめるか**: 「リンクだけの段落を外す処理が、ふつうの本文のハイライトを変えない」ことです。ただし、このテストの検出力は低いです。
  - JQaRA の候補は Wikipedia の本文の段落で、1 件ずつは短く（最大 403 字）、リンクの記法を含むものがほとんどありません（`](` を含む候補は dev 86,850 件中 16、test 166,700 件中 30）。リンクだけの段落を外す処理が節を変えた問いは、dev・test とも 0 問でした。同じ出力になるのは、データの作りからほぼ決まっています。
  - そのため、リンクの多い本文の段落を誤って外す危険は、このテストでは測れません。
  - 「30,000 字を超える本文もありません」は、候補 1 件ずつなら正しいです。問いごとにつないだ文書（`eval-jqara.ts` が `extractQueryHighlightDetails` に渡すもの）では、test の 64 / 1,667 件が 30,000 字を超えます（最大 35,545 字。dev は最大 17,630 字）。ただし、`eval-jqara.ts` は `extractQueryHighlightDetails` を直接呼び、全文の上限（`finalizeScrapeResult` の側）を通らないので、結果に影響しません。全文を渡す側の変更は、このテストでは通りません。
- **判断と回数**: dev で確かめ、test は、精度の指標を base と branch で 1 回ずつ測りました。ほかに、同じ出力かの確かめ（精度の指標は出さない）を、dev・test の全問で 1 回ずつ走らせました。

### 2. 全文の上限（200,000 字）の時間

- **200,000 字の文書**: 日本語の 72 ページ（`docs/evaluations/main-content/results.md` の日本語のページ。HTML のある 38 + 34 ページ）を `convertHtmlToMarkdown(html, url, 10_000_000, false, true)` で Markdown にしてつなぎ、先頭の 200,000 字を取りました。
- **測り方**: 3 つの検索語（`開場時間 チケット`・`収容人数 球場`・`release date version`）で、同じ文書に `extractQueryHighlightDetails` を 10 回かけ、中央値（小さい順の 6 番目）と最大を出しました。プロセスを替えて 3 回測りました。
- **基準**: 中央値 200 ms 以下。超えたら `HIGHLIGHT_SOURCE_MAX_CHARS` を 100,000 にして測り直します。
- **あわせて測ったもの**:
  - 同じ文書を 30,000 字で切った場合（今の動き）と、base のコードに 200,000 字を渡した場合（リンクだけの段落を外す処理の費用を分けるため）。
  - 実際の長い記事: 下の 3 で取得した 10 件の Markdown の先頭 200,000 字に、それぞれの検索語をかけた時間。
  - 作った最悪の入力: `[` で始まり、`](` を `n` 回並べ、`x)y)` で終わる 1 行（`[` + `](` × n + `x)y)`）を、`[a](b)` の行のすぐ後ろに置いた文書（空行を挟まないので、2 行の 1 つの塊になる）。リンクだけの段落の判定（`isNavBlock` の `BRACKET_LINK_LINE`）が、この形で二乗の時間がかかる、と先に指摘されていたので、その大きさを測りました。実際のページでは見つかっていません。

### 3. 長いページで、後ろのほうの答えが選ばれるか

- **ページ**: 日本語版 Wikipedia の長い記事 10 件（日本の歴史・東京都・第二次世界大戦・江戸時代・新幹線・宝塚歌劇団・富士山・日本の鉄道・大阪府・明治維新）。
- **取得**: base と branch のそれぞれの `src/scraper.ts` から `scrapeUrl` を import し、`{ url, query, noCache: true, mode: 'fast' }` だけを渡して 1 ページ 1 回ずつ呼びました。ほかの引数は既定のままです。応答の `highlights` を判定に使います。
  - 取得は 1 ページあたり 4 回です（問いを作るために全文を読む 1 回・base・branch・補助実験用の HTML の保存）。ページの間は 2.5 秒以上あけました。
  - この環境では `RS_TRAFILATURA_PATH` を設定していないので、本文は全ページ Readability の経路で作られました（補助実験は下の「rs-trafilatura を使う経路」）。
- **事実と問いの選び方**（取得の前に決めて、結果を見て変えていません）:
  1. 記事の本文（`脚注`・`注釈`・`出典`・`参考文献`・`関連項目`・`外部リンク`の見出しより前）の、後ろ 3 分の 1 を使います。ただし、branch が見える先頭 200,000 字の内だけです。
  2. その範囲の真ん中に近い、文章の段落（箇条書き・表ではない）から、固有名や数を含む文を 1 つ選びます。
  3. 文の中の語句を、決め手の語にします。決め手の語は、記事の中に 1 か所しか無く（リンクの記法・空白・`\`・`*` を除いた文字で数えて 1 回）、検索語に含まれません。
  4. 検索語は、決め手の語を含まない、3〜7 語の語の並びです。
  - 事実は、記事を読んで人手で選びました（盲検ではありません）。10 件のうち 8 件は、全文の 2/3 より後ろにあります。残り 2 件は、全文の 2/3 より後ろに使える範囲が無かったので、範囲を替えました。
    - 第二次世界大戦（全文 833,902 字）は、2/3（555,935 字）より後ろが全部 200,000 字の外なので、先頭 200,000 字の後ろ 3 分の 1（133,333〜200,000 字）にしました。
    - 富士山（全文 162,575 字）は、2/3（108,383 字）より後ろが、画像のギャラリー（107,512〜112,843 字）と、脚注・出典・参考文献・関連項目・外部リンクだけで、本文の文章が無いので、本文（112,843 字で終わる）の後ろ 3 分の 1 にしました。
- **判定**（base と branch に同じものを使います）:
  - **答えの節を選んだ**: ハイライトのどれかに、決め手の語が入っている。リンクの記法（`[文字](URL "title")` を文字だけに、画像は除く）・空白・`\`・`*` を除いた文字で照合します。決め手の語は記事の中に 1 か所しか無いので、入っていれば答えの場所から選ばれたことになります。
  - **参考（節の見出し）**: ハイライトの見出し（`## a > b > c` の c）が、答えのある節の見出しと同じか。見出しの無い記事（日本の歴史）は数えません。
  - **言語の一覧が入った**: ハイライトに、日本語以外の Wikipedia（`https://xx.wikipedia.org/`）へのリンクが 3 つ以上ある。
  - **リンクだけの段落が入った**: ハイライトの中に、2 行以上で `isNavBlock` が真の段落がある（branch の `isNavBlock` を両方に使いました）。
  - **決めた時期**: 主な指標（決め手の語が入っているか）と、事実・検索語は、走らせる前に `facts.json` に固定しました。判定の関数と、副指標（見出しの一致・言語の一覧・`isNavBlock` の数）は、走らせたあとに書きました（走らせた結果の字数を見たあとです）。

## 結果

### 1. JQaRA

base と branch の出力は、dev・test とも 1 文字も違いませんでした。全問で `highlights` と点数が同じです（違う問い: dev 0 問、test 0 問）。

| | 問い | 1 問あたりの選んだ数 | 選んだ段落の正解の割合 | 1 つでも正解を選べた問い |
|---|---|---|---|---|
| dev（base = branch） | 1,737 | 5.67 | 0.3675 | 0.9390 |
| dev、同じ数を `scorePassage` の上位から | 1,737 | 5.67 | 0.3966 | 0.9424 |
| test（base = branch） | 1,667 | 6.25 | 0.3283 | 0.8998 |
| test、同じ数を `scorePassage` の上位から | 1,667 | 6.25 | 0.3565 | 0.8950 |

`scorePassage`（k1=0.9、b=0.4）の順位の指標も同じです（dev: nDCG@10 0.7445、MRR@10 0.8272。test: 0.4568、0.6981）。

上の「1 問あたりの選んだ数」「正解の割合」「1 つでも正解を選べた問い」は、`docs/evaluations/term-matching/results.md` に書いた、同じ関数・同じ dev の記録（選んだ数 2.90・正解の割合 0.531・1 つでも正解 0.881）と違います。その記録は 2026-10-28 のもので、このとき、件数を指定しない呼び出しは上位 3 件を選んでいました。2026-10-29 に、件数を指定しないときは字数の目安まで足す選び方が入り（200272f・019add2）、既定の選ぶ数が増えています。今の main のコード（base）で、`maxHighlights: 3` を渡して同じ計算をすると、選んだ数 2.90（記録と同じ）・正解の割合 0.541・1 つでも正解 0.887 になります。残る 0.01 ほどの差の原因は特定していません。

### 2. 時間

200,000 字の文書（日本語の 72 ページをつないだもの）。中央値と最大（ms）は、10 回の値です。branch で 3 回測りました。

| 検索語 | 中央値（3 回） | 最大（3 回） |
|---|---|---|
| 開場時間 チケット | 29.5 / 28.2 / 27.8 | 66.3 / 64.6 / 66.1 |
| 収容人数 球場 | 16.2 / 14.2 / 13.8 | 19.4 / 16.4 / 17.2 |
| release date version | 14.6 / 13.0 / 14.9 | 16.0 / 15.9 / 21.5 |

基準の 200 ms の 1/5 以下です。基準を下回ったので、`HIGHLIGHT_SOURCE_MAX_CHARS` は 200,000 字のままです。最初の検索語の最大が中央値の倍ほどあるのは、プロセスの最初の 1 回が暖機の分だけ遅いためと考えられます。

同じ文書で、版と文字数を変えたときの中央値 / 最大（ms）:

| 検索語 | base、30,000 字 | base、200,000 字 | branch、30,000 字 | branch、200,000 字 |
|---|---|---|---|---|
| 開場時間 チケット | 6.6 / 32.0 | 28.2 / 64.0 | 6.0 / 34.1 | 34.1 / 71.3 |
| 収容人数 球場 | 1.5 / 2.6 | 12.3 / 14.0 | 2.1 / 3.3 | 15.2 / 17.7 |
| release date version | 2.8 / 6.7 | 14.0 / 16.1 | 2.7 / 5.1 | 12.7 / 14.8 |

文字数を 30,000 字から 200,000 字に増やした分が時間のほとんどで、リンクだけの段落を外す処理の費用は、この文書では小さいです（base の 200,000 字と branch の 200,000 字の差は、中央値で最大 6 ms）。

実際の長い記事（10 件）。それぞれの記事の先頭 200,000 字（日本の鉄道 65,023 字・富士山 162,575 字・江戸時代 197,672 字は全文）に、下の 3 の検索語をかけた時間です。

| 版と文字数 | 中央値の範囲（ms） | 中央値の中央値（ms） | 最大の最大（ms） |
|---|---|---|---|
| base、30,000 字（今の動き） | 4.4〜13.2 | 9.2 | 31.3 |
| base、200,000 字（リンクだけの段落を外す処理なし） | 17.0〜81.6 | 53.8 | 103.0 |
| branch、200,000 字 | 15.9〜77.7 | 52.6 | 107.5 |

一番遅かったのは明治維新（branch の中央値 77.7 ms）と第二次世界大戦（69.4 ms、最大 107.5 ms）です。

`scrapeUrl` 全体の所要時間は、2 通りで見ました。これは、このブランチ全体（本文の取り出し・URL の絶対化・ハイライトなど）の差で、ハイライトだけの差ではありません。

- **手元のサーバー**（保存した HTML を返し、ネットワークを使わない。query 付き、5 回の中央値）: branch は base より、東京都（HTML 約 1.1 MB）で 1,351 → 1,543 ms（+14%、+0.19 秒）、第二次世界大戦（約 3.3 MB）で 4,164 → 4,695 ms（+13%、+0.53 秒）でした。
- **実ネットワーク**: 上の「3. 長いページ」の取得（10 ページ、いつも base → branch の順に 1 回ずつ）では、branch が全ページで遅く（+0.98〜+2.58 秒、中央値 +1.68 秒）、いつも base が先でした。順番を入れ替えて取り直す（同じ `scrapeUrl` の呼び方、検索語は「鉄道 開業」、`noCache: true`・`mode: 'fast'`、取得の間 3 秒）と、次のようになり、最初の 1.0〜2.6 秒の差は再現しませんでした。

  | ページ | 1 回目 | 2 回目 | 3 回目 | 4 回目 |
  |---|---|---|---|---|
  | 江戸時代 | base 2,904 ms | branch 3,209 ms | branch 3,070 ms | base 3,682 ms |
  | 東京都 | branch 3,245 ms | base 2,817 ms | base 2,776 ms | branch 3,145 ms |

  江戸時代は決まった差がなく、東京都は branch が約 0.4 秒長いです（手元のサーバーでの +14% と合います）。最初の差が何によるか（順番の影響か、そのときのネットワークの状態か）は調べていません。

実際の費用は、手元のサーバーでの +13〜14%（東京都で +0.19 秒、第二次世界大戦で +0.53 秒。実ネットワークの取り直しでは東京都で約 +0.4 秒）と見ています。

作った最悪の入力（`[` + `](` × n + `x)y)` の 1 行を含む文書）に `extractQueryHighlightDetails` をかけた時間（ms、1 回）:

| 1 行の長さ | base | branch |
|---|---|---|
| 30,000 字 | 31 | 215 |
| 60,000 字 | 38 | 740 |
| 100,000 字 | 44 | 1,795 |
| 200,000 字 | 65 | 6,896 |

branch は長さの二乗で増えます。上限が 200,000 字だと、この形の 1 行を含むページ 1 つが、1 回の呼び出しの間 7 秒ほど処理を止める計算です（手書きの Markdown での測定からの推定です。HTML からこの形の 1 行を作れるかは確かめていません）。

## 限界

- **盲検ではない。** 事実と検索語は、記事を読んで人手で選びました。主な指標（決め手の語）と、事実・検索語は、走らせる前に固定し、結果を見て変えていませんが、選び方に偏りがあるかもしれません。副指標（見出しの一致・言語の一覧・`isNavBlock` の数）は、走らせたあとに決めました。10 件は少ない数です。
- **base の 0 件は作り方から決まる。** 事実がすべて 30,000 字の外にあるためです。
- **30,000 字の内にある答えを見ていない。** 全文から選ぶことで、先頭の答えが後ろの節に押し出されないかは、この評価では見ていません（検索の評価で見ます）。
- **JQaRA では、全文の上限の変更が通らず、リンクだけの段落を外す処理もほぼ働かない。** 同じ出力になるのは、データの作りからほぼ決まっています。確かめられたのは、リンクの少ないふつうの本文を変えないことまでで、リンクの多い本文の段落を誤って外す危険は、このテストでは測れません。
- **事実の位置が、全文の後ろ 3 分の 1 でない 2 件がある。** 第二次世界大戦（20.3%）と富士山（57.3%）。理由は「評価の方法」の 3 のとおりです（第二次世界大戦の本物の後ろ 3 分の 1 は、上限の外。富士山の 2/3 より後ろには、画像のギャラリーと脚注類だけがあり、本文の文章が無い）。
- **主な取得は、rs-trafilatura の無い環境（Readability の経路）。** 本番で 8 ページが通る rs-trafilatura の経路は、保存した HTML での補助実験で確かめました。答えがハイライトに入るかは同じですが、言語の一覧が入るのは、base が 4 ページから 1 ページ（第二次世界大戦）に減り、branch は 0 ページのままです。
- **ページは変わる。** Wikipedia の記事は編集されるので、再実行すると位置・字数・決め手の語が変わることがあります（この評価は 2026-11-04 の版です）。

```ts
import { readFileSync, readdirSync, writeFileSync } from 'node:fs';
import { convertHtmlToMarkdown } from '<branch>/src/html_parser.ts';
const parts: string[] = [];
let total = 0;
for (const set of ['ja-pages', 'ja-news']) for (const f of readdirSync(`${process.argv[2]}/${set}`).filter((x) => x.endsWith('.json')).sort()) {
  const d = JSON.parse(readFileSync(`${process.argv[2]}/${set}/${f}`, 'utf8'));
  if (typeof d.html !== 'string' || !d.html || total >= 200_000) continue;
  const md = convertHtmlToMarkdown(d.html, d.url, 10_000_000, false, true).markdown;
  parts.push(md);
  total += md.length;
}
writeFileSync(process.argv[3], parts.join('\n\n').slice(0, 200_000));
```

**4. rs-trafilatura を使う経路（補助）**: 10 ページの HTML をファイルに保存し（`fetch` で 1 ページ 1 回）、`Bun.serve` で返します（`ALLOW_LOCAL_FETCH=true`、`hostname: '127.0.0.1'`）。`RS_TRAFILATURA_PATH` にコマンドのパスを渡し、上の 3 と同じ呼び出しを `http://127.0.0.1:<port>/…` に対して行います。`RS_TRAFILATURA_PATH` を外して同じことをすると、rs-trafilatura が無い経路を、ネットワークなしで再現できます。ページの種類は、`rs-trafilatura --url <URL> --hybrid --markdown < page.html` の出力の `page_type` で見ます。

**5. 「気づいたこと」の表（本文の字）**: 保存した HTML を、作業ツリーごとの `convertHtmlToMarkdown(html, '<ページの本番の URL>', 2_000_000, false, true).markdown` に通して Markdown を作り（branch の結果は、上の 3 の「全文を読む」で保存した Markdown と、10 件とも全文が一致します）、次の関数で本文の字を数えます。

```ts
// 本文の字: 画像の記法 ![alt](URL "title") は alt ごと全部外し、リンク [文字](URL "title") は文字だけにする
// （入れ子の括弧・\ のエスケープ・title の中の括弧を読む。見出しの #、箇条書きの -、強調の * などの記号は残る）
function stripTargets(s: string): string {
  const n = s.length;
  const matchBracket = (start: number): number => { // '[' に対応する ']' の位置（無ければ -1）
    let depth = 0;
    for (let j = start; j < n; j++) {
      const c = s[j];
      if (c === '\\') { j++; continue; }
      if (c === '[') depth++;
      else if (c === ']' && --depth === 0) return j;
    }
    return -1;
  };
  const matchParen = (start: number): number => { // '(' に対応する ')' の次の位置（無ければ -1）
    let depth = 0, inTitle = false;
    for (let j = start; j < n; j++) {
      const c = s[j];
      if (c === '\\') { j++; continue; }
      if (inTitle) { if (c === '"') inTitle = false; continue; }
      if (c === '"' && s[j - 1] === ' ') { inTitle = true; continue; }
      if (c === '(') depth++;
      else if (c === ')' && --depth === 0) return j + 1;
    }
    return -1;
  };
  let out = '';
  for (let i = 0; i < n;) {
    const img = s[i] === '!' && s[i + 1] === '[';
    if (img || s[i] === '[') {
      const open = img ? i + 1 : i;
      const close = matchBracket(open);
      if (close >= 0 && s[close + 1] === '(') {
        const end = matchParen(close + 1);
        if (end >= 0) {
          if (!img) out += stripTargets(s.slice(open + 1, close));
          i = end;
          continue;
        }
      }
    }
    out += s[i++];
  }
  return out;
}
// 本文の字 = stripTargets(markdown).length、先頭 30,000 字の本文の字 = stripTargets(markdown.slice(0, 30000)).length
```
