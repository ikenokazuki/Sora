# 本文の取り出しの評価

2026-10-28。ページの本文を取り出す処理（`src/html_parser.ts` の `convertHtmlToMarkdown` → `selectMainContent`）の評価です。次の 2 つを直しました。

1. **一覧・まとめのページ**: Readability が一覧のカード 1 枚や横の宣伝枠だけを本文にしたとき、同じ形の項目が並ぶ入れ物に替えます（`largestRepeatedItemList`）。
2. **表で段組みした古いページ**: レイアウト用の表を「表の本文」とみなして、ページ全体に戻していました。この戻しをやめます（`isDataTable`、`BODY_FALLBACK_MAX_READ_CHARS`）。

## 評価の方法

- **WCXB**（Web Content Extraction Benchmark、arXiv 2605.21097、CC BY 4.0、https://github.com/Murrough-Foley/web-content-extraction-benchmark）
  - 2,008 ページ・7 種類（記事・掲示板・商品・まとめ・一覧・技術文書・サービス）で、英語が中心です。
  - dev 1,497 ページで調整し、test 511 ページで判断しました。
  - 指標は `evaluate.py` の語の F1 です。小文字にして `\w+` で語に切り、正解の本文と多重集合で比べます。
- **Bevendorff ら（SIGIR 2023）の評価集**（https://github.com/chatnoir-eu/web-content-extraction-benchmark、Apache-2.0）
  - CleanEval・CETD・Dragnet・L3S-GN1・Readability・Scrapinghub などの 8 つの評価集を合わせた 3,985 ページで、2007〜2017 年ごろの英語の記事が中心です。
  - WCXB とは別の作者のものです。調整には使わず、確かめるためだけに使いました。指標は WCXB と同じ語の F1 です。
- **日本語のページ**
  - Sora がよく読む種類の検索語 20 個（公式サイトのお知らせ・予定、チケット、商品、ブログ、官公庁）の上位 2 件ずつ、取得できた 38 ページです。
  - 正解は無いので、新旧の出力を並べ、旧の出力にあった行を新が落としていないかを見ました。
- **Sora の出力**: `convertHtmlToMarkdown(html, url, 10_000_000, false, true)` の Markdown から、記号と URL を外して採点しました。
- **比べた相手**:
  - 素の Readability（Sora と同じ `@mozilla/readability` と linkedom）
  - Trafilatura 2.0.0（既定の設定）
  - rs-trafilatura 0.2.2（下の節）
- **実行**:
  - WCXB: `bun scripts/eval-wcxb.ts --data <WCXB> --split test --out <予測の JSON>` のあと、`python3 -I <WCXB>/evaluate.py --split test --results <予測の JSON> --per-type`。
  - Bevendorff らの評価集: `bun scripts/eval-wcxb.ts --bevendorff <combined の場所>`。
  - rs-trafilatura の経路（下の節）は、`RS_TRAFILATURA_PATH` にコマンドのパスを渡して、同じスクリプトで測ります。
  - 採点では、Sora の出力の先頭のメタデータ（frontmatter）を外します（スクリプトは 2026-10-29 から外します）。
    - 「結果」の WCXB の表だけは、外さずに採点した値です。
    - Bevendorff らの表と、rs-trafilatura の節の値は、外して採点しました。

| まとめ | 117 | 36% | 19% |
| 商品 | 119 | 23% | 38% |

一覧では、次のものを選んでいました。Readability は本文を一つの要素として取るので、リンクの多い一覧より、近くの文章の段落を選びやすいためです。

- ニュースの一覧の代わりに、「Your content on Hospitality Net?」の枠
- 番組の一覧の代わりに、話題の一覧
- レシピの一覧の代わりに、カード 1 枚

- 特に L3S-GN1（古いニュース）は 0.644 対 0.913 で、精度は 0.58（素の Readability は 0.92）、再現率は 0.95 でした。

## 採用した方式

**一覧の直し**: 同じ形（タグと class）の子要素が 3 つ以上並ぶ入れ物のうち、項目の文字数の合計が最も多いものを探します。

- 16 字以下の項目はナビのラベルとして数えません。
- 項目の 6 割以上がナビのラベルなら、ナビの並びとして除きます。
- ナビ・ヘッダー・フッター・補助の領域の中は見ません。

Readability の本文が 600 字未満で、その並びに 300 字以上、かつ Readability の本文の 3 倍以上の文字があれば、並びの入れ物を本文にします。

| 案（WCXB の dev） | 全体 F1 |
|---|---|
| 変更前 | 0.7658 |
| 採用（Readability が 600 字未満のときだけ） | 0.7761 |
| 上限 1,500 字 | 0.7827 |
| 上限 3,000 字 | 0.7853 |
| 上限なし | 0.7856 |
| 3 倍を 2 倍にする | 0.7760 |
| Readability の本文を並びの前に残す | 0.7761 |

WCXB だけなら、上限なしが最も良い結果でした。ただし日本語のページでは、上限なしだと Yahoo!知恵袋の質問と回答（Readability が正しく取った約 740 字）が、横の関連の並びに替わりました。上限 600 字ではこれを防げるので、こちらを採りました。

**表の直し**: 次の 2 つを両方入れました。

- 救済の対象にする表を、見出しのある表（`th`・`thead`・`caption` があり、中に表を入れていないもの）に限ります。カレンダーや `role="grid"` は今までどおり対象です。
- `main`・`article` が無いページでページ全体に戻すのは、Readability の本文が 500 字未満のとき（予定表だけのページなど）に限ります。

Bevendorff らの評価集で比べると、片方だけでは次のとおりで、両方入れると 0.864 でした。

- 見出しのある表だけを対象にする: 0.861
- 短いときだけ戻す: 0.854

## rs-trafilatura の組み込み（2026-10-29）

上の比較を受けて、本文の取り出しに rs-trafilatura を組み込みました（`src/extractor/rs_trafilatura.ts`）。

- コマンドは `extract_stdin --url <URL> --hybrid --markdown` で呼びます。
  - `--markdown` を付けないと、本文の HTML からリンクの `href` が落ちます（rs-trafilatura の `include_links` が既定で無効のため）。
  - 落ちたままだと、日本語の 33 ページでリンクが 2,273 本から 0 本になりました。トークンが −36% に見えていたのは、ほとんどこのリンクの URL の分でした。
- rs-trafilatura が選んだ本文の HTML は、Sora の変換に通します。
  - rs-trafilatura 自身の Markdown は、一覧のページで HTML の字下げが残るためです。
  - トークンが 15〜42% 多くなっていました（≠ME のスケジュールで 15%、東京ドームのイベントで 42%）。
- 振り分けは次のとおりです。
  - **rs-trafilatura が「記事」と判定したページ**: Readability の本文を使います。Readability の本文が 200 字未満のときだけ、rs-trafilatura の本文に替えます。
  - **ほかの種類と判定したページ**（一覧・掲示板・商品・まとめ・技術文書・サービス）: rs-trafilatura の本文を使います。
- 組み込みの途中で、表の変換の不具合を 2 つ直しました。どちらも Readability の経路にも効きます。
  - **入れ子の表**: 外の表の行として、中の表の行とセルまで数えていました。
    - そのため、段組みに表を使うページで、同じ文が何度も出ていました（1 ページで最大 15 回）。
    - 表の行は、その表の行と、行の直下のセルだけにしました。Markdown の表と、構造化した表（`tables`）の両方です。
  - **空の行**: 1 行目にセルの無い表（`<tr></tr>`）で、例外になっていました。

## rs-trafilatura の経路の画像（v4.0.0）

2026-11-04。rs-trafilatura が返す本文の HTML には img が入らないため、v3.0.0 までは、この経路の本文から画像がすべて消えていました。v4.0.0 では、記事以外の種類のページで画像があるときだけ、画像の後ろに目印の 1 字（私用領域の文字）を置いた HTML で rs-trafilatura をもう一度走らせ、本文の文字が 1 回目と同じときだけ、目印を画像に戻します（`src/extractor/rs_trafilatura.ts`・`rs_images.ts`）。あわせて、本文の `a[href]` と `img[src]` を絶対 URL にし、`#` だけのリンクと `javascript:` のリンクを文字だけにしました（`absolutizeContentUrls`）。ここでは、本文の点が変わらないこと、日本語のページで本文の文字が変わらないこと、増える時間・メモリ・Markdown の長さを記録します。

### 測り方

- **版**: base は main の 294f1e0、branch は `fix/v4-extraction-and-params` の 8afe925（base から 23 コミット先）です。
- **実行**: 同じイメージ（Bun 1.4.4、本番と同じビルドの rs-trafilatura）に、base と branch を読み取り専用で入れ、ネットワークを切って走らせました。手順は「評価の方法」の「実行」のとおりです。Bevendorff らの評価集は、平均を 6 桁まで出して比べました。
- **採点**: `scripts/eval-wcxb.ts` の `toText` は、v4.0.0 から画像を alt ごと外します。URL の中の括弧（`filters:format(webp)` など）、alt の中の `\]`、data URI の画像の置き換え `[画像: alt]` まで外します。base にも branch の `toText` を重ねて測り直したので、表の base の値は、前の採点での値と少し違います（前の採点での値も並べました）。
- **測り直したわけ**: 最初の測定（7540c51）では、WCXB の dev が base 0.8400 に対して 0.8387 に下がりました。もとからある `cleanMarkdownTokens` の不具合と、採点の外し残しが、画像が戻ったことで rs-trafilatura の経路に多く出たためです。
  - alt の無い画像 `![](url)` が `!` だけになり、後ろにリンクが続くと画像の記法に見えて、リンクの文字が alt として外れていました。画像の URL に括弧があると、URL の残りが本文に出ていました。
  - どちらも直しました（空の画像を空のリンクより先に消す、URL の中の括弧を 1 段読む）。外したリンクの隣の文字がくっつく不具合（`1990` `1991` → `19901991`）も直しました。

各原因の中身です。

- **空白**: 並んだ `#`・`javascript:` のリンク（目次の開閉、星の評価など）を外すとき、隣の要素との間に空白を挟むので、base でくっついていた語（`Contentstoggle`、`stars2`）が分かれます。
- **`#` のリンクを外したこと自体、URL の絶対化**: 脚注の番号（`[3](#fn-sleep)`）が、前の語に続く文字として本文に残ります。リンクの文字に `]` を含むページ（docs.rs の `` [`#[tokio::main]`](attr.main.html) `` など）では、採点が相対 URL を外せず、URL の続きが語として数えられていたのが、絶対 URL になって外れます。
- **`cleanMarkdownTokens`**: `!` と URL の残りが消えます。alt の無い画像や空のリンクを消すと、前後に空白が無いときに語がくっつきます（`Cocktail![](url)Friendsgiving` は、base では `!` が残って `Cocktail!Friendsgiving`、branch では `CocktailFriendsgiving`）。Bevendorff らで差が最も大きい 2 ページ（−0.019 と +0.019）は、この原因です。
- **画像を戻したこと**: 採点は画像を空白に替えるので、画像の前後で語が分かれます。alt や title に閉じない括弧・2 段以上の括弧がある画像（LaTeX の `{O(n^{O(1)})}` など）は採点が外せず、alt の語が残ります（CETD の数式の多いブログで −0.019）。

### 時間とメモリ

最初の測定のあとに変わったのは `cleanMarkdownTokens`・`absolutizeContentUrls`・採点で、`src/extractor/` は変わっていないので、最初の測定の数字をそのまま使います。日本語の 72 ページと WCXB の dev の 4 ページおき 375 ページ、あわせて 447 ページで、`extractMainContentWithRs` の時間を測りました。

- **2 回目が増やす時間**:
  - 増えた時間が 5 ms を超えた 195 ページでは、中央値 76 ms、99% 点 508 ms です。
  - 同じプロセスの中で、2 回目の無い版と交互に 3 回ずつ測り、2 回目を走らせたページ（447 中 167。37%）だけを見ると、中央値 86 ms、90% 点 222 ms、99% 点 464 ms、最大 971 ms です。日本語の 33 ページでは中央値 61 ms、WCXB の 134 ページでは 90 ms でした。
  - 2 回目の無いページの差は、中央値 0 ms、最大 21 ms です。全ページでは、中央値 +1.2 ms、99% 点 +384 ms です。
- **メモリ**: 目印を入れた HTML での rs-trafilatura 自身の最大（`/proc` の VmHWM、434 ページ）は、中央値 11.4 MB、90% 点 15.8 MB、99% 点 25.0 MB、最大 44.8 MB です。
- 基準（増える時間の中央値 100 ms 以下、メモリの最大 60 MB 以下）を満たしています。設計書の値（中央値 80 ms、最大およそ 50 MB）とほぼ同じです。

## 既知の限界

- 古い英語のニュースでは、rs-trafilatura が記事を「一覧」と判定し、関連記事やコメントまで本文に入れることがあります（L3S-GN1 で −0.056）。
- 一覧のページで、投稿日時やブログ名などの付帯情報を落とすことがあります（アメブロ・はてなブログ）。
- rs-trafilatura の本文の画像は、記事以外の種類のページで、目印を入れた 2 回目の本文が 1 回目と同じときだけ戻します（v4.0.0。上の「rs-trafilatura の経路の画像（v4.0.0）」）。画像の一覧（`images`）は、今までどおりページ全体から取ります。
  - 記事と判定されたページは、Readability の本文を使い、その本文に画像が入っています。Readability の本文が 200 字未満で rs-trafilatura の本文に替わるときだけ、2 回目を走らせないので、画像は入りません。
  - 2 回目の本文が 1 回目と違うページ（日本語の 33 ページ中 1 ページ）と、`includeMedia: false` のときも、戻しません。
  - 戻した画像のうち alt の無いものは、Markdown では消えます（`cleanMarkdownTokens` の手順 1。前からそうでしたが、前は `!` が残っていました）。`formats: ["html"]` の本文には残ります。日本語では 750 枚中 448 枚（60%）でした。
- rs-trafilatura が使えないとき（コマンドが無い・失敗）の Readability の経路では、次の限界が残ります。
  - 一覧が何種類もあるページでは、いちばん文字数の多い並びが本文とは限りません（上のローチケ）。
  - ぴあアリーナの公演一覧では、公演名を取れません。
  - 掲示板では、Readability が「comment」などの名前の要素を消すため、投稿の本体を落とすことがあります。Readability の本文が 600 字以上だと、差し替えも起きません。
- WCXB と Bevendorff らの評価集は英語が中心です。日本語のページは、72 件を目で確かめただけです。
