# 楽天トラベル：内部データ経路の調査結果

調査日：2026-10-01（Asia/Tokyo）。基準コミット：`44336c4`。調査対象は匿名の国内宿泊検索。

**結論：日付・人数を指定した料金は、APIキーなしのHTTP GETで取得できた。ただし、今回の条件では製品機能を採用しない。** 検索結果HTMLに埋め込まれた `var ds = { ... }` が、施設ID・プランID・部屋ID・税込／税抜料金を持つ。施設名・所在地・プラン説明を同じ構造化経路から取得する方法と、任意の地名をHTTPだけで解決する方法は未確立。これらを画面HTMLから補う実装は、計画の自動採用範囲に含めない。

「取得不能」「匿名セッションが必須」「楽天に内部APIが存在しない」という結論ではない。確認した経路で、要求した公開契約を満たせるところまで到達していないという判断である。

## 判定

| ゲート | 結果 | 根拠 |
|---|---|---|
| G1：構造化経路の発見 | 通過。ただしHTML埋め込みJSON | 指定日の検索結果に `ds.conditions` と `ds.hotels` が存在。独立した空室JSON APIとは区別する |
| G2：HTTP再現と意味確認 | 未通過 | 3地域の匿名HTTP再現とブラウザ内状態の一致は確認。施設名・所在地の取得契約、汎用の場所解決、全ケースの画面料金照合は未達 |
| G3：Sora受入 | 未実施 | G2未通過のため、サービス・REST・MCP・OpenAPIへの追加は行っていない |

今回完了したのは、確認した経路についての調査と採否判断。ホテル検索機能の完成や本番導入は含まない。

## 再現した経路

1. 日付未指定の東京都検索画面で、チェックイン・チェックアウトを選択。
2. 日付指定検索が `GET /ds/vacant/searchVacant` に向くことを確認。
3. 東京都のみの指定では `/jparea/` へ302転送。転送先に指定日・人数が表示され、詳細地域の選択を求められる。
4. 画面が生成した東京駅リンクを開くと、日付付き施設・プラン一覧を200で取得。
5. 京都駅・草津温泉についても、公開画面が生成するリンクを取得。
6. 3地域のリンクを、Cookie・Authorization・独自ヘッダーなしの `fetch` で再送。

前回の仮説を訂正する。`/jparea/` への302だけではセッション不足を示さない。また、日付項目が生成されなかった一部プローブは、`rtl.util.date.separate()` にDOM要素を渡していた。同関数はjQueryオブジェクトを要求する。`YYYY/MM/DD` は正しい形式だった。

カレンダーは `.easepick-wrapper` のShadow DOMにある。日付の画面選択は成功したが、通常の検索ボタンを押す操作はこのChromium環境で `Input.dispatchMouseEvent` タイムアウトを起こした。検索経路の観測には、画面で選んだ日付を楽天自身の関数で分解した後、ネイティブフォーム送信を使用した。この違いを、通常の画面操作が完全に成功したものとして扱わない。

基準条件：2026-10-20〜2026-10-21、大人2人、1室。時刻・入力・HTTP状態・最小料金標本は [evidence.json](evidence.json) に保存。

|---|---:|---:|---:|---:|---|
| 東京駅・基準 | 200 | 430 ms | 5,611 ms | 22 | 一致 |
| 京都駅・基準 | 200 | 663 ms | 6,213 ms | 110 | 一致 |
| 草津温泉・基準 | 200 | 722 ms | 6,836 ms | 67 | 一致 |

HTTP6条件の中央値は553 ms。これは**観測済みURLを直接取得した時間**であり、場所解決・施設名取得・詳細取得を含む完成サービスの応答時間ではない。ブラウザ時間は新しい匿名ブラウザの起動と観測用3秒待機を含む。速度目標の達成とは判定しない。

各HTTP取得はCookieを引き継がず、ブラウザは新しい匿名BrowserContextを使った。価格・件数・順位は変動するため、固定の期待値にしない。通常版とモバイル版の全操作・全機能の同等性は未確認。

## 取得できたデータと残る依存

| 情報 | 観測できた場所 | 判断 |
|---|---|---|
| 有効な年月日・人数・部屋数 | `ds.conditions` | 送信条件との一致を確認可能 |
| 施設ID・プランID・部屋ID | `ds.hotels[hotelId].plans[planId].rooms[roomId]` | 同施設の別プラン・別部屋を保持可能 |
| 税込・税抜額 | `sumTotalChargeTaxInclusive` / `sumTotalChargeTaxExclusive` | 明示値を取得可能。表示単位や入湯税等を別途確認する必要がある |
| 検索件数・表示中施設 | `ds.totalResults` / `ds.displayedHotels` | 全件取得・全プラン網羅を保証するものではない |
| 施設名・所在地・プラン名・食事等 | 検索・詳細画面のHTML。詳細画面の `hotelBasicInfo` には施設名もある | 今回の `ds` には含まれない。要求契約全体をこのJSONだけでは生成できない |
| 場所候補 | `GetArea`、地域画面の駅・温泉候補JSONと生成リンク | 地域選択経路は確認。任意の日本語・英語の入力を少数HTTP要求で解決する手順は未確立 |

実画面では、東京駅・大人1人の施設 `141356`、プラン `5109708`、部屋 `sma` の表示合計34,000円と、埋め込みJSONの税込34,000円・税抜30,910円が一致した。3地域で最大3施設ずつの全表示項目を照合したとは主張しない。

連泊でも入力条件の保持は確認した。料金単位の詳細照合は未完了のため、「1泊の金額×泊数」で総額を生成する根拠にはしない。

## 見つかったJSON APIの用途

- `GetArea`：地域候補。楽天フロントエンドが送る公開アプリケーション識別子を観測した。利用者のAPIキーではなく、安定利用を保証する正式な契約でもない。
- `getHotelPics`：施設写真。空室・料金検索には使わない。
- `domestic-hotel-ad-search`：日付付き広告検索。保存した標本は応答のキーと文字数までで、`providers` の件数・内容は照合できない。一般の施設一覧の代替として採用できるとは確認していない。
- `/ds/getJson`：編集コンテンツのJSON:API。宿泊条件に一致する空室APIとは扱わない。
- クーポン・閲覧履歴API：補助表示。検索結果を生成する主経路とは扱わない。

大きなHTMLを保存対象から除外していた初期プローブは、約75万〜97万文字の検索結果内にある `ds` を見落としていた。統合したプローブは本文を読み、必要な状態だけを記録する。

## 成果物と確認方法

- [protocol.md](protocol.md)：観測した送信条件とデータ構造。
- [observed-cases.json](observed-cases.json)：公開画面から得た3地域のリンク。製品の地名辞書ではなく調査用ケース。
- [evidence.json](evidence.json)：秘密値・Cookie・HTML本文を含まない最小観測標本。
- [調査CLI](../../../scripts/probe-rakuten-travel.ts)：`capture`、`replay`、`verify`。通常の起動・CIから呼ばない。

```bash
# CHROME_PATH は稼働するChromiumのパスを指定する。
SORA_LIVE_TESTS=1 CHROME_PATH=/path/to/chromium \
  bun run scripts/probe-rakuten-travel.ts verify \
  --case tokyo --check-in 2026-10-20 --check-out 2026-10-21 \
  --adults 2 --out-dir /tmp/rakuten-verify-tokyo
```

`--case` は `tokyo | kyoto | kusatsu | all`。1実行24要求の上限があるため、ブラウザも使用する3地域の確認はケースごとの実行を推奨する。`replay` は標準HTTPのみ、`capture` は新しい匿名ブラウザのみ、`verify` は両方の記録を作る。`verify` という名前は採用条件の自動合格を意味せず、標本の比較は利用者が行う。日付省略時は実行日の日本時間を基準に14日以上先の火曜日を使う。

フラグ未設定では実通信しない。無効入力は通信前に拒否する。直接HTTP要求の開始間隔は3秒以上。ブラウザが起こす付随通信の順序は制御せず、別途記録する。画像・フォント・媒体と施設写真APIを省略するため、完全な画面描画の性能測定には使わない。403・429は記録して停止し、自動再試行しない。

探索用の一時スクリプト38本は、git対象外の `scratch/rakuten-travel-exploration/` に退避。以後の再現には統合CLIを使う。

統合CLIの単独TypeScript検査・バンドル作成、既存製品の型検査、7条件の保存標本の整合性・ローカル文書リンク確認が成功。最終CLIで東京駅を再取得して200・日付指定状態・要求12件・正常終了を確認した。固定429応答では1要求で停止し、失敗を記録した。調査CLIの回帰テスト4件は成功。アプリケーション全テストは1,089成功・10スキップ・4失敗。失敗したe-Govの4件は、変更前の `44336c4` の隔離作業ツリーでも同じHTTP 403で再現した。全テスト成功とは報告しない。ホテルサービスの契約テストとSora上での実環境受入試験は未実施。

既存の未解決失敗は `src/index.test.ts` の次の4件：

- `searchLaws and getLawData should interact with e-Gov Law API v2`
- `POST /gov/laws and POST /gov/law-text should handle REST requests`
- `searchLaws should handle article numbers like "政党助成法 第14条" without 404 error and fallback to law title`
- `searchLaws should return count: 0 for non-existent laws instead of throwing 404 GOV_ERROR`

レビュー後、保存項目を観測済み条件・数値ID・料金に限定した。ブラウザは公開画面自身の通信を受動観測し、同時1件・3秒間隔は明示的HTTP再送に適用するという裁定を計画へ明記した。サイト自身の並行XHRを抑制したという意味ではない。

## 未確認事項と次の判断

施設の完全なメタデータを持つ独立したAPI、全プランの取得、価格単位と税の全ケース照合、任意の地名・英語表記のHTTP解決、子供・複数室、5回連続の完成サービス性能、デプロイ環境とメモリ、長期安定性は未確認。

採用条件を変えずに進める場合、次に必要なのは施設メタデータと場所解決の構造化経路の実証。埋め込み料金JSONとHTMLの施設情報を組み合わせる方式は別の設計判断になる。現時点では、取得失敗を空室なしとして返す仮のホテル検索機能をSoraへ公開しない。
