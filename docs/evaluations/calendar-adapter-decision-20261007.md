# 汎用MCP内のTimeTree抽出アダプター採用（2026-10-07）

ユーザーは、汎用MCPツールにTimeTree専用API実装を含める意義を確認し、意義があれば専用設計を採用することを認めた。さらに、日本のWebをAIエージェントから利用するためのSelf-hosted MCP / REST統合サーバーとして評価するよう求めた。この位置付けでは、日本のWebサービスの情報を共通の入口から利用できる接続機能に価値がある。TimeTree補完は、予定情報への接続範囲を増やす機能として採用する。

## 判断

汎用性は、利用者が同じ`scrape`・`search_deep`の入力契約で様々なURLを扱えることで維持する。URLに応じた内部の抽出処理まで同一である必要はない。MCP仕様でもツールから外部APIを扱うことが想定されている。

## 日本のWebへの接続基盤としての意義

TimeTreeの公開カレンダーは、アーティストの出演予定だけでなく、店舗のセール・キャンペーンや自治体の地域イベントなどを発信する用途が公式に案内されている。予定情報をエージェントへ渡す接続処理は、Soraの検索・交通・天気などを使う行動計画の入力を増やす。今回の実装は公開ページ自身が読み込んだ予定の取得までであり、全月の巡回、非公開カレンダーの読み取り、予定の登録・変更は行わない。

MCPとRESTで同じ取得処理を使い、利用者やエージェントごとにTimeTreeのAPI解析を実装しなくてよい。既存コンテナ・認証・キャッシュ・タイムアウトの中で動作し、別サービス、追加DB、有料取得基盤、特定のLLMを必要としない。Self-hosted運用では、依存先と保守範囲をソース・テスト・フォールバックから確認できることにも価値がある。

今後の専用接続追加は、日本のWebにおける利用需要、汎用取得で欠ける重要情報、維持できる実装量と保守負担で判断する。今回の需要はユーザーの具体的なライブ予定検索で確認しているが、プロジェクト全体の利用頻度や各サイトの優先順位は未計測。

参考: [TimeTree公開カレンダーの用途](https://timetreeapp.com/intl/ja/public-calendar)。

## 取得経路の比較

- 通常DOM抽出では、TimeTreeの予定名17件を取得できるが、詳細画面にだけ存在する説明・出演時刻・会場を取得しない。
- 専用補完では、ページが既に受信した公開予定レスポンスから、同じ17件の説明・日時・会場・リンク・画像を保持できる。各予定を順にクリックして開く必要がない。
- 追加のAPIリクエスト、TimeTree用APIキー、外部の有料サービス、LLM呼び出しは不要。
- サイト固有処理は`src/timetree.ts`に分離する。対象ホスト・公開カレンダーURL・同じカレンダーのレスポンスパスだけで動作し、他ドメインへ適用しない。
- 予定データが存在しない・形式が不正の場合は、元の描画済みDOMをそのまま使う。本文救済・描画待機などの共通改善も維持する。

これはページ内で使われるAPIへの依存であり、公式の開発者向けAPIとして安定性を保証するものではない。API形式変更への追従は保守負担として残る。TimeTreeの利用頻度や、他の全サイトに専用処理を増やす費用対効果まで測定した判断ではない。

## 変更

削除したTimeTree補完処理と既存の5テストを復帰した。汎用のカレンダー予定ボタン保持テストは`example.com/calendar`のまま維持し、共通抽出がTimeTreeのURLに依存しないことを検証する。

scrapeとdeep検索のキャッシュ名前空間はv4へ変更し、汎用DOM版の予定名だけの結果を再利用しない。responseModeの既定値はfullのまま。専用MCPツール・新しい引数・設定項目は追加しない。
