# 応答の圧縮（search_deep の responseMode）の評価

2026-10-29。`search_deep`（MCP）と `POST /search`（REST）の `responseMode` の既定を `full` から `evidence` に変えるために測りました。

`evidence` は、ハイライトのある結果から本文の Markdown を省きます（`src/integrated_search_host_response.ts` の `projectIntegratedSearchEvidenceItem`）。ハイライトが本文の 0.75 倍以上の結果は、ハイライトの代わりに本文を返します（下の「ハイライトの選び方（件数を指定しないとき）」）。X の投稿、スニペットで代替した結果、取得に失敗した結果、`formats: ["markdown"]` を明示した呼び出しでは省きません。

## 共通の測り方

- **答えが残るか:** 返した文字列に、JQaRA の答えの文字列が入っているかで判定しました。比べる前に、両方を NFKC で正規化し、空白を除いています。
  - 数えるのは、`full` の出力に答えが入っているものだけです。
  - 答えは、JQaRA（https://huggingface.co/datasets/hotchpotch/JQaRA 、CC BY-SA 4.0）の `answers` 列から取りました。
- **トークン:** 文字数から見積もりました。日本語と全角の文字は 1 文字 0.77、その他の文字は 1 文字 0.25 として数えています。

## 実際の search_deep（40 問）

### 方法

1. JQaRA test から、q_id の順に 41 問おきに 40 問を選びました。
2. 問い文から語を 5 つ選んで検索語にしました（`tokenizeAndSelectTerms`）。
3. X の速報なし（`includeRealtime: false`）で、`integratedSearch` を 1 問 1 回ずつ呼びました。
4. 同じ結果を `full` と `evidence` で直列化し、答えが残るかとトークン数を比べました。

### 結果

| | 値 |
|---|---|
| 検索結果のあった問い | 22 問（残りの 18 問は 0 件） |
| `full` に答えがあった問い | 21 問 |
| そのうち `evidence` にも答えが残った問い | **21 問すべて** |
| トークン（40 問の合計） | 600,303 → 158,051（**−74%**） |
| トークン（1 問あたりの中央値） | 11,891 → 4,239 |
| 待ち時間 | p50 2.3 秒、p90 4.7 秒 |

答えが入っていたのは 21 問だけなので、この結果だけで「落とさない」とは言えません。下の 2 回目と、手元の評価と合わせて読んでください。

### 2 回目: 内容語の検索語（同じ 40 問）

1 回目の検索語は、`tokenizeAndSelectTerms` が「しょう」などの断片を選ぶことがあり、LLM が書く検索語に似ていませんでした。そこで 2 回目は、問い文の内容語を出た順に最大 5 つ並べた検索語で測りました（例: 「摂氏 マイナス 度 全て 原子」）。Yahoo に負担をかけないよう、問いの間を 10 秒あけています。

| | 値 |
|---|---|
| 検索結果のあった問い | 40 問すべて |
| `full` に答えがあった問い | 29 問 |
| そのうち `evidence` にも答えが残った問い | **27 問（93%）** |
| ページ単位（`full` の結果に答えがあったページ） | 94 ページ中 83 ページで残った（88%） |
| トークン（40 問の合計） | 851,725 → 226,812（**−73%**） |
| トークン（1 問あたりの中央値） | 20,983 → 4,511 |
| 待ち時間 | p50 2.8 秒、p90 4.3 秒 |

- **答えを落とした 2 問の状況:** どちらも、答えのあるページが 1 つだけで、そのページのハイライトに答えが入りませんでした。応答の `contextSufficiency` は `no_gap_detected` で、足りないことを示す手がかりはありませんでした。
- **答えを落としたページの順位:** 11 ページの順位は 1〜5 位に散っていました。
- **1 位の結果だけ本文を残す案:** 2 問のうち 1 問が戻りますが、トークンは 65% 増えます（全文と比べると −56%）。この案は採りませんでした。

1 回目と 2 回目を合わせると、答えがあった 50 問のうち 48 問（96%）で `evidence` にも答えが残りました。

## 手元の JQaRA（ページ単体）

### 方法

JQaRA の候補の段落からページを作り、ハイライト（`extractQueryHighlightDetails`）に答えが残るかを、ページごとに見ました。

- **ページの作り方**は 2 通りです。
  - long: 1 問の候補をすべて節にした長いページです（dev 50 節、test 100 節）。答えがあるのは 1〜数節だけです。
  - article: 候補を Wikipedia の題名ごとにまとめた、記事 1 本ぐらいのページです。答えを含むページだけを使いました。
- **検索語**も 2 通りです。
  - question: 問い文そのまま。
  - keywords: 問い文の内容語を、出た順に最大 5 つ並べたものです（例: 「摂氏 マイナス 度 全て 原子」）。LLM が `search_deep` に渡す形に近づけました。

### ハイライト 3 件（選び方を変える前の既定）の結果

| ページ・検索語 | dev で答えが残った割合 | dev のトークン比 | test で答えが残った割合 | test のトークン比 |
|---|---|---|---|---|
| long・question | 0.880 | 0.071 | 0.789 | 0.040 |
| long・keywords | 0.723 | 0.063 | 0.614 | 0.036 |
| article・question | 0.984 | 0.775 | 0.885 | 0.406 |
| article・keywords | 0.800 | 0.640 | 0.639 | 0.306 |

### ハイライトを 5 件にした場合

- long のページでは改善しました。
  - test の long・question は 0.789 → 0.870、long・keywords は 0.614 → 0.706 です。
  - トークン比は 0.04 → 0.07 に増えました。
- article のページでは変わりませんでした。数の上限で答えを落としていたのではなく、答えのある段落が選ぶ候補に入っていない（検索語との一致が無いか弱い）と見られます。

## ハイライトの選び方（件数を指定しないとき）

上の測定のあと、`highlightMaxCount` を指定しないときのハイライトの選び方を変えました（`src/enrichment.ts` の `extractQueryHighlightDetails`）。

### 規則

1. **窓に書き出しを付ける:** 長い節（800 字超）を窓で切るとき、節の書き出しを 350 字まで前に付けます。MMR の重複の判定には、従来どおり書き出しを付けない窓を使います。
2. **字数の目安まで足す:** 上位 3 件の後、合計が 1,600 字に収まる限り、窓で切った節を丸ごとに戻し、MMR の順で後ろの候補を足します（8 件まで）。
3. **拾えていない検索語の節を足す:** 選んだハイライトに無い検索語（採点で外れる 1 字の語も含む）がページにあれば、それを最も多く含む節を 1 つ足します。
   - 字数は「1,600 字の残り」と 800 字の大きいほうまでです。
   - 長い節は窓で切ります。収まらない表・コード・切れ目の無い長い文の節は飛ばして、次の節を試します（5 節まで）。
4. **本文を返す:** `evidence` で、ハイライトが本文の 0.75 倍以上の結果は、ハイライトの代わりに本文を返します（`src/integrated_search_host_response.ts`）。
   - 次の 2 つの場合は、従来どおりハイライトを返します。
     - 別の結果が `highlightsSameAs` でその結果を指している。
     - `maxTotalChars` で本文を切り詰める。

規則の効き方:

- 件数を指定したときは、規則 2・3 を使いません。`null` は省略と同じに扱い、端数は切り上げ、1 未満は 1 にします（REST は件数を検査しないため）。選ぶ節（どの節を、どの順で）は前と同じで、規則 1 の書き出しだけが付きます。
- 指定しないときも、先頭 3 件の節は前と同じです（U 字の並べ替え `reorderUFlat` の前）。
- 規則 1〜3 は、`scrape`・`scrape_batch`・`crawl_site` の既定のハイライトにも効きます。保存した 40 問のページでは、ハイライトの合計は 1 ページ平均 1,428 字から 1,705 字になりました。
- ハイライトを使うほかの処理も変わります。
  - 結果の並べ替え（`rerankByDeepEvidence`）は、ハイライトに検索語がどれだけあるかを使います。保存した 40 問では 4 問で並びが変わり、答えのある最上位のページが 2 位から 3 位に下がった問いが 1 つありました（上がった問いは無し）。
  - `contextSufficiency` もハイライトを使うので、`adaptiveScrape` の追加の取得は減る見込みです（測っていません）。
- キャッシュのキーの版を上げました（`search:integrated:v11`・`scrape:v8`）。上げないと、本番に入れた後もキャッシュが切れるまで前の選び方のハイライトが返ります。
- SPA のときにブラウザを起動するかの判定（`shouldEscalateToBrowser`。5 件を指定）は、規則 1 の書き出しを含む文で判定します。
  - 保存した 40 問の 214 結果を、すべて SPA と判定されたものとして判定させました。6 結果で「起動する」が「起動しない」に変わり（179 → 173 結果）、逆向きはありません。
  - 6 結果のうち 4 結果は静的な本文に答えがあり、2 結果は本文のどこにも答えがありません。
  - 書き出しは静的な本文の文です。800 字を超える節がある本文にしか付かないので、書き出しを判定から外す設定は作りませんでした。

### 作った理由

実際の search_deep の 2 回目の結果を保存して（40 問・93 ページ）、答えを落とした 12 ページの原因を調べました。

| 原因 | ページ |
|---|---|
| 長い節を窓で切り、答えが窓の外にあった | 5 |
| 答えのある節が 4 位以下だった | 4 |
| 1 字の検索語が採点で外れ、その語を含む節を選ばなかった | 2 |
| MMR が重複とみなして外した | 1 |

### 手元の JQaRA

| ページ・検索語 | test（前 → 今） | test のトークン（前との比、全文との比） | dev（前 → 今） |
|---|---|---|---|
| long・question | 0.7888 → 0.9004 | ×1.92、0.078 | 0.8803 → 0.9372 |
| long・keywords | 0.6137 → 0.7457 | ×1.77、0.064 | 0.7231 → 0.8031 |
| article・question | 0.8851 → 0.9594 | ×1.51、0.613 | 0.9843 → 0.9965 |
| article・keywords | 0.6386 → 0.7158 | ×1.63、0.497 | 0.8003 → 0.8175 |

- 前に残っていて、今は落ちたページは、test・dev のどの組でも 0 です。
- **件数を増やすだけの場合と比べました。** 3 件の選び方のまま件数を 5 件・8 件にした値を、今と同じトークンの位置で線形に補間しました。
  - long・question は 0.884（今は 0.9004）、long・keywords は 0.721（今は 0.7457）です。
- **字数だけで説明できる分も見ました。** 今と同じ字数をランダムな節で埋めると、long・question 0.510、long・keywords 0.482 でした。

### 保存した 40 問の結果

保存した結果のページから、ハイライトを作り直して比べました。

- **注意:** このページは規則を作るのに使ったものです。手元の JQaRA と違い、確かめの値ではありません。
- **答えが残ったページ:** 81 → 88（93 ページ中）。
- **答えが残った問い:** 27 → 29（29 問中）。
- 規則を作った時点では 89 ページでした。差の 1 ページは、書き出しを MMR の重複の判定に入れていたため、たまたま答えの節が 3 位に入っていたものです。判定を前と同じに戻したので落ちました。
- **トークン（縮めた形）:** url・title・source・markdown・highlights・snippet だけを残した結果を直列化して数えました。本番の応答は項目がもっと多いので、比は本番と違います。
  - `evidence`: 163,221 → 202,318（×1.24）。全文との比は 0.207 → 0.246 です。
  - `full`: 790,068 → 823,740（+4.3%）。ハイライトが長くなるためです。

### 実際の search_deep の 3 回目（規則を作るのに使っていない 36 問）

1・2 回目と重ならない 36 問で、実際の `search_deep` を 1 問 1 回ずつ呼んで結果を保存しました。そのページで、前の選び方と今の選び方のハイライトを作り直し、MCP の直列化（本番の形）で比べました。

- **問いの選び方:** JQaRA test を q_id の順に並べて 41 問おきに選び、2 回目から 20 問ずらしました。検索語は 2 回目と同じ内容語 5 つです。
- **40 問の予定を 36 問で止めた理由:** 手元のプロセスが Yahoo の 429 を 1 回数えたためです。間隔は 12 秒で、本番の `yahoo_429_total` は前後で増えていません。

| | 前の選び方 | 今の選び方 |
|---|---|---|
| 答えが残ったページ（`full` に答えのある 82 ページ中） | 66 | **69** |
| 答えが残った問い（`full` に答えのある 25 問中） | 22 | 22 |
| `evidence` のトークン（36 問の合計） | 179,553 | 215,013（×1.20） |
| `full` のトークン | 797,403 | 826,984（+3.7%） |
| `evidence` と `full` の比 | 0.225 | 0.260 |
| 1 問あたりの中央値（`evidence`） | 4,819 | 5,405 |
| 1 ページの抽出時間（180 結果、3 回の中央値） | 平均 4.4 ms・最大 50 ms | 平均 3.9 ms・最大 53 ms |

- **今の選び方で新しく落としたページはありません。** 増えた 3 ページは、規則 1・2・3 が 1 ページずつ拾ったもので、規則 4 によるものはありません。
  - この 36 問では、規則 4 で本文を返した結果は 35 結果ありました。そのうち答えのあるページは、規則 4 が無くてもハイライトに答えが入っていました。規則 4 はトークンを約 2.8% 足しただけです。
- **問い単位の差は出ませんでした。** 増えた 3 ページは、どれも別のページで答えが残っていた問いのものです。
- **どちらの選び方でも落とした 3 問:**
  - 2 問は、数千〜2 万字の長い節（見出しの無いページを含む）で、窓が答えの外を選びました。
  - 1 問は、答えの節の点が首位の 0.35 倍に届かず、候補に入りませんでした。答えの節に拾えていない検索語も無いので、規則 3 も働きません。
- **抽出時間:** 規則 2 で MMR が選ぶ件数を 8 件に増やすと、そのままでは 2 倍ほど遅くなりました（平均 8.2 ms・最大 270 ms）。MMR が組ごとに分かち書きをし直していたためです。候補ごとの語の集合を一度だけ作るようにして、前と同じぐらいに戻しました。

## 読み方

- **ページ単体では、語を並べた検索語のときに答えを落とすことがあります。** 記事 1 本ぐらいのページで、test 0.716、dev 0.818 です（選び方を変える前は 0.639・0.800）。
- **実際の `search_deep` では、答えの多くが残ります。** 1 回目は 21/21 問、3 回目（規則を作るのに使っていない問い）は 22/25 問で、`full` にあった答えが `evidence` にも残りました。理由は 2 つあると見ています。
  - 検索の上位ページは、検索語を含みやすい。
  - 1 問に複数のページを返すので、どれかのページに答えが残る。
- **足りないときは、モデルが取り直します。** MCP の指示文とツールの説明には、根拠が欠ける・曖昧なときは `responseMode: "full"` か `formats: ["markdown"]` で取り直すよう書いてあります。応答の `contextSufficiency` は、検索語がどの証拠にも出てこないことを示します。
- **全文が要る呼び出し側は、`responseMode: "full"` を明示してください。** 網羅的な列挙、比較、全文の要約などです。
