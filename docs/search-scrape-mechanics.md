# Sora 検索・スクレイプの仕組み

本書は Sora の Web 検索から本文取得・証拠抽出までの一連の動作を説明します。
利用者向けの操作手順は [README.md](../README.md)、監査証跡は
[retrieval-v2-dod.md](retrieval-v2-dod.md) を参照してください。

## 全体像

```text
Yahoo 検索 (Web / Realtime)
  ↓ 候補統合 (RRF)・診断スコア付与
Scrape 対象の選択 (上限 limit に対し候補プールを広めに確保)
  ↓ 本文取得 (静的 HTTP → 必要時のみ Chromium)
証拠抽出 (ρSelect v2: ハイライト選択)
  ↓ 深層リランキング (取得後エビデンスで再評価)
応答 (compact 既定、verbose 時のみ診断情報を付与)
```

検索エンジンの順位と最終回答用の順位は別物として扱います。
前者は取得用、後者は取得後の証拠で決めます。

## Yahoo Web 検索

- 単一 SERP はプロバイダ順を保持します。BM25 による全面並べ替えはしません
  （`SORA_WEB_NATIVE_RANKING=false` で従来動作に戻せます。providerRank は記録継続）。
- lexical スコアは順位決定に使わず、診断用にのみ付与します。
- 複数クエリ統合は opt-in（`SORA_WEB_QUERY_UNION=true`）で、加重 RRF
  （original 1.0、fallback/rescue 0.6）により統合します。同一 URL の
  クエリ別順位は `providerRanks` に残し、来歴を失いません。
- Q0 取得後に件数・要件カバレッジ・ドメイン偏りを評価し、弱い場合だけ
  Q1 を実行します（adaptive rescue）。十分なら追加リクエストしません。
- scrape 失敗時は有効コンテンツ基準で候補を補充します。

## Provider Pressure Controller

Yahoo 上流の 429 対策として、プロセス全体で 1 つのコントローラが状態を持ちます
（X Realtime とは共有しません）。

- 成功で間隔を少しずつ短縮（下限 150ms）、429 で倍増（上限 5000ms）します。
- 直近 30 秒の 429 が 3 件で回路開放し、15 秒冷却後に 1 件だけ試します。
- `Retry-After` 応答は構造化エラーで保持し、冷却に反映します。
- 長時間の待機はしません（最大 250ms）。圧力 high ではクエリ予算を 1 件に絞り、
  フラグ設定よりプロバイダ健全性を優先します。
- 429 検出時は追加負荷を止め、`throttled: true` と
  `stopReason: 'provider_rate_limited'` を返します。Q0 の成功分は保持します。

## キャッシュと SingleFlight と stale

実行順は fresh キャッシュ → SingleFlight 合流 → プロバイダ → stale 退避です。

- 同一検索の同時実行は 1 件のプロバイダ要求にまとめます。
- 成功結果は Yahoo 側に fresh 5 分／stale 30 分で保持します。
- stale は通常返しません。冷却中・回路開放・429・上流失敗のときだけ返します。
- 認証付き scrape は共有キャッシュを使いません。テナント別管理です。

## X Realtime 検索

- `recent`（新着順）と `popular`（話題順）の意味を保ち、汎用 Web スコアで
  置き換えません。
- bounded な wave 実行（上限あり）で候補を集め、カバレッジ充足・予算超過・
  429 で停止します。失敗した wave の兄弟結果は保持します。

## Deep Search（search_deep）

- 最終件数より広い候補プールから取得対象を選びます。
- REST `POST /search`・`POST /search/integrated` と MCP `search_deep` の
  `adaptiveScrape: true`（opt-in、上限 `scrapeBudget`、既定 8・最大 20）で、
  証拠充足の判定に基づき追加取得します。不足が解消すれば早期停止します。
  `scrapeContent: true` の場合に有効で、`scrapeBudget` が `limit` 未満なら
  `limit` まで引き上げます。
- 失敗分は `scrape_refill` として補充し、試行回数ではなく有効証拠で数えます。
- 取得後の本文・ハイライトで最終リランキングします。
- 価格・日付などの値を求めるクエリは、回答カバレッジが閾値未満なら
  追加取得を続けます（言及のみでは止めません）。

## 証拠抽出（ρSelect v2）

- クエリ固有の数学的最適化でハイライトを選択します。本体は変更しません。
- 要件抽出（entity／intent／support 語＋時間意図）、価格・重量・日時などの
  回答値検出、言及と回答の分離、entity 近接、表・定義・文の構造評価、
  時間的関連度を組み合わせます。
- 精度抽出で不足なら想起（recall）抽出を試し、改善した方を採用します。
- 回答値の判定は、見出し文（「■チケット料金」）の後ろ2文までの値も回答とみなします（`DEFAULT_VALUE_LOOKAHEAD`）。
  見出しと値が別文に分かれる日本語ページで回答なしと誤判定していたためで、保存済み100ページ・23クエリの実測では
  ハイライト選抜が98/100不変、変化2件は改善、`answerCoverage` は上昇31件・低下0件でした。0を指定すると従来動作です。
  副作用として、SPA判定時のブラウザ起動回避（静的本文の回答カバレッジ0.5以上）も、この形の本文で働きやすくなります。
- 抽出リソース上限（候補数・入力バイト・時間）を守ります。
- 明示的日付要求（10月11日・明日など）は想定年と照合し、年不一致を減点します。現在意図（最新・現在など）とは独立した軸です。
- 年なしの月日はサーバー実行日時から次に到来する日付の年を仮定します。
  例: 2026年9月30日時点の「10月11日」は2026年、同日の「9月1日」は2027年です。
  過去の調査では年を明示してください。「今日」「明日」などのクエリ解釈も
  サーバー日時が基準です。本文内の相対日時注記 `annotateTemporal` は記事の公開日時を基準とする別処理です。
- `updated` は検索プロバイダーへの更新期間フィルターであり、開催日フィルターではありません。
  すべてのクエリを最新優先にはしません。時間語・回答値の検出は辞書と規則に基づくため、
  網羅的な意味理解や検索精度の保証ではありません。
- 候補は安価な語彙順で 12→24→48 件と段階投入し、回答カバレッジが埋まったら停止します（診断に candidateExpansion を記録）。
- 語彙（intent語・stopwords・時間語）は src/retrieval/lexicons/ に分離し、スコア倍率は EVIDENCE_WEIGHTS 一表に集約しています。

## ブラウザ利用方針

- 既定は静的 HTTP 取得です。Chromium は SPA 検出・描画失敗などの場合のみ
  起動します（起動・節約回数はメトリクスで確認できます）。
- 静的本文に実証済みの回答がある場合は、SPA 信号があってもブラウザを
  起動しません。回答なき弱い証拠だけでは起動を続けます。
- 認証情報はクロスオリジン redirect で除去し、SSRF 検証と応答サイズ上限を
  適用します。
- 描画の待機は、`networkidle2` を基本としつつ、`load` 後の静止待ちを 5 秒で
  打ち切ります（計測タグやロングポーリングで静止しないページ向け）。その後の
  DOM 静止判定は、DOM の変化ではなく見えている本文（長さ・先頭/中央/末尾・
  画像数）の変化で行い、属性だけを書き換え続けるページで上限まで待ちません。
  `data-src` / `srcset` の遅延読み込み画像は HTML 解析側で実 URL に解決します。
- 共有 Chromium は無操作 5 分（`BROWSER_IDLE_TTL_MS`）で閉じ、次の利用時に
  再起動します。開いているコンテキスト（ブラウザセッション等）がある間は
  閉じません。同時描画数は、未指定ならメモリから 1〜5 を自動算出します。

## Deep Search の応答量と待ち時間

- `maxTotalChars`（任意）は本文合計の上限です。上位ほど多く配分し、短い
  ページの余りは残りへ再配分します。`highlights` は削りません。
- `scrapeDeadlineMs`（任意、既定は無効）は遅いページの打ち切りです。半数が
  揃ってから 5 秒、または上限で打ち切り、`deadlineExceeded` とスニペットで
  返します。発動した応答はキャッシュせず、補充・追加取得も行いません。
- `contextSufficiency` は、要件語（`extractQueryRequirements`）の言及と
  回答値の有無を、取得できた本文・ハイライト・X 投稿に対して判定した信号です。
  `no_gap_detected` は十分の保証ではありません。

## 可観測性

- 既定応答は compact です。`verbose: true` で取得クエリ・順位来歴・圧力・
  予算・停止理由などの診断が出ます。
- `GET /metrics`（JSON の `counters`、Prometheus 形式）で運用カウンタを
  出力します。カウンタ一覧は README のメトリクス節を参照してください。
- live 評価は間隔を空けた少量実行とし、結果 JSON を `eval/results/` に残します。
