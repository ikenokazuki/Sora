# Sora 調査機能の最終ゴールと実行計画

> 後任への指示: この文書を最初に読み、タスク順に実行する。実装時は superpowers:executing-plans 等の適用可能な計画実行スキルを使う。既存の未コミット変更を保持し、各チェック欄に結果と成果物の場所を記録する。文書だけで全ゴール達成とは扱わない。

**Goal:** 呼出元LLMが任意の判断目的について、初回で可能な限り十分な根拠を取得し、不足を既存WEB検索で補い、確認済みと未確認を区別できる、必要最小限のSora調査機能を確立する。

**Architecture:** 呼出元LLMが問いの分解・意味解釈・最終判断を担当する。Soraは既存のWEB検索・本文取得と、追加価値が実証された専用取得器を提供し、取得過程・根拠・日時・未取得事項を返す。スキルはこの手順を教える。内部LLMは導入しない。

**Tech Stack:** 既存Bun/TypeScript/Hono/MCP/SQLiteを使用。比較実験までは新しいフレームワークや依存を追加しない。

**Spec:** 本文の要件を最新の合意として扱う。背景は同ディレクトリの country-intel-strategy-review.md、country-intel-quality-evaluation.md、country-intel-handoff.md。古い「固定分野を埋める」目標より本書を優先する。

## 0. 後任が最初に理解すること

ユーザーは、この機能を残すこと自体を目的にしていない。既存WEB検索とスキルだけで同等以上なら、専用収集器を縮小してよい。ただし必要情報の取得を諦めて、欠落通知だけで済ませてはいけない。

企業SNS投稿判断は重要な評価対象だが、専用用途ではない。旅行・観光、金融、マーケティング、未知の調査目的にも利用する。日本だけでも中国だけでもない。中国は特殊な取得環境を評価する国として含める。

「MCP」は接続方式、「スキル」はLLMへの手順、「プラグイン」は配布方法。それだけで取得範囲や正確性が向上するわけではない。配布パッケージ作成は品質確認後とし、今は不要。

## 1. 最終ゴールと完了条件

次のすべてを満たして初めて完了とする。

1. 既存検索＋スキルを基準として、専用取得器の価値を比較実験で説明できる。
2. 初回で必要事項をまとめて取得でき、根拠・時点・観測範囲・取得失敗を返せる。
3. 呼出元LLMがSoraの既存search_web/scrapeで不足を補える。未確認事項に対応するID・検索案・必要な出典種類が分かる。
4. 誤分野、対象国外、古い出来事、空SNS、証拠参照切れに対する回帰検証がある。
5. 強めのモデルと能力の低いモデルの少なくとも2構成で、同じ調査手順が機能するか検証済み。利用可能なモデルが1つならこの項目は未達と明記する。
6. 主要12か国の品質と制約を国別に示す。全体平均だけで低品質な国を隠さない。
7. 必要最小限のプロバイダー一覧、代替経路、障害検知・復旧・停止の運用手順がある。
8. 時間上限、中断、キャッシュ、保存期限、同時利用、応答サイズを実測する。

「全世界を完全網羅」「炎上を必ず予測」「どんなモデルでも同じ判断」は完了条件にしない。根拠があっても未来の結果を保証しない。

## 2. 絶対に守る制約

- 内部LLMを導入しない。外部モデル比較は評価に限る。評価用のモデル呼出しを製品ランタイムへ埋め込まない。
- 呼出元モデルの変更だけで同じ品質になると断言しない。取得部分と調査計画の品質を別に測る。
- 初回で最大限取得する。追加検索を前提に初回を弱くしない。
- 定期収集を復活させない。要求時収集と期限清掃は別の機能として扱う。
- 国別例外・専用HTML解析を、比較実験前に追加しない。
- Yahooリアルタイムは日本語圏の投稿観測。Weibo熱搜は投稿全文検索ではない。
- HTTP200、記事数、枠が満杯、単体テスト成功を目的達成の証明にしない。
- 公開情報0件、取得失敗、検索範囲外、未調査を区別する。
- 既存の未コミット差分、ステージ済みcollector削除を壊さない。無断コミット・デプロイ・Nix変更は行わない。
- APIキーや費用が必要な実験は利用可能性・権限を確認。利用できなければ実測済みと書かない。
- 成果物は通常の日本語で記述する。

## 4. 評価設計

### 4.1 比較する二方式

A: 呼出元LLM＋同じ調査スキル＋Soraの既存search_web/scrape。
B: A＋現在の専用収集機能。必要なら最初は実験用の取得器subset注入で比較する。

同じモデル、同じ質問、同じ時間/出力/検索回数予算で比較する。順番を交互にし、近い時刻に実行。モデル、設定、プロンプト、各ツール引数、開始終了時刻、全結果、失敗を保存する。

さらに二種類の試験を分ける。
- 固定計画試験: A/Bに同じ確認事項を渡す。取得経路そのものの差を測る。
- 自由計画試験: 元の問いだけを渡す。弱いモデルが重要事項を計画できるか測る。

### 4.2 ケース

最初はJP/US/CN/SA/IN/BR × 次の4用途 = 24ケース。固定標本の合成テストと、ライブの実在出典による評価を混同しない。

- SNS/マーケティング: 架空企業の投稿文、画像の説明、業種、プラットフォーム、対象国、公開予定時刻を指定。直近事件、文化・言語解釈、企業関連論争の確認事項を持つ。架空企業の実在しない論争を作らない。
- 旅行観光: 都市、出発日、交通手段、旅行者条件を指定。現行の公的注意、交通制約、対象期間を確認。
- 金融: 具体的な企業または経済指標、判断対象日を指定。発表主体、数値、単位、対象期間、公表日、訂正の確認。
- 自由目的: 教育、調達、製品サポート等、既存の固定分野に収まりにくい問い。

最低6件は、取得不能・同名別国・過去情報・相反する資料・現地語表記揺れ・関連する情報が公開されていない条件を含める。過去の炎上事例は事件後の情報混入とモデルの既知知識に注意し、過去時点の予測能力の証明としない。

ケース形式:
{
  "id": "CN-travel-01",
  "region": "CN",
  "scenario": "travel",
  "question": "実験前に対象都市・日付を固定した具体的な問い",
  "asOf": "実験開始のISO日時",
  "requirements": [
    {"id": "transport", "question": "予定路線に対象日の運休があるか", "critical": true, "expectedSource": "運行会社または公的交通機関"}
  ],
  "referenceEvidence": [],
  "expectedUnknowns": [],
  "reviewStatus": "unreviewed"
}

上記は形式例。実行対象のcases.jsonには抽象文のまま登録しない。referenceEvidenceには採点者が独立に確認したURL、引用、日時、何を支持するかを入れる。正解が不明な必須項目は未採点として残す。

### 4.3 指標と合格条件

比率の分母を必ず記録する。
- 必須事項充足率: 根拠で支持された確認事項 / 事前に必要とした確認事項。欠落通知だけでは分子に入れない。
- 初回充足率と補完後充足率を別に出す。
- 根拠支持率: 引用が主張を支持する件数 / 検査した主張数。
- 地域/問い適合率: 適合した主要証拠 / 主要証拠。
- 重大な誤り: 古い情報を現在とする、別の国を対象とする、取得不能を問題なしとする等。
- SNS: 投稿本文とランキングと報道を区別できたか。取得0件の理由を返したか。
- 運用: 所要時間、外部HTTP数、トークン、費用、DB増分、失敗率、保守が必要な取得器数。

採用ゲート（今回の計画上の目標。安全保証ではない）:
- 参照IDの解決100%、標本中の重大な誤り0。
- 根拠支持率95%以上、地域/問い適合率90%以上。
- 初回の必須事項充足率80%以上、補完後90%以上。
- 上記を国・用途・モデル別に示す。情報非公開等の達成不能も分母から黙って除外せず、公開情報で解決可能な部分の値を別掲する。
- 閾値未達なら理由と再試験を記録。実装を完成扱いにしない。情報制約による未達はユーザーへ報告する。
- 24件では精密な統計を主張しない。候補を絞った後、JP/US/FR/CN/DE/IN/BR/ID/KR/ES/SA/RU ×4用途へ拡張し、複数日・3反復で確認する。

検索予算はまず各方式同じ30秒、追加で60秒条件。これは比較条件であり本番SLAの確定ではない。初回MCP内部予算と呼出元の計画時間を別計測する。

採点は方式名を隠して原文と照合。生成モデルだけの自己採点で合格にしない。別モデル採点は補助とし、重大事例は人またはレビュー担当が確認する。

A中心の場合:

- [ ] 既存利用者の契約を確認してから非推奨化を文書化。即削除しない。
- [ ] 現行収集器を全用途の十分な回答として案内しない。

Bが必要な場合:
- [ ] research_country_contextの単一region/query呼出しは維持し、必要なら確認事項配列を任意追加。
- [ ] 確認事項をID付きで受け取り、結果をIDごとに返す。日付・地域・検索語を呼出元が明示できるようにする。
- [ ] confirmedを機械判定で乱発しない。MCPが返す取得状態と、呼出元が決める意味的十分性を分離する。

推奨の最小結果契約（既存型への追加を優先）:
type RequirementAcquisition = {
  requirementId: string;
  status: 'retrieved' | 'empty' | 'failed' | 'not_attempted';
  evidenceIds: string[];
  attemptedQueries: string[];
  gaps: string[];
  suggestedQueries: string[];
};

retrievedは候補証拠が取得できた意味で、要件充足の保証ではない。statusに十分/安全を混ぜない。候補・背景を捨てずに区別し、呼出元が必要に応じ原文を参照できるようにする。

- [ ] 検索facetは取得経路として残し、意味的な確定分類と分離。
- [ ] 期限外の出来事を背景へ分離。日付不明を最新としない。
- [ ] SNS要求済み0件の不足と、実際に観測した言語・プラットフォームを返す。
- [ ] すべてのevidenceIdが同一contextの取得APIで解決できることを検査。
- [ ] 初回応答は重複・メタデータを抑え、主要根拠と不足を優先。詳細取得の参照は維持。
- [ ] スキルで不足IDをsearch_web/scrapeの追加調査へ結び付ける。既存検索処理をコピーして新しい検索エンジンを作らない。

回帰テストはTask 1の具体例を使う。意味判定を呼出元に委ねた項目は、単体テストでは候補情報を保持する契約を検査し、自由計画試験で正しく判断できるか確認する。

| 弱いモデルが調査を省略 | スキル/入力契約を小さく明確にし再評価 | 勝手に内部LLMを導入 |
| APIキーがない | 固定標本・既存道具の独立作業を進め、未実測を明記 | 比較結果を推定で埋める |
| 比較差が小さい | 小さく保守しやすい構成を採る | 専用収集器の維持を目的化 |
| 品質不足が公開情報制約 | 代替出典や契約データの選択肢と未達を報告 | 欠落通知だけでゴール達成 |
| 全件を読むと予算超過 | 問い別の優先順位と段階的原文取得 | 根拠を消して十分と表現 |

## 7. 最終報告の形式

1. 達成/未達を冒頭に記載。
2. 採用した構成と、それを選んだA/B実験の結果。
3. 初回と補完後の品質を国・用途・モデル別に示す。
4. 未解決の取得制約と、利用側が誤解してはいけない範囲。
5. テスト・負荷・保持期限・費用の検証結果。
6. 変更ファイル、実験記録、運用手順へのリンク。
