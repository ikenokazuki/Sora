# 汎用情報収集機能の方針再評価

評価日: 2026-09-23。実装を進める前の判断資料。
結論の区分: 「観測」はコードまたは既存実験で確認。「仮説」は比較実験が必要。「未検証」は調査・測定未実施。

## 1. 暫定結論

現在の方式を、そのままプロバイダー追加と国別修正で拡張するのは推奨しない。国別ニュースを多く取得する仕組みと、任意の目的に必要な証拠を集める仕組みは要件が異なる。現行実装は前者に寄り、後者に必要な目的適合性・不足検出・情報の意味の検証が弱い。

ただし全面的な作り直しも現時点では正当化されない。既存の取得アダプター、本文抽出、出典・日時の保存、MCP/REST入口は比較実験に再利用できる。

暫定第一候補は「汎用検索と本文取得を土台に、調査目的から必要事項を計画し、必要な専門データだけ加える、一回呼出しの調査ツール」。内部で有限回の追加探索と根拠検証を行う。LLMは計画・意味判定を担当できるが、URL/引用/時刻/予算/参照整合性はプログラムで確認する。これが既存方式やグラウンディング単体より高精度・低負担かは未検証。

## 2. 目的を評価可能にする

推奨する目的:
「国・地域、調査したい問い、時間範囲を受け取り、初回呼出しの予算内で、回答に必要な関連証拠と重要な周辺情報を最大限取得し、出典・時点・未取得事項とともに利用側LLMへ返す。」

- 国だけを渡した場合は広域概況。金融・旅行などすべての個別目的の十分性を保証しない。
- 問いがある場合は対象企業・場所・期間・判断に必要な項目を優先する。汎用性は新しい問いを扱えることであり、常に固定の6分野を全部埋めることではない。
- 「リアルタイム」は共通の一語にしない。取得時刻、情報源の公開時刻、出来事の時刻、株価等の観測時刻、キャッシュ経過時間を区別する。
- 「網羅性」はインターネット全体に対して測れない。必要事項ごとの根拠の有無と、独立に用意した評価事例に対する取りこぼしを測る。
- 初回で取り切る目標は維持する。そのための内部追加検索は許容。利用側に何度も再実行させる設計を既定にしない。
- 取得できない情報を明示することは必要だが、欠落表示だけで収集目標の達成としない。

例: 「中国の旅行」では必要情報が曖昧。「来週上海へ旅行する際の運休・入国条件・災害」は、運行会社、行政、気象情報など確認先と時点を評価できる。

## 3. 現在の問題

### 3.1 品質上の観測済み問題

詳細証拠は country-intel-quality-evaluation.md に記載。

1. 検索クエリの分野を記事内容の分野として採用し、水泳記事が保健欄に入る。
2. 依頼との適合性より本文の有無等が優先され、金利調査の金融欄に刑務所の記事が入る。
3. 地域への言及と現地への影響が混在し、国外災害への援助が現地旅行情報に入る。
4. 過去に終了した災害が現在の運休調査へ入り、公開日と出来事の有効期間を十分区別できない。
5. 多言語の表記揺れを拾えず、サウジの記事68件中65件が地域未確認候補になる。
6. SNSを要求して0件でも不足が明示されない事例がある。熱搜は投稿本文検索ではない。
7. 中国の追加実験で応答内に参照先のない証拠IDが5件。スキーマ検証だけでは検出できない。
8. 本文にナビゲーション、広告案内、重複が残る。初回JSONは追加実験で約220〜290KB。
9. 検索結果の見出し、抜粋、取得本文、構造化データの強さが違うが、ファクトという名前で過信されやすい。
10. 取得経路としてのofficial_webと、公式出典であるという意味が混同される欄がある。

現時点のテスト成功は既存契約の動作を示すが、意味的な品質の達成を示さない。291件のテストが成功しても、上記は存在する。

### 3.2 運用上のコード確認事項

| 項目 | 確認した実装 | 懸念と次の検証 |
| --- | --- | --- |
| キャッシュ | report.ts が dependencies.cache ?? null を渡し、registryの既定永続キャッシュを使わない | noCache=falseでもこの層は再取得。別層のキャッシュとは区別。通常/強制再取得のHTTP回数を測る |
| 保存期限 | pruneCountryIntelの参照は定義とテストのみ。report経路はpruneHotObservationsを呼ぶ | TTLの値があっても古いレポートは自動削除されない。外部運用ジョブ有無も確認し、要求時の間引き清掃等を設計 |
| 総時間上限 | reportの残り時間と別にprovider.timeoutMsが優先される | 29秒が厳密な終了保証ではない。遅い通信・二段目検索の実測が必要 |
| 中断伝播 | scrapeArticleアダプターは外側signalを取得前後で確認。内部スクレイパは独自timeout | 呼出元が終了しても内部取得が即座に中断される保証は未確認 |
| 同時実行 | provider_httpの待機列はsignalを受けず、レスポンスヘッダ受信後に枠を解放 | 待機中キャンセル、本文取得中の並列量、複数利用者での遅延を測る |
| レート制限 | host間隔の確認と実際の取得に待機が挟まる | 同時要求が同じ時刻の判定を通過し得る。単一利用の成功と負荷時の安定性は別 |
| 障害分類 | Yahoo検索アダプターは例外を空配列へ変換する経路がある | 通信失敗と検索0件が混ざる。原因を保った診断が必要 |
| 保存量 | 全件レポートと証拠詳細を保存 | 要求あたりDB増分・WAL・清掃後容量を測る。定期収集停止だけでは容量管理にならない |
| 環境差 | sandbox内DNS失敗、外で成功という実測 | 接続障害を直ちにDNS設定/上流障害と断定しない。実運用コンテナ内の経路も評価 |
| 本番差 | 主な検証は作業ツリー・直接関数実行 | 本番の設定、REST/MCP直列化、複数同時要求まで確認していない |

上記はコード上の確認または検証が必要な懸念。全項目で実害を再現したわけではない。

### 3.3 追加で未検証の運用事項

- ユーザー/テナント間の保存済みcontextへのアクセス境界。IDが推測しづらいだけで十分とは扱わない。
- 取得した外部本文のプロンプト注入。LLMによる計画を導入する場合、本文の命令で送信先や権限を変えない。
- 任意URL、リダイレクト、動的な出典発見からの取得に対する既存SSRF防御の適用範囲。防御の実装は存在するが、この経路全体の監査は未実施。
- 検索APIへ送る質問の機密性、利用条件、保存可能範囲。提供元・契約ごとに導入時確認する。
- ニュースとマーケット価格、旅行の運行状況など専門データの区別。一般Web検索だけで目的に必要な最新性を満たすとは限らない。
- 問題がないとの結論の扱い。検索0件から「運休なし」「炎上なし」「安全」を導かない。
- 監視体制: providerのHTTP成功率だけでなく、目的適合率、鮮度不明率、根拠欠落、コスト、p95時間を観測する。

## 4. 代替案の比較

精度欄は実験結果ではなく評価上の見通し。精度優位は比較実験で決める。

| 方式 | 実装・運用負担 | 利点 | 残る問題 | 判断 |
| --- | --- | --- | --- | --- |
| A 現行の多数プロバイダー＋ルール | 高い。非公式経路の追随と多言語ルール保守 | 個別ソースの制御、構造化情報、既存資産 | 意味判定、目的適合性、国ごとの例外増加 | 基準として保持。追加拡張は一旦止める |
| B Gemini等の検索グラウンディング単体 | 自作部分は最小 | 問いの解釈、検索・要約を任せられる | 未調査事項や選別前資料の観測に限界。引用があっても十分性は別 | 最低限の比較対象。単独採用も排除しない |
| C 検索・抽出API＋小さな調査制御 | 中程度。取得保守を外部へ移せる | 生の根拠を保持し、質問・日付・出典を自分で検査 | API費用、索引偏り、地域差、SNS制約 | 暫定第一候補 |
| D スキル＋呼出元LLM＋既存の検索道具 | サーバー側は小さい | 呼出元モデルを利用できる。調査手順を配布しやすい | 弱いモデルの手順遵守・欠落検知が揺れる。複数ツール往復 | 補助導線として有望。単一呼出し要件は別途保証が必要 |
| E 検索主体＋少数の専門API/地域ソース | 中程度 | 公的警報や市場・運行情報など検索だけでは弱い領域を補える | 無制限追加するとAへ戻る | Cに必要なものだけ加える案 |
| F ライセンス付きニュース/SNS等 | 契約・統合負担、費用は要調査 | 必要な範囲で履歴・更新・取得権限を確保できる可能性 | 中国や各SNSを一律にカバーする保証なし | 公開経路で必須要件を満たせない場合に限定検討 |

スキル/プラグインは配布・呼出し方法であり、それ自体が取得能力や精度を改善するわけではない。同じ調査手順をサーバー内で実行すれば単一呼出しにできるが、モデル費用と実行制御が必要になる。

## 5. 公式仕様から確認できること

- GeminiのGoogle Search groundingには、検索クエリと引用を確認する応答情報がある。返却形式はAPIによって異なる。完全なブラックボックスと扱う必要はない。ただし、検索ログや引用が存在することは未発見情報まで含めた網羅性の証明ではない。
  https://ai.google.dev/gemini-api/docs/google-search
- Tavily Searchは検索結果の本文情報、raw content、日時等の指定を備える。country指定はgeneral検索での国優先であり、対象国で発生した記事だけを保証するフィルターではない。
  https://docs.tavily.com/documentation/api-reference/endpoint/search
- Exa Searchはコンテンツ取得とlivecrawl/maxAgeHours等の指定を備える。クロールの新しさと記事内容の出来事の新しさは別。
  https://exa.ai/docs/reference/search

これらは仕様確認のみ。現環境の中国・アラビア語等に対する到達性・関連性・費用・遅延の比較実験は未実施。価格数値や優位性をここでは断定しない。複数サービス採用時も、同じ転載記事や共通上流を独立した裏付けに数えない。

## 6. 最小限の比較実験

### 段階1: 小規模な選別

6か国（JP/US/CN/SA/IN/BR）×4種類の問い=24ケース。最初から全サービスを実装せず、A現行、Bグラウンディング単体、C検索API1社＋計画・検証の3方式を比較。Dスキル案はCと同じ計画を呼出元LLMで実行する少数ケースから比較する。

問い:
1. 金融: 指定した経済指標・金融政策の最新発表と対象時点。
2. マーケティング: 特定商品/業界の最近の変化。ニュースと実際の消費者投稿を区別。
3. 旅行: 特定都市・日程の交通障害/公的注意情報。
4. 一般: 業種・生活・教育等、既存の6分野に収まりにくい自由な問い。

SNSとリアルタイムは横断条件として必ず含める。国だけの概況も少数加える。日本語入力と現地語入力、多言語国、公開情報が存在しないケースを含む。

各方式には同じ問い・時間予算・出力予算を与える。最初は全体30秒、その後必要なら60秒で別条件を試す。秒数は合意済みSLAではなく比較条件。内部検索回数・API費用・トークン・外部通信数を全記録。複数方式を近い時刻に交互の順番で実行する。

### 段階2: 品質の測り方

- 試験前に、各ケースの必須確認事項と公式資料等の参照回答を独立に用意する。
- 方式名を隠して関連性・誤り・十分性を判定する。同じLLMだけで生成も採点も完結させない。多言語標本は言語理解のあるレビュアーまたは別モデル＋原文照合を使う。
- 主張単位で根拠が本当に支持するか、日時・数値・場所が一致するかを調べる。URLや引用の存在だけでは合格にしない。
- 主要指標: 必須事項充足率、根拠支持率、地域/分野適合率、過去情報の現在扱い率、SNS不足の通知率、既知重要事項の取りこぼし。
- 運用指標: p50/p95応答時間、1問あたり総費用、出力トークン、DB増分、保守対象数、上流障害時の劣化。
- 精度とは別にカバレッジを測る。無難な少数記事だけ返す方式が過大評価されないようにする。
- 24ケースは選別用であり、p95や国別品質を確定するには不足。候補が絞れたら12か国・複数日・各3回以上で広げる。

暫定ゲート案: 証拠参照解決100%、標本内の重大な根拠なし断言0、明示的なSNS取得失敗の隠蔽0。関連性90%以上、必須事項80%以上などはユーザー用途に合わせて事前に決める。重大事項の欠落を平均点で相殺しない。

### 段階3: 利用側LLMでの検証

同じ利用側LLMへ各方式の証拠を渡し、同じ問いに答えさせる。強いモデルだけでなく後任に想定する小さいモデルも評価する。これで取得結果の見栄えではなく、実際の判断材料としての効果を測る。小さいモデルが欠落を理解できない場合は、出力構造と候補/確認済みの区分を改善する。

### 段階4: 運用検証

最終候補だけを1/5/10同時要求、キャッシュあり/なし、上流429/timeout、応答途中切断で試す。クライアント切断後の残存処理、同一要求の重複取得、DB保存・清掃、REST/MCP応答サイズを確認する。

## 7. 採用の判断規則

- Bが十分な品質で費用・時間も許容なら、独自収集の大部分を削減する選択肢を採る。自作の維持を目的化しない。
- Bの不足検知や再現性が弱くCが改善するなら、Cを中心にする。
- Cで中国の熱榜、警報、価格、交通等だけ不足するなら、Eとして該当ソースだけ残す。
- Dが呼出元モデルの違いで不安定なら既定実行経路にせず、手動の深掘り用途にする。
- Aが独自に取れる重要情報を持つなら、そのプロバイダーを残す。件数だけ多いものは残す根拠にしない。
- 公開SNSで必須事項が満たせなければ、契約データか要件調整が必要。検索器の置換だけで全投稿・完全リアルタイムを約束しない。

## 8. 当面の作業範囲

本体の追加実装・全面リファクタリング・プロバイダー拡張を止め、比較用の小さな実験ハーネスと評価標本を先に用意する。既存の未コミット変更は保持する。APIの認証・予算・提供元の利用条件が未確認の方式は、実測済みと扱わない。

この文書時点で実施したのは、既存実験とコードの再評価、代替サービス公式仕様の確認、比較方法の策定。方式間のライブ比較と本番負荷検証はまだ実施していない。現時点の推奨は仮説であり、その検証を次の作業とする。
