# エラーの画面から保存した Cookie を戻し続けない

日付: 2026-10-26

## 経緯

v2.49.0（TikTok の動画を字幕で読む）を本番に反映すると、本番だけ TikTok が毎回 HTTP 403 になった。同じイメージの候補（新しい DB）と、手元のサーバーでは読めた。

ブラウザは、開いたページの Cookie と localStorage をサイト（ホスト名）ごとに DB に保存し、次に同じサイトを開くときに戻す。本番の DB には、`www.tiktok.com` の WAF の札（`_waftokenid`・`waforigin_id` など 9 個。2026-10-25T20:44Z に保存）と、localStorage（46 個。TikTok の確認の仕組みの BDTuring・ARGUS など）が残っていた。以前に 403 を受けたときに保存した分を、毎回戻して開き、毎回 403 を受けていた。

確かめたこと:

- 本番と同じ krun・`slirp4netns` の新しいコンテナでは読めた（ネットワークの違いではない）。名前の解決も本番と同じだった。
- 反映前の本番の DB の控えの写しで起動したコンテナでは 403 になり、その写しから TikTok の行を消すと読めた。
- 本番の DB から TikTok の行（Cookie 2 行、localStorage 1 行）を消すと、本番でも読めた（ユーザーの判断）。

## 設計

- ブラウザで開いたページの本文のドキュメントが HTTP 400 以上を返したときは、そのページの Cookie と localStorage を保存しない。そのホストの保存していた分も消す（`dbDeleteTenantSession`）。
- 保存していた分を戻して開いたページがエラーだったときは、ブラウザの枠（`browserSemaphore`）を手放してから、保存分を戻さずに 1 回だけ開き直す。札が残っていても、その取得で読める。
- 呼び出し側が Cookie（ログイン状態）を渡した取得では、保存分を消すことも開き直すこともしない。エラーの原因が、渡された Cookie のこともあるため。

## 確認

- `src/browser_cookie_reset.test.ts`（本物の Chromium）: 札を持っていると 403 になるページを、札を戻さずに開き直して読むこと、札と localStorage が消えること、エラーの画面が付けた Cookie を保存しないこと。実装の前は 2 件とも失敗した。
