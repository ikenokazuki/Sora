# 検索語の URL と、読めないページの扱いの設計

日付: 2026-10-26

## 経緯

LibreChat の Agent が「この動画を要約して」に対し、`search_deep` を `query: "https://www.youtube.com/watch?v=5Jq35KcE8vI"`・`limit: 5`・`videos: 3` で呼んだ。結果は 3 件だった。

- 1 件目は指定の動画。Yahoo の Web 検索がこのページを返したので、字幕で読めた。ただし題名は Yahoo の検索結果のもので、英語に訳されていた（"Chatting and doing my makeup, plus my latest dilemma"）。
- 2・3 件目は関係ない動画（科学映像館の「窓ひらく」「あかり」）。Yahoo の動画検索に、URL そのものを検索語として渡したため。

検索語に URL が来るのは YouTube に限らない（X・TikTok・Instagram・画像・PDF など）。そこで、URL の種類に関係なく、検索語の URL はその URL を読む形にする（ユーザーの判断）。

## 調べたこと（2026-10-26、本番）

`search_deep` は検索語の URL を自分では読まない。URL の文字列を検索語にして、Web・X・動画を検索する。Yahoo に載っていない URL（X の投稿、画像、新しい動画など）は何も読めない。

`scrape` の読み方（URL の種類ごと）:

- YouTube の動画: 字幕と説明文（v2.47.0）。
- X の投稿: 本文と投稿者（0.3 秒）。
- ニコニコ動画: 題名と説明文（10.7 秒）。コメントと字幕は無い。
- Threads: 投稿の本文。Instagram: 題名が「Instagram」になり、画像の説明文などが本文になる。
- TikTok: Chrome の 403 のエラー画面（"You don't have authorization to view this page"）を、本文として返していた。
- 画像ファイル（jpg）: 画像のデータを文字として 1,500 字返し、本文として扱っていた。

TikTok（2026-10-26）:

- 静的な取得では、動画のページは WAF の確認画面（1.4KB）になる。
- Sora のブラウザ（`scrape` の通常の描画）では、開けることも 403 になることもある。本番では 403 になり、Chrome のエラー画面の文字が本文になっていた。その後の手元の確認では、確かめた 2 本とも開けた（約 12 秒、ページは約 50 万字）。
- 開けたページのデータ（`__UNIVERSAL_DATA_FOR_REHYDRATION__` の `webapp.video-detail`）には、説明文（`desc`）と、字幕の欄（`video.subtitleInfos`・`video.claInfo.captionInfos`）がある。確かめた 2 本は、どちらも字幕が無かった（`captionInfos: []`、`noCaptionReason: 3`）。
- 公式の oEmbed は、このサーバーからだと、動画については埋め込みのタグ（iframe）しか返さない（題名・投稿者も無い）。埋め込みのプレーヤーのページ（`/player/v1/<動画 ID>`）は空の枠で、データは開いたあとに TikTok のボット対策の署名（mssdk・argus）を付けて取りに行く。
- このため、TikTok の字幕は今回は扱わない。字幕のある動画で、ページのデータの字幕の URL を読めるかを、別に確かめる。

## 設計

### search_deep: 検索語の URL を読む

- 検索語に http(s) の URL があれば、検索をせずに、その URL を（最大 `limit` 件、検索語の順に）`scrape` と同じ方法で読む。YouTube は字幕、X は投稿、PDF は本文、ほかはページになる。
- Web 検索・X の検索（`includeRealtime`）・動画の検索（`videos`）・PRF・並べ替えはしない。URL を検索語にすると、どれも関係ない結果になるため。
- URL 以外の語は、読んだページから関係する部分（ハイライト）を選ぶのと、十分さの判定（`contextSufficiency`）に使う。URL だけなら、ハイライトは付けずに本文を返す。
- 題名は、読んだページの題名にする。読むときに、検索結果の題名の代わりとして URL を渡さない（X の読み取りは、渡された題名をそのまま投稿の題名にするため）。
- URL の切り出し（`splitQueryUrls`）: 空白・`<>"`・`|[]{}` と、全角の括弧・句読点・引用符（`（）「」『』【】〔〕、。，．“”‘’`）で止め、次の `http(s)://` の手前でも止める（`URL,URL`・`[URL](URL)`）。対になっていない `)` から後ろと、末尾の句読点（`.,;:!?'*~` と全角の `！？：；…`）は外す。`'` と、対になった `()`（`/wiki/Foo_(bar)`）と、日本語の入った URL（`/wiki/君と見るそら`）は切らない。ホスト名に `.` が無いもの（`https://とは`・`http://localhost:3000`）は URL として扱わず、今までどおり検索する。
- URL を読めなかった（取得の失敗・エラーの画面）ときも、検索には戻らない。URL を検索語にした検索は、関係ない結果になるため。
- 既知の限界: 空白なしで日本語の語が続く URL（「URLを要約」）は、語まで URL に入る。末尾が `!` の URL（`…サンシャイン!!`）は、`!` が外れる。

### search_video: 検索語が URL なら検索しない

- Yahoo の動画検索に URL を渡すと関係ない動画が返るので、検索しない。`items: []` と、`message`（「URL の動画は get_youtube_transcript（YouTube）か scrape で読む」）を返す。

### search_deep の YouTube の題名

- Web 検索の結果が YouTube の動画なら、題名を YouTube の題名（字幕を取るときに得たもの）にする。Yahoo は YouTube の題名を英語に訳して返すことがある。

### scrape: 画像・音声・動画のファイル

- `Content-Type` が `image/`・`audio/`・`video/` なら、中身を読まない。種類と大きさだけを返し、「Sora は中身を読めない」と書く（`contentStatus: "unavailable"`。本文を読めないので、説明文だけのページの `metadata_only` とは分ける）。HTTP の状態が 400 以上なら、それも書く（404 のときに代わりの画像を返すサイトがある）。
- 上限（30MB）を超えるファイルは、取得の部品（`fetchWithSafeRedirects`）が本体を読まずに断る。このときの例外に `Content-Type` と大きさを付け、動画・音声のファイルなら、取得の失敗ではなく同じ形の結果にする。断るときは、読まない本体を捨てる（受け取り続けない）。
- 既知の限界: `application/octet-stream` で返る画像は、今までどおり文字として読む。

### scrape: エラーのページ

- HTTP の状態が 400 以上のページは、`contentStatus` を `unavailable` にし、本文の先頭に HTTP の状態を書く。静的な取得とブラウザの両方で行う。ブラウザでは、本文のドキュメントの応答の状態を記録する（リダイレクトの後の最後のもの。iframe は見ない）。
- 仕上げ（`finalizeScrapeResult`）の後に当て、エラー画面の文から作ったハイライトを外す。`responseMode: "evidence"` はハイライトのある結果の本文を省くので、ハイライトが残ると、HTTP の状態の注記が消えてエラー画面の文だけが根拠に見えるため。
- TikTok がブラウザでも 403 を返したときは、これで「読めない」になる。`search_deep` は `unavailable` のページを根拠に数えず、次の候補を読む。並べ替えの後、`unavailable` のページは、検索語によく合っていても読めたページの後ろに回す（エラー画面には検索語がそのまま載っていることが多く、点数を下げるだけでは上に残った）。
- 既知の限界: 404 を返しつつ JavaScript で本文を出すページ（SPA の 404 フォールバック）も `unavailable` になる。

### 十分さの判定

- `contextSufficiency` は、`unavailable` のページを証拠に数えない（取得失敗と同じ）。画像のファイルや、403 で読めなかったページだけを読んだときは `no-usable-content` になる。説明文だけのページ（`metadata_only`。字幕の無い YouTube など）は、今までどおり数える。

## 対象外

- TikTok の字幕（上記。字幕のある動画で別に確かめる）。
- 短縮 URL（t.co など）を転送先の URL で判定すること。今は t.co 経由の YouTube を字幕で読まない。
- Instagram などの投稿を `fetch_social_post` の仕組みで読むこと。
- 検索語に URL と語の両方があるときに、語で検索も行うこと。

## 確認

- `src/url_in_query.test.ts`: URL の切り出し、`search_deep` が検索語の URL を渡された順に読み、Web・X・動画を検索しないこと、題名（YouTube・X）、ハイライトに語を使うこと、エラーのページを読めたページの後ろに回すこと、十分さの判定（説明文だけのページは数える）、`search_video` の `message`、画像のファイル（エラーの状態つき・上限を超える動画）、エラーのページ（静的な取得とブラウザ、本文の無い 403）。
- 本番の形の確認（手元のサーバー、2026-10-26）は PR に書いた。
- 別のエージェントのレビュー（10 件）のうち、2 件は直さなかった。絞り込みを付けたときに 20 件までになり、`page` が 20 件単位なのは、同梱の MCP（1 ページ 20 件・`limit` は 1〜20）と同じ。キャッシュの版は上げなかった。古い結果は最長 30 分で消え、版を上げると反映の直後に Yahoo などへの問い合わせが増えるため。
