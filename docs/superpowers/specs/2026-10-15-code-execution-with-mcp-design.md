# 「MCP でコード実行」の考えを取り入れる 設計

日付: 2026-10-15
状態: 設計文書（レビュー待ち）。ここに記載した機能は未実装です。
参照: Anthropic Engineering「Code execution with MCP」（https://www.anthropic.com/engineering/code-execution-with-mcp）

## 1. 目的と範囲

記事の主張は「ツール定義と中間結果がコンテキストを圧迫するので、ツールをコードから呼べる API として見せ、絞り込みや連鎖をコード側で行う」ことです。Sora は MCP サーバーなので、取り入れられるのは次の 2 点です。

1. **サーバーの中で完結する範囲（A）**: ツール定義の段階的開示を仕上げ、応答の絞り込みを共通化し、文脈の大きさを測って守る。
2. **コード側から使うための API（B）**: コード実行環境を持つエージェントが、Sora を型付きの関数として呼べる TypeScript クライアントを、既存の REST と OpenAPI から生成して公開する。

含めないもの:

- Sora 自身がコードを実行するツール（サンドボックスを持つ案）。記事のサンドボックスは、**エージェント側（クライアント）の実行環境**の話で、MCP サーバーが持つものではない。匿名公開のサーバーに持たせると攻撃面と資源管理の負担だけが増える。
- 個人情報のトークン化。MCP クライアント側の機能。
- 削除済みの CLI・スキル・プラグイン（コミット da52230、MCP のみの構成）の復活。B は CLI ではなく、REST を呼ぶ型付き関数の生成物で、サーバーの構成は変えない。

## 2. 記事との対応と現状（2026-10-15 実測）

| 記事の考え | Sora の現状 |
|---|---|
| ツール定義を必要なときだけ読む | 遅延読み込み（`SORA_DEFER_TOOLS`）と `search_tools` で実現済み |
| 初期のツール定義を小さく | 既定の `tools/list` は 14 ツール、25,141 文字（説明 3,473 文字、引数のスキーマ約 20,000 文字。`scrape` 5,660、`search_deep` 5,226）。全ツールだと 50 ツール |
| `search_tools` の詳細度（名前のみ／説明付き／スキーマ全体） | 未対応。検索すると必ず有効化し、スキーマは見せない（応答は 470 文字） |
| 中間結果をモデルに通さない | ツールごとにばらばら（`limit`、`maxTotalChars`、`verbose`、`responseMode`）。共通の絞り込みは無い |
| ツールをコード API として公開 | REST と OpenAPI（`/openapi.json`）はあるが、型付きの関数としては公開していない |
| 数字で効果を確かめる | 文脈の大きさを測るテストが無い（`instructions` の文字数上限だけ） |

## 3. A: サーバーの中で完結する範囲

### 3.1 `search_tools` の詳細度

- 引数を足す: `detail?: 'names' | 'summary' | 'schema'`（既定 `summary` = 現在の出力）、`activate?: boolean`（既定 `true` = 現在の動作）。
- `names`: 名前・カテゴリ・タグ（【…】）だけ。`summary`: 現在の形式（説明の先頭 80 文字）。`schema`: 一致したツールの入力スキーマ（JSON）を含める。一度に返すのは最大 8 ツール（カテゴリ全体に当たったときの暴発を防ぐ）。超えた分は件数を示す。
- `activate: false` なら、セッションの有効化もツール一覧の変更通知もしない。探すだけで状態を変えない。
- ツール一覧のカタログ（`ToolCatalogEntry`）に入力スキーマを持たせる。実装は `src/mcp.ts` の `registerTool` に集約し、SDK が `tools/list` に出す変換と同じものを使う（食い違いを防ぐ）。

### 3.2 初期のツール定義を軽くする

- 既定の `tools/list`（14 ツール）の合計を、**25,141 文字から 18,000 文字以下**にする。
- 手段: 引数の説明が 150 文字を超えるものの散文を短くし、長い使い分けの説明は `search_tools` の `detail: "schema"` で読めるようにする。型・列挙値・範囲・既定値は削らない。
- 守ること: 説明を削って使い方を誤らせない。短縮の前後で `scrape`・`search_deep` などの引数の意味が変わっていないことを、レビューと既存のテストで確かめる。精度の評価（モデルが正しく呼べるか）は自動化されていないので、**範囲を最も重い引数に限る**。

### 3.3 応答の絞り込み `fields`

- 結果の一覧を返すツールに、任意の `fields: string[]` を足す: `search_web`、`search_news`、`search_realtime`、`search_poi`、`search_deep`（結果ごとの項目）。省略時は従来どおり。
- 許される項目は、そのツールの結果 1 件のスキーマ（`types.ts`）のキーに限る。未知の項目は 400（REST）／入力エラー（MCP）。
- 絞り込みは**キャッシュの後**に行う（キャッシュは完全な結果を持ち、`fields` は返す形だけを変える）。共通の関数 `projectFields(items, fields, allowed)` を 1 か所に置く。
- MCP と REST の入力スキーマ（`types.ts`）に同じ定義を使う。OpenAPI にも出る。

### 3.4 文脈の大きさを測り、守る

- `scripts/measure-context.ts`: 既定の `tools/list` の文字数、全ツールの文字数、`search_tools` の各詳細度の応答の文字数、`fields` あり・なしの代表的な応答の文字数を JSON で出す。
- `src/context_budget.test.ts`: 既定の `tools/list` ≤ 18,000 文字、`search_tools` の `names` 応答 ≤ 1,200 文字、など、しきい値を超えたら落ちる（`instructions` の 8,500 文字の検査と同じ考え方）。しきい値は実装時の実測に余裕を足して決める。

## 4. B: コード側から使うための TypeScript クライアント

エージェントが「ファイルを探して、必要な関数だけ読み、コードで連鎖・絞り込みする」ための生成物。REST を呼ぶので、サーバーの構成は変わらない。

### 4.1 生成物（リポジトリの `client/`）

```
client/
  README.md                  使い方（環境変数、例）
  catalog.json               ツール名・カテゴリ・1 行の説明・キーワード・REST の対応（探すための索引）
  runtime.ts                 callSora(): fetch、SORA_URL、SORA_API_KEY、タイムアウト、エラー（code・retryable）
  search.ts                  searchTools(query, detail): catalog.json を検索（名前／説明／スキーマの場所）
  servers/sora/
    <tool>.ts                型（入力・出力）と、関数 1 つ。JSDoc に説明。callSora を呼ぶだけ
    index.ts                 全関数の再公開
```

- 対象は `REST_MAP`（`scripts/tool-health/catalog.ts`）にある、REST に対応するツール。`search_tools` は含めず、`client/search.ts` が代わりをする。
- 型は OpenAPI のリクエストスキーマと 200 応答スキーマから作る（小さな変換: オブジェクト、配列、列挙、null 許容、任意項目。解釈できないものは `unknown`）。`fields` は入力の型に含まれる。
- 関数の名前はツール名のキャメルケース（`searchPoi` など）。入力の検証はサーバーが行う（クライアントで二重に持たない）。

### 4.2 公開

- 生成物はリポジトリにコミットし、`Containerfile` で `/app/client` にコピーする。
- サーバーが読み取り専用で配る: `GET /client`（ファイルの一覧）、`GET /client/<path>`（`client/` の下だけ。`..` を含む・一覧に無いパスは 404）。コード実行環境が `curl` で必要なファイルだけ取れる。認証は他の REST と同じ。
- OpenAPI への影響: 新しい 2 つの GET を `docs_contract` の対象に足す。

### 4.3 食い違いの防止

- `scripts/gen-client.ts` が生成し、テスト `client_sync.test.ts` が「いま生成したものとコミット済みの `client/` が一致する」ことを確かめる（OpenAPI やツールの定義を変えて、生成を忘れると落ちる）。
- 生成した型の使い方をテストで確かめる: 型検査（`tsc`）が `client/` を含み、`callSora` を偽の fetch に差し替えて、代表的なツール 5〜6 個の呼び出しの形（メソッド、パス、本文、エラーの扱い）を検証する。

## 6. 後段: コードの整理

改修の後に、**動きを変えない**整理だけを行う。範囲はコード（ドキュメント・ブランチ・CI は対象外）。

- `src/mcp.ts`（約 2,700 行）を、ツールの登録をカテゴリごとのファイルに分ける（登録の順序とツール名は変えない）。
- 使われていないコード・依存の削除（`noUnusedLocals` は有効。未使用の export と依存を調べる）。
- `any` の削減（現在 src 全体で約 380 か所。MCP の入口と REST の入口を優先）。
- 重複の統合、命名・コメントの統一（周囲の書き方に合わせる）。
- 守ること: 全テスト、`schema:notation`、型検査、lint、実 API 検査（手元の候補イメージ）が通ること。**`tools/list` と OpenAPI の出力を整理の前後で保存して比べ**、意図しない差が無いことを確かめる。

## 7. 完了条件

- A: 既定の `tools/list` が 18,000 文字以下（実測を `docs/code-execution.md` に記録）。`search_tools` の 3 つの詳細度と `activate: false` が動く。`fields` が 5 つのツールで MCP と REST の両方で動く。
- B: `client/` が生成され、一致テストと型検査が通る。サーバーが `/client` を配る。
- 既存のテスト・実 API 検査が変わらず通る（応答の既定の形は変わらない）。
- 整理の前後で `tools/list` と OpenAPI に差が無い。

## 8. リスクと対策

- **定義の短縮でモデルが誤って呼ぶ**: 短縮は説明の散文だけ、範囲は最も重い引数に限る。型・列挙・範囲は残す。効果と副作用を実測で記録し、悪化したら元に戻せるよう、短縮は別コミットにする。
- **生成物の食い違い**: 一致テストで防ぐ。
- **`/client` の配布面**: 読み取り専用、`client/` の下の一覧にあるファイルだけ、パス検査あり。ソースコードや設定は配らない。
- **`fields` の誤用**: 未知の項目は拒否する。既定は変えないので、既存の利用者に影響しない。
- **整理で動きが変わる**: 前後の比較（`tools/list`、OpenAPI）と全テストで検出する。
