# 「MCP でコード実行」の考えを取り入れる 設計

日付: 2026-10-15（同日に書き直し。初版は `fields` と定義の短縮目標を含んでいたが、実測で採らないことにした。§7）
状態: 設計文書（レビュー待ち）。ここに記載した機能は未実装です。
参照: Anthropic Engineering「Code execution with MCP」（https://www.anthropic.com/engineering/code-execution-with-mcp）

## 1. 目的と範囲

記事の主張は「ツール定義と中間結果がコンテキストを圧迫するので、ツールをコードから呼べる API として見せ、絞り込みや連鎖をコード側で行う」ことです。Sora は MCP サーバーなので、取り入れられるのは次の 2 点です。

1. **A: 段階的開示の仕上げと、文脈の大きさの計測**（サーバーの中で完結）。
2. **B: コード側から使うための TypeScript クライアント**。コード実行環境を持つエージェントが、Sora を型付きの関数として呼べるように、既存の REST と OpenAPI から生成して公開する。**記事の効果（コード側で絞って、モデルに見せる量を減らす）の本体はこれ。**

その後に、**動きを変えないコードの整理**を行う（§6）。

含めないもの:

- Sora 自身がコードを実行するツール。記事のサンドボックスは**エージェント側（クライアント）の実行環境**の話で、MCP サーバーが持つものではない。匿名公開のサーバーに持たせると攻撃面と資源管理の負担だけが増える。
- 個人情報のトークン化（MCP クライアント側の機能）。
- 削除済みの CLI・スキル・プラグイン（コミット da52230、MCP のみの構成）の復活。B は REST を呼ぶ型付き関数の生成物で、サーバーの構成は変えない。

## 2. 記事との対応と現状（2026-10-15 実測）

実測は、実際のクライアントが受け取る HTTP の経路（`POST /mcp`）で行った。

| 記事の考え | Sora の現状 |
|---|---|
| ツール定義を必要なときだけ読む | 遅延読み込み（`SORA_DEFER_TOOLS`）と `search_tools` で実現済み。既定の `tools/list` は 14 ツール 24,457 文字。全ツールだと 50 ツール 59,988 文字（本番は後者の設定。ホスト側のツール検索で実際にモデルへ渡る量は減る） |
| `search_tools` の詳細度（名前のみ／説明付き／スキーマ全体） | 未対応。検索すると必ず有効化し、スキーマは見せない（応答は約 470 文字） |
| 中間結果をモデルに通さない | モデルが直接呼ぶ経路では、ツールごとの既存の手段がある（`limit`、`maxTotalChars`、`verbose`、`responseMode: "evidence"`）。**コードで絞る経路が無い** |
| ツールをコード API として公開 | REST と OpenAPI はあるが、型付きの関数としては公開していない。49/50 ツールに REST がある（無いのは `search_tools` のみ） |
| 数字で効果を確かめる | 文脈の大きさを測るテストが無い（`instructions` の 8,500 文字の上限だけ。現在 8,494） |

応答の大きさ（実測）: `search_web` 3.8K 文字、`search_news` 6.5K、`search_poi` 3.5K、`search_realtime` 4.7K、`search_deep`（3 件）**43.2K**（本文 `markdown` が 80%）。コードで絞れば、43K の応答を数百文字にして見せられる。

## 3. A: サーバーの中で完結する範囲

### 3.1 `search_tools` の詳細度

- 引数を足す: `detail?: 'names' | 'summary' | 'schema'`（既定 `summary` = 現在の出力）、`activate?: boolean`（既定 `true` = 現在の動作）。
- `names`: 名前・カテゴリ・タグ（【…】）だけ。`summary`: 現在の形式（説明の先頭 80 文字）。`schema`: 一致したツールの入力スキーマ（JSON）を含める。
- `schema` は、一致が多いときの暴発を防ぐため、最大 8 ツール・合計 20,000 文字までにして、超えた分は件数と「検索語を絞る」案内を返す。
- `activate: false` なら、セッションの有効化もツール一覧の変更通知もしない。探すだけで状態を変えない。
- ツールのカタログ（`ToolCatalogEntry`）に入力スキーマを持たせる。形は `tools/list` が出すものと同じにする（`tools/list` の整形関数を共有して、食い違いを防ぐ）。
- 既存の動作（引数なしの呼び出し）は変えない。`instructions`（上限 8,500 文字、現在 8,494）は変えない。

### 3.2 文脈の大きさの計測と回帰ガード

- `scripts/measure-context.ts`: HTTP の経路で、既定の `tools/list` と全ツールの `tools/list` の文字数、`instructions` の文字数、`search_tools` の各詳細度の応答の文字数を JSON で出す。
- `src/context_budget.test.ts`: 上の値が**現在の実測に小さな余裕を足したしきい値**を超えたら落ちる。ツールや引数の説明を増やすときに、意識して上げる。しきい値は実装時の実測で決める。
- 定義の短縮はしない（§7）。実装時に、同じ文言が複数の引数・ツールで繰り返されている箇所を洗い出し、**意味を変えずに共通化できるものだけ**を短くする。数値目標は置かず、効果は実測で記録する。

## 4. B: コード側から使うための TypeScript クライアント

エージェントが「ファイルを探して、必要な関数だけ読み、コードで連鎖・絞り込みする」ための生成物。REST を呼ぶので、サーバーの構成は変わらない。

### 4.1 生成物（リポジトリの `client/`）

```
client/
  README.md                  使い方（環境変数、例）
  manifest.json              配布するファイルの一覧（パスと大きさ）
  catalog.json               ツール名・カテゴリ・1 行の説明・キーワード・REST の対応（探すための索引）
  runtime.ts                 callSora(): fetch、SORA_URL、SORA_API_KEY、タイムアウト、エラー（code・status・retryable）
  search.ts                  searchTools(query, detail): catalog.json を検索（名前／説明／ファイルの場所）
  servers/sora/
    <tool>.ts                型（入力・出力）と、関数 1 つ。JSDoc に説明。callSora を呼ぶだけ
    index.ts                 全関数の再公開
```

- 対象は `REST_MAP`（`scripts/tool-health/catalog.ts`）にある 49 ツール。`search_tools` は含めず、`client/search.ts` が代わりをする。
- 型は OpenAPI（`generateOpenApiDocument()`）のリクエストスキーマと 200 応答スキーマから作る。小さな変換で、オブジェクト・配列・列挙・null 許容・任意項目を扱う。解釈できないものは `unknown`。
- GET のツールは、入力を query にし、パスパラメータ（REST の `:contextId` と OpenAPI の `{contextId}` の書き方の違いは生成側で吸収する）を置き換える。POST は JSON の本文。
- 実測で見つけた欠け: `watch_list`（入力なし）は引数なしの関数にする。国別コンテキストの 3 ツールは、パスの書き方の違いで OpenAPI に引けなかったので、上の吸収で解決する。解決できないツールがあれば、生成を失敗させて気づけるようにする（黙って落とさない）。
- 関数の名前はツール名のキャメルケース（`searchPoi` など）。入力の検証はサーバーが行う（クライアントで二重に持たない）。エラーは REST の形（`error`・`code`・`status`・`retryable`）をそのまま持つ。

### 4.2 公開

- 生成物はリポジトリにコミットし、`Containerfile` で `/app/client` にコピーする。
- サーバーが読み取り専用で配る: `GET /client`（`manifest.json` の内容）、`GET /client/<path>`（`manifest.json` にあるファイルだけ。`..` を含む・一覧に無いパスは 404）。コード実行環境が `curl` で必要なファイルだけ取れる。認証は他の REST と同じ。ソースコードや設定は配らない。
- `/client` を `docs_contract` と OpenAPI の対象に足す。

### 4.3 食い違いの防止

- `scripts/gen-client.ts` が生成し、テスト `client_sync.test.ts` が「いま生成したものとコミット済みの `client/` が一致する」ことを確かめる（OpenAPI やツールの定義を変えて、生成を忘れると落ちる）。
- `client/` を型検査の対象（`tsc`）に含める。`callSora` を偽の fetch に差し替えて、代表的なツール 5〜6 個の呼び出しの形（メソッド、パス、query／本文、エラーの扱い）を検証する。

### 4.4 効果の実測

`search_deep` の応答（実測 43,184 文字）を、コードで絞った場合にモデルへ見せる量（タイトル・URL・要点だけにして数百文字）を、同じ質問で実測し、`docs/code-execution.md` に載せる。直接 MCP で呼んだ場合と、`responseMode: "evidence"` の場合も並べる。

## 5. 文書

`docs/code-execution.md` を足す: 記事の考えと Sora の対応、`client/` の使い方（取得の `curl`、環境変数、TypeScript の例）、REST と OpenAPI を使った絞り込み・連鎖・ポーリングの例、§3.2 と §4.4 の実測値。README の該当節と `docs/operations` にリンクする。

## 6. 後段: コードの整理

改修の後に、**動きを変えない**整理だけを行う。範囲はコード（ドキュメント・ブランチ・CI は対象外）。

- `src/mcp.ts`（約 2,700 行）を、ツールの登録をカテゴリごとのファイルに分ける。登録の順序、ツール名、説明は変えない。
- 使われていないコード・依存の削除。`noUnusedLocals` は有効なので、未使用の export と依存を調べる（調べるツールは一時的に実行し、依存には加えない）。
- `any` の削減（テストを除く src で約 280 か所。`mcp.ts` と `routes/` は計 5 か所でほぼ無く、多いのは `services/yahoo.ts` 85、`scraper.ts` 49、`html_parser.ts` 23、`services/life.ts` 19、`browser_stealth.ts` 14）。この上位のファイルを優先し、外部の応答の解析は `unknown` と絞り込みに置き換える。件数ではなく、正当な理由の無い `any` を無くすことを目標にし、挙動を変えないことを既存のテストで確かめる。
- 重複の統合、命名・コメントの統一（周囲の書き方に合わせる）。
- 守ること: 全テスト、`schema:notation`、型検査、lint、実 API 検査（手元の候補イメージ）が通ること。**整理の前後で、HTTP の `tools/list`（既定と全ツール）と OpenAPI の出力を保存して比べ、差が無いこと**を確かめる。

## 7. 検討して採らなかったもの

- **応答の絞り込み `fields`（初版にあった）**: 実測で、対象の 4 ツールの応答は 3.5K〜6.5K 文字しかなく、絞っても数百〜2,000 文字しか減らない。大きいのは `search_deep`（43K、本文が 80%）で、既存の `maxTotalChars` と `responseMode: "evidence"` で対処できる。`search_poi` は応答の 42% が `attributions`（出典）で、出典の表示は利用条件で必須なので、`fields` で落とせると利用条件違反を誘発する。記事の趣旨（絞り込みはコード側で行う）にも反し、API の面（MCP・REST・OpenAPI・テスト）を増やすだけになる。コードで絞る経路は B が担う。
- **初期の定義を 18,000 文字以下にする目標（初版にあった）**: 実測で、HTTP の既定は 24,457 文字（14 ツール）で、短縮で減らせるのは数千文字。一方、モデルが引数を誤って呼ぶリスクを自動で評価できない。本番はホスト側のツール検索でさらに絞られる。回帰ガード（§3.2）と、意味を変えない重複の整理に縮めた。
- **Sora によるコード実行**（サンドボックス付きのツール）: §1。
- **CLI・スキルの復活**: §1。
- **GitHub の生ファイルでのクライアント配布**: 外部依存になり、セルフホストの版と API が食い違う。サーバーが自分の版のクライアントを配る方が確実。

## 9. リスクと対策

- **生成物の食い違い**: 一致テストで防ぐ。
- **`/client` の配布面**: 読み取り専用、`manifest.json` にあるファイルだけ、パス検査あり、認証は他の REST と同じ。ソースコードや設定は配らない。
- **型の変換が不十分**: 解釈できない型は `unknown` にし、生成したクライアントを型検査に含める。解決できないツールは生成を失敗させる。
- **`search_tools` の `schema` が大きい**: 最大 8 ツール・20,000 文字で打ち切る。
- **整理で動きが変わる**: 前後の比較（`tools/list`、OpenAPI）と全テスト、実 API 検査で検出する。分割は機械的な移動に限り、コミットを小さく分ける。
- **`context_budget.test.ts` が開発の邪魔になる**: しきい値に余裕を持たせ、上げ方（意識して更新する）を文書に書く。

## 10. 範囲外

- 個人情報のトークン化、クライアント側の状態の永続化（`workspace/`・`skills/`）。
- 他言語のクライアント（OpenAPI から各自生成できる）。
- モデルが正しく呼べるかの自動評価。
- `search_web` など既存の応答の形の変更（重複する項目の削除など）。
