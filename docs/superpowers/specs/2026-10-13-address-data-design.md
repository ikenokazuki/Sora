# 住所データ基盤と住所ツールの設計

作成日: 2026-10-13。対象: `/path/to/sora`、v2.38.0、基準コミット `de3d5a9`。
状態: 設計文書。設計の内容は会話で承認済みで、本書はレビュー待ちです。ここに記載した機能は未実装です。
実装手順: 実装計画を `docs/superpowers/plans/` に別に作成します。

## 1. 達成すること

Sora に次の住所の機能を追加します。

1. 郵便番号から住所候補を特定する。住所から郵便番号を引く（逆引き）。
2. 与えられた住所を、番地・号まで正規化する。
3. 緯度経度から住所を引く（逆ジオコーディング）。
4. 郵便番号・住所・緯度経度を突き合わせる。住所どうしを名寄せする。
5. 既存の `get_elevation` と `search_poi` が使う住所の解決を、ローカルのデータに寄せる。

守る制約は次の4つです。

- **保守コストを増やさない。** 参考にした Geolonia の normalize-japanese-addresses の考え方に従い、アルゴリズムとデータを分けて、アルゴリズムは保守されている OSS に任せます。
- **住所と郵便番号の解決は第三者の API に依存しない。** 一次データを Sora が自分で取得して持ちます。
- **配送で使えるよう、正確さを損なわない。** 確実でないものは、確実でないと出力で示します。
- **この機能を使わないユーザーに負担をかけない。** 巨大なデータは、使う範囲だけ処理します。

## 2. 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 正規化の細かさ | 番地・号（level 8）まで。住居表示に加えて地番も含める | 用途が配送で、住居表示でない町が大半（町字の 91.6%）のため |
| 郵便番号の範囲 | 通常の郵便番号（KEN_ALL）に加えて、大口事業所の個別郵便番号（JIGYOSYO）も含める | 法人宛ての住所に必要なため |
| 住所以外の地名 | 駅名・ランドマーク・通称は従来どおり外部（Nominatim → 国土地理院）で解決する | ローカルの住所データには無く、別のデータを足す保守に見合わないため |
| ツール | 新規は3つ（`search_postal_code`、`normalize_address`、`reverse_geocode`）。突き合わせは `normalize_address` に同居させる | 専用ツールを増やすと登録箇所と保守が増えるため |
| 既定の動作 | `lazy`（使われたときだけ取得する）。事前取得と `eager` は運用者の選択 | 使わないユーザーに何も起こさないため |
| 構築の実行場所 | Sora 本体とは別の子プロセス（コンテナ内）。ホスト側のタイマー（NixOS の変更）は使わない | 運用の変更を要求しないため |

## 3. 設計の要点

1. **結合キーは `lg_code`（6桁）+ `machiaza_id`（ABR の町字ID）。** 町字、住居表示、地番、郵便番号、逆引きの索引が同じキーで結ばれ、突き合わせはキーの比較になります。
2. **アルゴリズムは `@geolonia/normalize-japanese-addresses` 3.1.3（MIT）に任せ、データだけ自前化する。** ライブラリはデータの読み取りを外から差し替えられるので、自前のデータを読ませます。
3. **使った分だけ取得する（pay-as-you-go）。** 起動時の処理、常駐タイマー、ダウンロードは一切ありません。データは市区町村単位で、その市区町村が初めて使われたときに取得・構築します。
4. **構築は別プロセス・低優先度・1件ずつ。** 本体のイベントループを塞ぎません。
5. **更新は使われたときの再確認。** 古いデータで即答し、作り直しは裏で行います。

## 4. データ元と利用条件

### 4.1 デジタル庁 アドレス・ベース・レジストリ（ABR）

`https://data.address-br.digital.go.jp/` 配下の静的ファイル（`.csv.zip`）で、HEAD で ETag と Last-Modified が取れます。全国・都道府県・市区町村の3種の粒度があります。

| 用途 | URL（`…` は `https://data.address-br.digital.go.jp/`） |
|---|---|
| 都道府県・市区町村の一覧 | `…mt_pref/mt_pref_all`、`…mt_pref_pos/mt_pref_pos_all`、`…mt_city/mt_city_all`、`…mt_city_pos/mt_city_pos_all`（合計約 75KB） |
| 町字（市区町村） | `…mt_town/city/mt_town_city{lg_code}`、`…mt_town_pos/city/mt_town_pos_city{lg_code}` |
| 町字（都道府県。索引用） | `…mt_town/pref/mt_town_pref{NN}`、`…mt_town_pos/pref/mt_town_pos_pref{NN}`（47県で 11.0MB と 4.1MB） |
| 住居表示（市区町村） | `…mt_rsdtdsp_rsdt/city/mt_rsdtdsp_rsdt_city{lg_code}`、`…mt_rsdtdsp_rsdt_pos/city/mt_rsdtdsp_rsdt_pos_city{lg_code}` |
| 地番（市区町村） | `…mt_parcel/city/mt_parcel_city{lg_code}`、`…mt_parcel_pos/city/mt_parcel_pos_city{lg_code}` |

存在しない組み合わせは 404 です（住居表示の無い市区町村、政令市の親行など）。市区町村単位のサイズ（zip）の例:

| 市区町村 | 町字 | 町字位置 | 住居表示 | 住居表示位置 | 地番 | 地番位置 |
|---|---|---|---|---|---|---|
| 千代田区 | 2.7KB | 2.0KB | 43KB | 113KB | — | — |
| 世田谷区 | 3.8KB | 4.2KB | 1.1MB | 2.9MB | 1.9MB | 0.2MB |
| 札幌市中央区 | 10KB | 13KB | 360KB | 953KB | — | — |
| 福知山市（262013） | 7.0KB | 6.5KB | なし | なし | 約2.5MB | 約2.4MB |

全国一括にすると、住居表示が約 480MB、地番が約 10GB（推定）になります。市区町村単位なら、1か所あたり多くが 10MB 以下です。

配信の CDN は国外 IP からの接続を拒否します（Geolonia の生成器のコメントによる）。日本のホストからは取得できることを確認しています。国外の運用者は取得できません（6.4 のエラーを返す）。

利用条件は公共データ利用規約 1.0（PDL1.0）で、出典の記載と、加工した旨・加工者の明記が必要です。地番マスターは、登記所備付地図データ利用規約（G空間情報センター）にも従います。

### 4.2 日本郵便 郵便番号データ

ダウンロードの URL は 2026 年に移動しました（旧 zip は 404、旧ページは 301 で新ページへ転送）。そのため、ページを GET して zip へのリンクを解決し、失敗したら既知の直 URL を使います。

| データ | 直 URL（`…` は `https://www.post.japanpost.jp/service/search/zipcode/download/`） | 内容 |
|---|---|---|
| KEN_ALL | `…utf/zip/utf_ken_all.zip`（旧ページ `https://www.post.japanpost.jp/zipcode/dl/utf-zip.html`） | 2.1MB、UTF-8、124,526 行 |
| JIGYOSYO | `…office/zip/jigyosyo.zip`（旧ページ `https://www.post.japanpost.jp/zipcode/dl/jigyosyo/index-zip.html`） | 776KB、Shift_JIS、22,424 行、13 列 |

KEN_ALL は月末に更新されます（2026-09-30）。条件は「著作権を主張しません。自由に配布していただいて結構です」で、出典の表示は不要です。

### 4.3 出典の文言

出力の `attribution` に入れます。

- ABR を使った結果: 「『アドレス・ベース・レジストリ』（デジタル庁）（https://dataset.address-br.digital.go.jp/）を加工して作成（加工: Sora）」
- 地番を使った結果は、上に加えて登記所備付地図データの出典。文言は、実装の最初に規約の本文を確認して確定する（未確認事項 1）。
- 郵便番号: 任意で「日本郵便株式会社 郵便番号データ」を付記する。

### 4.4 使わないデータ

- ABR の「町字・郵便番号変換表」（`abr_post_code.zip`）: 公開の一覧に出ておらず、直 URL が見つからなかったため使いません。KEN_ALL の町域名を ABR の町字に名前で結びつけます（5.4）。
- MLIT 位置参照情報（Geolonia の生成器は補完に使う）、HUB 検索 API、proj4、地番のポリゴン形状（筆界）。

## 5. データ基盤

### 5.1 保存先と版

保存先は `SORA_ADDRESS_DIR`（既定は `dirname(getDatabasePath())/address`、本番は既存ボリューム内の `/data/address`）です。

```
address/
  status.json                  各データの署名・確認日時・最終利用日時・サイズ・最終エラー
  lock                         状態ファイルの更新の排他と、同じデータを作る重複ジョブの防止（pid と時刻。古いものは失効）
  master/<ver>/ja.json         全国マスターから作る都道府県・市区町村の一覧
  postal/<ver>/postal.sqlite   郵便番号の行
  index/<ver>/geo.sqlite       逆ジオコーディング用の町字点の索引
  city/<lg_code>/<ver>/        town.json、住居表示.txt、地番.txt（あるものだけ）、範囲表
```

差し替えは、一時ディレクトリで作って検証してから `<ver>` を作り、`status.json` を一時ファイルから rename して行います。旧版は直近1つを残し、読み取り中のファイルが消えないようにします。

### 5.2 取得の単位とタイミング

| 単位 | 取得元 | 目安のサイズ | 取得のきっかけ |
|---|---|---|---|
| 全国マスター | 都道府県・市区町村マスター | 約 75KB | 住所ツールの初回使用 |
| 郵便番号 | KEN_ALL、JIGYOSYO | 約 2.9MB | 郵便番号を使う機能の初回使用 |
| 町字の点の索引 | 47県の町字と位置参照 | 約 15MB | `reverse_geocode` の初回使用 |
| 市区町村の町字（段A） | 町字、町字位置 | 数KB〜数十KB | その市区町村の住所が使われたとき |
| 市区町村の番号（段B） | 住居表示・地番、それぞれの位置参照 | 数十KB〜十数MB | 同上（段Aに続けて） |

### 5.3 仮想ファイル

ライブラリが住所を解釈すると、必要な1市区町村分の `ja/<都道府県>/<市区町村>.json` と、必要なら `…-住居表示.txt` / `…-地番.txt` の範囲だけを読みます。Node 版が公開している `requestHandlers.file` を差し替えて、この読み取りを自前の関数に任せます（`normalize('東京都千代田区千代田1-1')` で、読み取りが `ja.json` と `ja/東京都/千代田区.json` の2回だけ呼ばれることを確認済み）。

- 関数は、読み取りの対象を `address/` の中へ対応づけます。市区町村が未取得なら、構築を依頼して待ちます（6.4 の待ち時間まで）。
- ライブラリが町の JSON をメモリに保持するため、同じ版の `town.json` と txt の組を使い続けるよう、モジュールのインスタンスごとに「配った版」を記憶します。
- 配った版が更新・破棄されたとき、および24時間ごとに、モジュールを作り直します。ライブラリ内の無制限のキャッシュの肥大化と、データの差し替えへの対策です。Bun では `?query` を付けた import は同じインスタンスのままなので使えず、`require.cache` から消してから import し直します（実測で、別のインスタンスになり、古いインスタンスは回収されます）。消して読むまでは1件ずつ行います。
- ライブラリは動的 import で読むので、起動時間とバンドルに影響しません。

### 5.4 構築

**全国マスター。** `ja.json`（`{ meta: { updated }, data: [{ code, pref, pref_k, pref_r, point, cities: [...] }] }`）を作ります。政令市の区なし親行は除外します（ABR の 1,918 行から 20 を除いて 1,898 になることを、Geolonia の公開データと一致確認済み）。

**段A（市区町村の町字）。** 町字と位置参照を (lg_code, machiaza_id) で左結合し、`town.json`（Geolonia 形式）を作ります。`chome` を漢数字化（`@geolonia/japanese-numeral`）し、`chome_n`、`koaza`、`rsdt`（`rsdt_addr_flg === '1'`）、`point` を持たせます。座標は `rep_srid` が EPSG:6668 / 4612 / 4326 のときだけそのまま採用します（実質恒等変換なので proj4 は使わない）。

**段B（市区町村の番号）。**

- 住居表示は本体と位置参照を (lg_code, machiaza_id, blk_id, rsdt_id, rsdt2_id)、地番は (lg_code, machiaza_id, prc_id) で、一時 SQLite により結合します（本体と位置参照は同じキー集合だが行順が違い、位置参照側に重複キーがある）。位置参照の重複キーは最初の行を採用し、位置参照が無い場合は座標なしで続けます。
- 町字ごとの節を連ねた txt と範囲表を書きます。節は `住居表示,<町字ID>\nblk_num,rsdt_num,rsdt_num2,lng,lat\n…` と `地番,<町字ID>\nprc_num1,prc_num2,prc_num3,lng,lat\n…`。ライブラリは節の1行目を捨てるだけなので、ファイル先頭のヘッダー部は省略し、開始位置は0からにします。
- 完了後に `town.json` へ `csv_ranges` を反映して、新しい版を有効にします（段Aだけの `town.json` を先に有効にし、段Bの完了で置き換える）。段Bが無い町は、ライブラリが level 3 に退避します。
- 状態フラグや廃止日による絞り込みは、Geolonia の生成器と同じく行いません。

**町字の点の索引。** 47県の町字と位置参照から、(lg_code, machiaza_id, 緯度, 経度, 格子) を `geo.sqlite` に入れます（約 19.7万点）。格子は約 1.1km 四方です。

**郵便番号。** `postal.sqlite` に郵便番号と市区町村コード（lg5）のインデックスを張ります。

- KEN_ALL の整形: 「以下に掲載がない場合」（1,870行）と「…の次に番地がくる場合」（17行）は町域を空にして、市区町村の既定行にします。括弧注記つき（6,479行）は括弧の前を町域にして、原文を `townRaw` に残します。階の注記つきの建物別の行は、町字に結びつけません。
- JIGYOSYO は、`office` に事業所名、`detail` に小字・丁目・番地等を入れます。個別番号の種別 1 は `po_box` です。
- zip は `yauzl`、CSV は `papaparse`、JIGYOSYO は `TextDecoder('shift_jis')` で読みます。
- **町字への結びつけ**は、市区町村ごとに使われたときに計算し、メモリに保持します。KEN_ALL の町域名を、同じ市区町村の ABR 町字の `oaza_cho`、`koaza`、`oaza_cho+koaza`、`oaza_cho+chome` に照合します。照合の前に、NFKC 正規化、漢数字のアラビア数字化、「大字」「字」「丁目」の除去、ヶ/ケ・ノ/之・ッ/ツの揺れの吸収を行い、「…一円」は末尾を外します。括弧注記が「（n〜m丁目）」なら `chome_n` が範囲内の町字に絞り、「（n〜m番地）」や番地の列挙は住所の番地が入るかで絞ります。
  - 実データの試作では、町域を持つ行（建物別の行と市区町村の既定行を除く）42,377 行のうち 41,224 行（97.3%）が結びつきました（東京・大阪・北海道・京都・愛知・神奈川・埼玉・福岡・兵庫・広島）。北海道が最も低く 91.1% です。
  - 未結合の行も、順引き（郵便番号 → 住所）には使えます。座標と逆引きの索引には載りません。

### 5.5 巨大データの処理方法

1. **全国で処理しない。** 5.2 の単位だけを処理します。全国の地番（約 10GB の zip、展開すると数百GB の CSV）は、運用者が事前取得を指定しない限り、触れません。
2. **ストリームで読む。** zip は一時ファイルに落とし、`yauzl.open` の `openReadStream` で展開しながら CSV を逐次解析します。CSV 全体をメモリに載せません（`fromBuffer` は数MB 以下の小さい zip だけ）。
3. **結合はディスク上の一時 SQLite で行う。** 市区町村単位なので、行数は多くても数十万〜百万行台です。メモリは一定で、終わったら一時ファイルを消します。
4. **出力は小さくする。** 住居表示・地番は1行 約28バイトの txt で、市区町村ごとに独立して保存します。
5. **別プロセス・低優先度・1件ずつ。** 構築は子プロセスで行い、`os.setPriority(0, 10)` で優先度を下げます。同時に走るのは既定で1件です。
   - 子の入口は、アプリ全体のバンドルではなく**構築専用の小さな入口**（`src/services/address_build_main.ts`）にします。Containerfile にビルドとコピーを1行ずつ足します（実測で、専用の入口は起動 0.06 秒、アプリ全体のバンドルは 0.6 秒・メモリ 152MB）。開発時は TypeScript の入口をそのまま使います。
6. **ディスク予算と破棄。** `SORA_ADDRESS_MAX_MB`（既定 2048）を超えたら、最近使われていない市区町村から破棄します。破棄したものは次に使われたとき再構築されます。事前取得を指定した市区町村は破棄せず、予算が足りなければ構築を止めて状態に記録します。
7. **待ちすぎない。** 6.4 のとおり、上限を決めて打ち切ります。
8. **事前取得は運用者の選択。** `SORA_ADDRESS_PRELOAD`（都道府県コードのカンマ区切り、または `all`）を指定すると、起動後に低優先度で順に取得します（再開できる）。目安は、全国で取得約 10GB、数時間規模（推定。実測して記録する）です。

### 5.6 更新

- 常駐タイマーは持ちません。**使われたときに**、そのデータの確認日時が期限（町字 7日、住居表示・地番 30日、郵便番号 7日、全国マスター・索引 30日）を過ぎていれば、裏で再確認します。HEAD で ETag / Last-Modified を比べ、変わっていれば作り直します。
- 古いデータで即答し、作り直しは裏で行います（stale-while-revalidate）。失敗しても旧データを使い続け、`lastError` を記録します。期限を大きく超えたら、出力の `dataset.stale` が `true` になります。
- 事前取得を指定した運用では、起動時に1回、署名を再確認します（24時間以内なら省略）。

### 5.7 設定

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `SORA_ADDRESS` | `lazy` | `off`: 3ツールを登録しない（`SORA_DEFER_TOOLS=false` の運用でも一覧に出ない）。ジオコーダーはローカルを見ない。`lazy`: 3ツールが呼ばれたときだけ取得する。ジオコーダーは取得済みのデータだけを使い、取得を引き起こさない。`eager`: ジオコーダーも、データが無い市区町村では裏で取得を始める（待たない） |
| `SORA_ADDRESS_DIR` | `dirname(getDatabasePath())/address` | 保存先 |
| `SORA_ADDRESS_MAX_MB` | `2048` | ディスク予算 |
| `SORA_ADDRESS_WAIT_MS` | `20000` | 住所ツールがデータの取得を待つ上限 |
| `SORA_ADDRESS_BUILD_CONCURRENCY` | `1` | 構築の同時実行数 |
| `SORA_ADDRESS_PRELOAD` | なし | 事前取得する都道府県コード、または `all` |

使わないユーザー（`off` または `lazy` で呼ばれない）には、ファイルの作成、通信、子プロセス、タイマー、メモリ使用が一切発生しません。

## 6. ツール

3ツールとも遅延有効（`deferredDefault`）で、モジュールは既存の `disaster`（`get_elevation`、`search_poi` と同じ）に置きます。REST は `/geo/` 配下で GET / POST の両方です。座標は `lat` / `lon`（`get_elevation` と同じ）で表します。

### 6.1 `search_postal_code`（郵便番号 ⇄ 住所候補）

REST は `/geo/postal-code`。入力は `{ zipcode?, address?, noCache? }` で、`zipcode` と `address` のどちらか一方です（両方、またはどちらも無いときは `INVALID_INPUT`）。

- **`zipcode`（順引き）**: ハイフンと全角を許容し、7桁を検証します。
  - 返却: `{ zipcode, count, candidates[{ kind, prefecture, city, town, townRaw, detail?, office?, lgCode, lat?, lon?, machiazaIds? }], dataset, attribution }`。
  - `kind` は `general` / `office` / `po_box`。該当なしは `count: 0`（エラーにしない）。
  - 一般の候補の座標は、結びついた町字の代表点の平均です。事業所は、住所を正規化して座標を付け、キャッシュします。
- **`address`（逆引き）**: 住所を正規化し、町字に結びついた郵便番号を返します。
  - 返却: `{ address, normalized, level, postalCodes[{ zipcode, town, townRaw, exact, fallback }], dataset, attribution }`。
  - `exact` は括弧注記（丁目・番地の範囲など）まで合うこと。`fallback` は町字の専用番号が無く、市区町村の既定番号を返したことを表します。

### 6.2 `normalize_address`（正規化 ＋ 突き合わせ）

REST は `/geo/normalize-address`。入力は `{ address, level?, zipcode?, lat?, lon?, compareAddress? }` です。`level` は 1〜8（既定 8）で、解釈する深さの上限です。`lat` と `lon` は対で指定します。

- 先頭の `〒nnn-nnnn` と郵便番号は外して `postalCode` として返します（ライブラリは `〒` 付きだと解析できず level 0 になるため）。
- 返却: `{ input, postalCode?, pref, city, town, addr?, other, normalized, level, numberSource, keys, point?, postalCodes[], checks?, dataset, attribution }`。
  - `level` は 0（解析できず）、1（都道府県）、2（市区町村）、3（町丁目）、8（番地・号）。
  - `normalized` は pref + city + town + addr。建物名などは `other` に分けます。
  - `numberSource` は番地・号を何で照合したか（`rsdt` / `chiban` / null）。null なら番号は整形だけで未照合です。
  - `keys` は名寄せ・突き合わせの安定キー: `{ prefCode, lgCode, machiazaId, blk?, rsdt?, rsdt2?, prc? }`。
  - `point` は `{ lat, lon, level }`。`level` は 1（都道府県の代表点）、2（市区町村）、3（町字の代表点）、8（住居番号または地番の代表点）。
- **`checks`**（指定した項目だけ返す）:
  - `zipcode`: 住所から引いた郵便番号に、渡された番号が含まれるか。`match`（一致）、`partial`（同じ市区町村だが町が違う、または既定番号のみ）、`mismatch`（市区町村が違う）、`unknown`（解決できない）と、`expected[]`、`reason`。
  - `coordinates`: 渡された座標を逆ジオコーディングし、住所とキーで比較します。同じ町丁目で、level 8 なら距離 150m 以内で `match`。同じ市区町村で町が違う、または距離が離れていれば `partial`。市区町村が違えば `mismatch`。`distanceMeters` と最寄りの住所を添えます。
  - `compare`: `compareAddress` も正規化し、キーが一致する最も深い階層（`sameLevel`）、`identical` / `same-block` / `same-town` / `same-city` / `different` と `differences[]` を返します。

### 6.3 `reverse_geocode`（緯度経度 → 住所）

REST は `/geo/reverse`。入力は `{ lat, lon, maxDistanceMeters? }`（既定 300、最大 2000）です。

1. 町字の点の索引から、近い町字を最大10件取ります。
2. それらの市区町村の段Bを用意し、住居表示の町なら住居表示の節、それ以外なら地番の節から、最寄りの点を探します。
3. 範囲内にあれば level 8 の住所、無ければ最寄りの町字（level 3）を返します。

返却: `{ lat, lon, found, address?, normalized?, level, numberSource, distanceMeters, approximate, keys, postalCodes[], alternatives[≤3], dataset, attribution }`。精度の限界として、代表点による最寄り判定であり、ポリゴンの包含判定ではないことを、説明文と `approximate` で示します。

### 6.4 共通の出力と状態

- `dataset{ updatedAt, stale }`: 使ったデータのうち最も古い更新日と、期限を大きく超えているか。
- `incomplete: true` と `pending[]`: 待ち時間の上限（`SORA_ADDRESS_WAIT_MS`）までにデータが揃わなかったとき。取れている範囲で答え（段Aがあれば level 3）、構築は裏で続けます。次の呼び出しで完全になります。同じ市区町村への同時の要求は、1回の構築にまとめます。
- エラー: `ADDRESS_DATA_UNAVAILABLE`（必要なデータを取得できない。国外からの接続拒否、通信失敗、取得元の形式変更。理由つき、HTTP 502）。`SORA_ADDRESS=off` のとき REST は `ADDRESS_DISABLED`（404）を返します。入力の誤りは既存どおり `INVALID_INPUT`（400）です。

## 7. 既存機能との統合

- **ローカル優先のジオコーダー**（`src/services/geocoding.ts`）:
  - `createGeocoder({ local })` に注入口を足し、既定は住所モジュールの局所ジオコーダーにします。呼び出し側の `geocodeAddress` は変えません。
  - 住所らしい入力（正規化が level 3 以上で点がある）と郵便番号（`1000001`、`〒100-0001`）はローカルで解決します。`source: 'abr'`、`needsVerification: false`（郵便番号が複数の町にまたがる場合は `true`）。1.1 秒間隔の制限を受けません。
  - ローカルで解決できない入力（取得済みデータが無い、`off`、取得失敗、地名・駅名・施設名・通称）は、**待たずに**従来の経路（Nominatim → 国土地理院）へ進みます。`eager` では、データが無い市区町村の取得を裏で始めます。
  - `GeocodingResult.source` に `'abr'` を足し、`GEOCODING_ATTRIBUTIONS.abr`、`ElevationResultSchema` と `PoiSearchResultSchema` の enum、tool-health の出典マーカーと期待値（`geo.address` は `abr` も許す）を更新します。
- **`search_poi`**: `center` が住所・郵便番号でも解決されます。新しい任意項目 `withAddress`（既定 false）で、各施設に `addressInfo{ normalized, level, numberSource, keys, postalCodes, check{ status, distanceMeters } }` を付け、施設の住所を座標と突き合わせます（住所の質が低い OpenPOI の結果を見分けられる）。
- **`get_elevation`**: `geocodeAddress` 経由で自動的にローカル優先になります。コード変更は不要です。
- 外部依存として残るもの: Nominatim と国土地理院（住所以外の地名）、OpenPOI（`search_poi` の検索そのもの）、国土地理院の標高 API（`get_elevation`）。
- 検討して統合しないもの: `get_weather` の `city_map.ts`（気象庁の予報区コードへの対応表で、ABR の市区町村コードでは置き換えられない）、`search_road_traffic` の都道府県名、`search_route` の駅名。

## 8. 地番と配送の正確さ

- 宛先は、住居表示実施区域では「丁目・番・号」、それ以外では「大字・字＋番地（地番）」で書かれ、配達はどちらにも行われます。ABR の町字 727,467 件のうち住居表示ありは 61,423 件（8.4%）、市区町村 1,892 のうち住居表示の町があるのは 687（36%）です（町字の数での比率で、人口比ではない）。
- 地番データが関わるのは「番地の実在確認」と「番地単位の座標」だけです。郵便番号、町域名、番号の表記整形（「７番１号」→「7-1」）は、地番データがなくても動きます。
- 地番が無いと、住居表示でない町の座標は町字の代表点（数百m〜数km の誤差）になります。配送ルートや誤配防止のため、地番を含めます。実測した6市（長崎・高知・佐賀・福知山・豊橋・函館）では、住居表示でない町の 94〜99% に地番があります。
- 参考ライブラリは、町に住居表示の印（`rsdt`）があれば住居表示データ、なければ地番データを引き、どちらも無ければ level 3 で止めて番地以降を整形だけします。住居表示の町では地番を使いません（郵便上の住所は住居表示のため）。
- 地番データは登記所備付地図に基づきます。**存在確認は証拠であって証明ではありません。** 出力に `numberSource` を必ず返し、最終的な配達可否は運送会社の住所照合に任せる前提とします。

## 9. レイテンシ

測定は、本番ホスト（日本。メモリが逼迫しスワップを使っている状態）で、試作コードにより行いました。試作は CSV を丸ごと解析する非ストリーム版です。実装後に同じ条件で測り直し、右列の目標を満たすことを完了条件にします。

| 場面 | 実測 | 目標 |
|---|---|---|
| データが揃った後の `normalize_address` | 世田谷区（住居表示）で p50 0.4ms、p95 4ms。地番の町が多い京都市中京区（町の JSON が 814KB）で p50 4ms、p95 24ms。住所でない文字列を見分けるのは約 0.4ms | p95 50ms 以下 |
| モジュールの作り直し直後・市区町村の最初の読み込み | 世田谷区 69ms、京都市中京区 209ms | 250ms 以下 |
| 郵便番号の順引き（SQLite の索引引き） | 1回 2µs（14.7万行） | p95 20ms 以下 |
| `reverse_geocode`（近傍10町の節を読んで最寄りを探す） | 世田谷区で p50 4ms、p95 7ms（約 7,900 行を走査） | p95 50ms 以下 |
| 既存ジオコーダーの住所解決 | 今は最低 1.1 秒間隔＋外部通信（上限 10 秒）。ローカルなら上の `normalize` と同じ桁 | 住所は 50ms 以下。地名は今と同じ |
| 初めて使う市区町村・町丁目まで（段A） | 取得＋構築が 63〜132ms（zip 5〜23KB） | 500ms 以下 |

- ダウンロードは速く（1ファイル 55〜190ms）、時間の大半は CSV の解析と結合です。

## 12. リスクと対策

- **初回呼び出しの待ち時間**: 上限で打ち切り、`incomplete` と `pending` で明示します。段Aだけで level 3 の答えは速い。事前取得で解消できます。
- **試作の測定条件**: メモリが逼迫したホストで、非ストリーム版で測りました。実装版は解析がストリームになり、メモリは減りますが、所要時間は同程度か少し増える可能性があります。完了条件で測り直します。
- **地番の規約が未確認**: 実装の最初に本文を確認します。確認できなければ、地番の段は無効のまま出荷します。
- **地番で照合できた結果の過信**: `numberSource` を出力し、説明文に「存在確認は証拠であって証明ではない」と明記します。
- **ディスクの膨張**: 予算と破棄で上限をかけます。事前取得で予算が足りなければ止まり、状態に記録します。
- **郵便番号と町字の結びつけ**: 実測 97.3%。未結合の行は順引きでは使えるので、劣化は座標と逆引きの欠落に留まります。
- **逆ジオコーディングの精度**: 代表点による最寄り判定の限界を、`approximate` と `distanceMeters` と説明文で明示します。
- **ABR のファイル名や列の変更**: ヘッダー名で読み、検証で弾き、旧データを維持します。`stale` で見える化します。
- **ABR の国外ブロック**: 国外の運用者は取得できず、`ADDRESS_DATA_UNAVAILABLE` を返します（`off` にできる）。live 検査は 403 を `blocked`（soft hold）にします。
- **ローカル優先化による既存の出力の変化**: 住所らしい入力で、データが取得済みのときだけです。`source` と `geocodingAttribution` に由来が出ます。地名・駅名の経路は不変で、契約テストで固定します。
- **Geolonia ライブラリの更新停止**（最終リリースは 2024-12-24）: MIT なので、問題が出たら固定して使うか取り込めます。`requestHandlers` の差し替えに依存するため、ライブラリの更新は統合テストで検出します。追加依存（`undici` など）はイメージを数MB 増やしますが、起動には影響しません。

## 13. 実装の分け方（概要）

各段階の終わりで型検査・lint・関連テストが通り、単独で成立する状態にします。詳細は実装計画に書きます。

1. スパイクと前提の確認: 依存の追加、手書きデータでの `requestHandlers.file` の差し替え、`server.js` からの動的 import、規約の確認、未使用時に何も起こらないことの確認。
2. 設定・状態・待ち行列・子プロセス・仮想ファイル・ディスク予算と、全国マスター、段A。
3. `normalize_address`（level 3）と、郵便番号の取り込み・結びつけ、`search_postal_code`。
4. 段B（住居表示・地番）、level 8、町字の点の索引、`reverse_geocode`。
5. 突き合わせ（`checks`）。
6. 統合: 局所ジオコーダー、`search_poi` の `withAddress`、関連スキーマと既存テストの更新。
7. 登録（MCP・REST・OpenAPI・ツール台帳・live 検査・契約テスト・README・instructions）と、運用メモ `docs/operations/address-data.md`。
8. 実データでの検証と調整。
